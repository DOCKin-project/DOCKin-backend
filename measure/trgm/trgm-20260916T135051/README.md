# D1 — `pg_trgm` GIN을 작업일지 검색에 붙이면: 100만 행, 인덱스 전후 A B A B

- 일시: 2026-09-16 13:51~14:05 KST, 로컬(Windows 10, i3-6100, Docker Desktop/WSL2)
- rig: `scripts/db/trgm-lab.sh` (기본값: `ROWS=1000000 WRITE_ROWS=50000 PASSES="A B A B"`)
- 컨테이너: `pgvector/pgvector:pg17`, `--memory=512m` (운영과 같음), `shared_buffers` 128MB 기본, `synchronize_seqscans=off`(아래 함정 3)
- 표: `work_logs` 꼴 100만 행, 힙 **469MB**. 본문은 `CorpusSeedGeneratorTest`의 어휘 조합(설비×부위×증상×원인×조치×후속), 행 259자 근처.
  희귀 문장 `'특이사항으로 크랭크축 균열을 발견했다.'`는 1/10,000행(100건). 500명·6구역 = `WorkLogListBenchmarkTest`와 같다.
- A = `user_id` B-tree만(운영 V4와 같다) / B = `title`·`log_text`에 `gin_trgm_ops` GIN 둘
- 관련: `docs/DB-IMPROVEMENT-PLAN.md` D1, `docs/PG-BOOK-EXPERIMENTS.md` 카드 ④, `WORK-BACKLOG.md` P2-15-5 ⑤

> **절대 시간을 옮겨 적지 말 것.** 이 호스트의 값이다. 볼 것은 A↔B의 배수, 같은 조건 두 패스의 폭, 실행계획의 노드다.

"실제 SQL"은 `WorkLogRepository.searchWorkLogs`가 내는 문장 그대로다 — 구역 84명 `IN` + `(title LIKE OR log_text LIKE)` + 커서 + `ORDER BY created_at DESC, log_id DESC` + `LIMIT 20`.

## 결과 — 대가

| 항목 | 값 |
|---|---|
| GIN 크기 | `title` **24MB** + `log_text` **157MB** = 181MB. 힙 469MB의 **39%** (인덱스 합계 233MB, 총 703MB) |
| 빌드 `CREATE INDEX CONCURRENTLY` | title 23.7s · log_text **180.4s** |
| 빌드 일반 `CREATE INDEX` | title 11.5s · log_text **89.8s** — CONCURRENTLY가 **2배** |
| 쓰기 50,000행 INSERT × 3, 중앙값 | A **3.3 / 2.7s** → B **13.4 / 13.7s** = **4.5배** |
| `pg_prewarm` 블록 수 | A 63,718 (498MB) → B 87,185 (681MB) — **512MB 컨테이너에 다 안 들어간다** |

## 읽는 법

1. **실제 검색은 키워드가 뭐든 A에서 약 240ms고, 그 240ms는 LIKE가 아니다.** 네 검색 모두 계획이 같다: `idx_work_logs_user` Bitmap Index Scan → Bitmap Heap Scan **29,900블록** (병렬 2 워커) → Filter(LIKE) → Sort → Limit. 구역 84명의 16만 8천 행이 힙 6만 페이지 전체에 흩어져 있어 절반을 읽고, `ORDER BY`가 있어 `LIMIT 20`의 조기 종료가 없다. 키워드는 읽은 뒤 거른다. **P2-15-5 ⑤가 "B-tree로 안 변한다"고 한 자리의 실제 비용은 키워드 필터가 아니라 구역 필터 + 정렬이다.**
2. **GIN이 계획을 바꾼 것은 희귀 4자(Q1)뿐이다.** 그때 160배. 희귀 3자는 안 쟀다 — 트라이그램은 생기니 같은 방향이겠지만 `[실측 필요]` — 힙 98블록만 읽는다. 통제군 A 두 패스는 241 / 300(폭 20%), B 두 패스는 1.7 / 1.7.
3. **흔한 3자(Q2)는 플래너가 갈팡질팡한다.** 패스 2는 GIN을 안 골랐고(261ms, A와 같음) 패스 4는 GIN∧user BitmapAnd를 골랐다(122ms, 2배). 두 패스 사이에 바뀐 건 `ANALYZE`의 표본뿐이다. 골라도 2배인 이유는 힙 블록 수가 거의 같아서다(9,979 vs 10,058 — 1/3이면 모든 페이지에 있다) — 줄어든 건 병렬 워커의 중복 읽기고, 대신 병렬이 사라진다. **같은 검색이 통계 표본에 따라 120↔260ms를 오가는 것은 인덱스가 주는 이득이 아니라 변동이다.**
4. **2자 키워드(Q3·Q4)는 GIN이 아예 못 쓴다.** `LIKE '%균열%'`에서 pg_trgm이 뽑을 트라이그램이 없다(패턴은 패딩 없이 3자 단위). 계획은 A와 같고, 패스 4에서 0.7~0.8배로 **더 느린** 것은 함정 5(캐시 경합 `[추정]`) 방향이다. 한국어 검색어는 2자가 흔하다 — 설비명·부위명·증상 대부분. 이걸 하려면 `pg_bigm`(2-gram)인데 이 이미지엔 없다.
5. **Q5(⑤ 원문)의 A 11ms는 이 rig의 값이지 P2-15-5의 432ms가 아니다.** 함정 4. GIN은 그 복권을 없앤다(1ms 고정)는 것까지가 이 줄이 말하는 것이다.
6. **대가는 넓다.** 힙의 39% 크기, 벌크 쓰기 4.5배, 온라인 빌드 3분, 그리고 512MB 컨테이너에서 GIN 181MB가 힙 페이지를 캐시에서 밀어낼 수 있다(prewarm 681MB > 512MB — 작업 집합과 한도의 비교일 뿐, 상주율은 안 쟀다. `[추정]`, `pg_buffercache`로 확인). 실제 쓰기는 한 행씩이라 `fastupdate` 대기 목록이 4.5배를 줄여 주겠지만, 그 목록을 비우는 비용은 어차피 누군가(autovacuum 또는 다음 INSERT)가 낸다.

## 판단 — D1은 "지금은 안 붙인다"를 추천한다 (결정은 사용자)

이득은 좁다: 잰 것 중 계획이 바뀐 건 **희귀 4자**뿐이다(희귀 3자는 `[실측 필요]`). 흔한 키워드는 변동만 생기고, 2자 키워드는 아무 일도 없다.
대가는 넓다: 크기 39%, 쓰기 4.5배, 캐시 경합 가능성`[추정]`.
그리고 느린 자리(240ms)는 LIKE가 아니라 **구역 필터 + 정렬**이라 GIN이 답이 아니다 — 그 자리의 후보는 P2-15-8이 거절한 복합 인덱스 계열이고, 100만 행이 됐을 때 다시 잰다.
운영 `work_logs`는 2만 행이고, 그 규모에선 A가 이미 한 자릿수 ms다.

바뀌는 조건: (a) 행이 수십만을 넘고 (b) 검색어 분포가 3자 이상(트라이그램이 생기는 길이) 희귀어 위주라는 것이 `pg_stat_statements`(D3)로 보일 때. 그때는 `log_text`만이 아니라 **`title`만** 붙이는 선택지(24MB, 11s)도 있다 — 제목엔 설비명이 항상 들어간다.

## 부수 발견 — `ANALYZE`가 행 수와 무관하게 50초

시드 뒤와 매 패스 앞의 `ANALYZE work_logs`가 **47~55초**. 2만 행 연기 시험에서도 42초였다 — 표본이 30,000행으로 고정이라 행 수와 무관하다.
원인은 en_US.utf8의 `strcoll`: `log_text` 표본 3만 건을 정렬하는 데 42s, `title` 11s, 같은 표본을 `COLLATE "C"`로 바꾸면 **0.4s**. 긴 공통 접두사를 가진 한국어 문장에서 glibc 다단계 비교가 극단적으로 느리다.
운영 `dockin-db`도 en_US.utf8이라(`compose.yaml`에 로케일 설정 없음) **autovacuum의 auto-analyze가 `work_logs`에 올 때마다 CPU 50초를 쓴다**(10% 변경마다). 잠금은 `ShareUpdateExclusive`라 읽기·쓰기를 막진 않는다. `[미검증: 운영 실측 없음]` — `pg_stat_user_tables.last_autoanalyze`와 그 시각의 CPU를 보면 갈린다. 대안은 `ALTER TABLE ... ALTER COLUMN log_text SET STATISTICS 10`(표본 3,000행) — 본문 컬럼의 히스토그램은 어차피 아무 쿼리도 안 쓴다.
