# JVM 가비지 컬렉터 — 종류와 이 저장소의 실제 상태

- 기준일: 2026-08-06
- 계기: 색인 부하에서 GC 로그를 처음 켜보니 **이 앱이 Serial GC로 돌고 있었다.** 아무도 그렇게 지정한 적이 없다.
- 관련: 백로그 P2-14-3, [이슈 #32](https://github.com/DOCKin-project/DOCKin-backend/issues/32), `compose.gc.yaml`

> **이 문서의 목적은 컬렉터를 고르는 것이 아니라 "지금 무엇이 돌고 있고 왜 그것이 골라졌는지"를 아는 것이다.**
> 바꾸는 판단은 그 다음이고, 이 저장소의 규칙대로 **재보기 전에는 내리지 않는다.**

---

## 0. GC가 무엇인가

프로그램이 객체를 만들면 메모리를 차지한다. 문제는 **언제 그것을 치우느냐**다.

C 계열에서는 사람이 직접 반납한다.

```c
WorkLog* log = malloc(...);
...
free(log);              // 직접 반납
```

이 방식이 어려운 이유는 실수의 결과가 전부 다르기 때문이다.

| 실수 | 결과 |
|---|---|
| `free`를 **안 하면** | 메모리 누수. 프로세스가 계속 커지다 죽는다 |
| **두 번** 하면 | double free. 크래시 |
| 반납하고 **또 쓰면** | use-after-free. **보안 취약점의 단골이다** |

**자바에는 `free`가 없다.** 대신 JVM 안에서 도는 청소부가 이 일을 대신한다.
그것이 **Garbage Collector**다.

### 무엇을 쓰레기로 판정하는가

기준은 하나다.

> **지금 살아 있는 코드에서 이 객체까지 도달할 수 있는가?**

GC는 확실히 살아 있는 것들 — 실행 중인 메서드의 지역변수, static 필드 등, 통틀어
**GC Root** — 에서 출발해 참조를 타고 간다. A가 B를, B가 C를 참조하면 셋 다 살아 있다.
**타고 갔는데 닿지 않는 것이 쓰레기다.**

```java
WorkLog log = new WorkLog();   // 생성
log = null;                     // 아무도 이 객체를 가리키지 않는다
                                // -> 도달 불가 -> 다음 GC 때 회수
```

이 저장소 코드 어디에도 "이것을 치워라"가 없는데 메모리가 터지지 않는 것이 이 덕분이다.

### 대가 — 앱이 멈춘다

참조를 세는 동안 **그 참조 관계가 바뀌면 계산이 틀린다.** 앱이 계속 객체를 만들고
참조를 갈아끼우면 GC는 무엇이 살아 있는지 확정할 수 없다.

그래서 GC는 앱을 잠깐 멈춘다. 이것을 **stop-the-world**라 하고, 멈춘 시간이 **pause**다.

```
GC(69) Pause Young (Allocation Failure) 124M->55M(247M) 65.093ms
                                                        ^^^^^^^^^
```

**이 65ms 동안 이 서버는 아무 요청도 처리하지 않았다.** 그 순간 들어온 요청은
그만큼 더 기다린 것이다.

**이 pause를 어떻게 줄일 것인가에 대한 답이 여러 개이기 때문에 컬렉터가 여럿이다.**
아래 1절부터가 그 이야기다.

## 1. 왜 컬렉터가 여럿인가

GC는 세 가지를 동시에 잘할 수 없다. 하나를 올리면 다른 것이 내려간다.

| 축 | 뜻 | 누가 신경 쓰나 |
|---|---|---|
| **처리량(throughput)** | 전체 시간 중 앱이 실제로 일한 비율 | 색인 배치 |
| **지연(pause)** | 한 번 멈출 때 얼마나 멈추나 | API 응답 |
| **footprint** | GC 자신이 쓰는 CPU와 메모리 | 컨테이너, 작은 힙 |

**컬렉터가 여럿인 이유는 이 셋 중 무엇을 포기할지가 상황마다 다르기 때문이다.**
이 서비스는 두 성격을 다 갖는다 — 낮에는 API, 새벽 03:00에는 색인 배치(`rag.indexing.cron`).
그래서 "어느 쪽에 맞출 것인가"가 실제 질문이 된다.

---

## 2. 공통 전제 — 대부분의 객체는 금방 죽는다

거의 모든 컬렉터가 힙을 **young**과 **old**로 나눈다. 요청 하나를 처리하며 만든 객체는
대부분 그 요청이 끝나면 쓰레기가 되기 때문이다. 그래서 **young만 자주, 싸게 청소**하고
거기서 살아남은 것만 old로 승격시킨다.

이 저장소의 GC 로그에 그것이 그대로 보인다.

```
GC(69) Pause Young (Allocation Failure) 124M->55M(247M) 65.093ms
```

| 조각 | 뜻 |
|---|---|
| `Pause Young` | young 영역만 청소했다 |
| `Allocation Failure` | 새 객체를 놓을 자리가 없어서 촉발됐다. **정상적인 이유다** |
| `124M->55M` | 청소 전 124M, 청소 후 55M. **69M이 한 번에 죽었다** |
| `(247M)` | 현재 힙 전체 크기. 최대치(400M)가 아니라 **지금 커밋된 크기**다 |
| `65.093ms` | 이 동안 앱이 멈췄다 |

**young 컬렉션이 싼 이유는 죽은 것을 하나씩 지우지 않기 때문이다.** 살아남은 소수만
다른 영역으로 복사하고 나머지는 통째로 버린다. 그래서 **쓰레기가 많을수록 오히려 빠르다.**

## 3. 컬렉터별 정리

| 컬렉터 | 방식 | 강점 | 대가 | 플래그 |
|---|---|---|---|---|
| **Serial** | 스레드 하나로 전부 멈추고 청소 | footprint 최소, 단순 | 힙이 커질수록 pause가 그대로 길어진다 | `-XX:+UseSerialGC` |
| **Parallel** | 여러 스레드로 멈추고 청소 | **처리량 최대** | pause가 길다. JDK 8까지 기본값이었다 | `-XX:+UseParallelGC` |
| **G1** | 힙을 region으로 쪼개 **일부만** 청소. 마킹은 앱과 동시에 | 균형. pause 목표치를 지정할 수 있다 | region 관리 오버헤드 | `-XX:+UseG1GC` |
| **ZGC** | 거의 전 과정을 앱과 동시에 | pause가 **힙 크기와 무관**하게 1ms 미만 | CPU와 메모리를 더 쓴다 | `-XX:+UseZGC` |
| **Shenandoah** | ZGC와 목표는 같고 구현이 다르다 | 저지연 | 배포판에 따라 없을 수 있다 | `-XX:+UseShenandoahGC` |
| **Epsilon** | **아무것도 청소하지 않는다** | 힙을 다 쓰면 죽는다. 성능 테스트·수명이 짧은 작업용 | 실서비스용이 아니다 | `-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC` |

핵심 축은 **"멈추고 하느냐, 앱과 동시에 하느냐"** 다. 위로 갈수록 멈추고 아래로 갈수록
동시에 한다.

> **동시에 하는 것은 공짜가 아니다.** 앱이 객체를 쓰는 도중에 GC가 그 객체를 옮기려면,
> 모든 참조 접근에 검사 코드(read/write barrier)가 끼어야 한다. **저지연 컬렉터는
> 그 대가로 평상시 처리량을 조금씩 내주고 있다.** ZGC가 "pause는 1ms 미만이지만
> CPU를 더 쓴다"는 것이 이 뜻이다.

### G1을 조금 더

JDK 9부터 기본값이라 실무에서 가장 자주 만난다. 이름이 **Garbage First**인 이유는
힙을 균등한 region으로 쪼갠 뒤 **쓰레기가 많은 region부터** 고르기 때문이다.
같은 시간에 가장 많이 회수되는 쪽을 먼저 친다.

그래서 G1은 **"pause를 몇 ms로 맞춰라"** 는 목표를 받을 수 있다.

```
-XX:MaxGCPauseMillis=200      # 기본값 200
```

목표를 낮추면 한 번에 처리하는 region 수를 줄여 pause를 짧게 만들고, 대신 GC 횟수가
늘어 처리량이 내려간다. **이것이 "축을 맞바꾼다"의 구체적인 형태다.**

## 4. 이 이미지에서 실제로 쓸 수 있는 것 (실측)

배포판마다 포함된 컬렉터가 다르므로 문서를 믿지 않고 이미지에서 직접 확인했다.

```
openjdk version "21.0.12" 2026-07-21 LTS
OpenJDK Runtime Environment Corretto-21.0.12.8.1 (build 21.0.12+8-LTS)
```

| 컬렉터 | 결과 |
|---|---|
| Serial | ✅ `Using Serial` |
| Parallel | ✅ `Using Parallel` |
| G1 | ✅ `Using G1` |
| ZGC | ✅ `Using The Z Garbage Collector` |
| Shenandoah | ✅ `Using Shenandoah` |
| Epsilon | ✅ `Using Epsilon` |

**여섯 개 전부 쓸 수 있다.** Corretto는 Shenandoah를 포함한다(Oracle JDK에는 없다).

확인 방법:

```
docker run --rm --entrypoint sh <image> -c 'java -XX:+UseG1GC -Xlog:gc:stdout -version'
```

## 5. JVM이 알아서 고른다 — 그 규칙이 이 저장소에 걸렸다

아무것도 지정하지 않으면 JVM이 실행 환경을 보고 정한다. 판정 기준은 **server-class machine**
여부이고, 조건은 **CPU 2개 이상 그리고 메모리 1792MB 이상**이다. **둘 다** 만족해야 G1이 된다.

이 저장소의 컨테이너는 메모리 제한이 512M이라 탈락한다.

```
[info][gc     ] Using Serial
[info][gc,init] CPUs: 4 total, 1 available
[info][gc,init] Memory: 512M
```

### 2×2로 갈랐다

원인이 CPU인지 메모리인지 가르기 위해 네 조합을 직접 돌렸다.

| | 메모리 512M | 메모리 2G |
|---|---|---|
| **CPU 무제한** | Serial | **G1** |
| **CPU 1.0** | Serial | Serial |

두 가지를 읽을 수 있다.

1. **메모리 512M만으로 이미 Serial이었다.** CPU 상한(P2-10-3)을 넣기 전부터 그랬다
2. **CPU 상한이 두 번째 독립 원인을 추가했다.** 이제는 메모리를 2G로 올려도 Serial이다 —
   **손잡이 하나가 가려졌다**

> **이 기준은 물리 머신 시절에 만들어졌다.** "메모리 1.7GB도 없으면 장난감 기계겠지"가
> 당시에는 합리적이었다. 그런데 **컨테이너 시대에는 512M짜리 진짜 서버가 흔하다.**
> 기준이 현실을 따라가지 못한 자리이고, 그래서 아무도 모르게 컬렉터가 바뀐다.

## 6. 이 저장소의 GC 실측 (2026-08-06, 색인 부하 13분)

`compose.gc.yaml`로 `-Xlog:gc*,gc+heap=debug`를 켜고 색인을 돌린 결과다.

```
Young GC  132회     pause  min 2.3ms / median 12.9ms / max 132.6ms
Full  GC    8회     전부 (Metadata GC Threshold)
힙 점유             124M -> 55M (247M)     최대 400M 중 247M만 커밋
```

### 힙 400M이 좁다는 근거는 없다

**`Allocation Failure`로 인한 Full GC가 한 번도 없었다.** Full GC 8회는 전부
`Metadata GC Threshold`이고, 이것은 힙이 모자라서가 아니라 **기동 중 클래스 로딩으로
메타스페이스가 늘 때** 나는 것이다. 전부 기동 후 90초 안에 몰려 있고 그 뒤로는 없다.

또한 최대 400M 중 **247M만 커밋**되어 있다. 힙이 더 필요했다면 400M까지 늘었을 것이다.

> **다만 400M이라는 값 자체에도 근거는 없다.** 컨테이너 제한과 같은 값(512M)이던 것을
> 여유를 두려고 내린 것이지(P2-10-1) 측정으로 고른 값이 아니다. **"좁다는 근거가 없다"와
> "이 값이 맞다"는 다르다.**

### 눈에 띄는 것은 pause 최댓값

```
median 12.9ms  ->  max 132.6ms      약 10배
```

색인 배치에서는 문제가 아니다. **API 응답 경로에서는 보인다.**
다만 이 측정은 색인 부하 중에 잰 것이라 **API 트래픽 하의 pause 분포는 아직 모른다.** `[실측 필요]`

## 7. 힙 밖에도 메모리가 있다 — 컨테이너 제한과 힙 상한을 같게 두면 안 되는 이유

위의 `Metadata GC Threshold`가 그 증거다. **메타스페이스는 힙이 아니다.**
`-Xmx400M`에 잡히지 않는다.

JVM이 힙 밖에서 쓰는 것들:

| 영역 | 무엇 |
|---|---|
| 메타스페이스 | 클래스 정보. Spring은 클래스를 많이 로드한다 |
| 스레드 스택 | 스레드당 기본 1MB. Tomcat 워커 200개면 그것만으로 상당하다 |
| 코드 캐시 | JIT이 컴파일한 기계어 |
| 다이렉트 버퍼 | NIO, Netty(Redisson·WebClient가 쓴다) |
| GC 자신의 자료구조 | 컬렉터마다 다르다 |

**그래서 힙 상한을 컨테이너 메모리 제한과 같게 두면, 힙을 상한까지 채우는 것만으로
컨테이너 제한을 넘어 OOM Killer에 죽는다.** 그때 남는 것은 자바 예외가 아니라
**종료코드 137**이라 원인이 로그에 없다.

이것이 P2-10-1에서 512M → 400M으로 내린 이유이고, **GC 로그가 그 판단을 사후에 뒷받침했다.**

## 8. GC 로그 켜고 읽는 법

이 저장소에서는 `compose.gc.yaml` 오버레이로 켠다.

```
docker compose -f compose.yaml -f compose.gc.yaml up -d dockin-app
docker exec dockin-app-1 sh -c 'tail -f /tmp/gc.log'
```

플래그는 이렇다.

```
-Xlog:gc*,gc+heap=debug:file=/tmp/gc.log:time,uptime,level,tags:filecount=5,filesize=20M
       ^^^ 무엇을      ^^^^^^^^^^^^^^^^^ 어디에   ^^^^^^^^^^^^^^^^^^^^^ 무엇을 덧붙여
```

| 자주 쓰는 조각 | 뜻 |
|---|---|
| `gc` | 컬렉션 한 줄 요약. 이것만으로도 대부분 파악된다 |
| `gc*` | GC 관련 전부. 기동 시 컬렉터 선택도 여기서 나온다 |
| `gc+heap=debug` | 세대별 점유 추이. **힙이 좁은지 넓은지 보려면 필요하다** |
| `safepoint` | 앱이 멈춘 전체 시간. GC 외의 정지도 잡힌다 |

> **이 오버레이가 성립하는 전제는 `JAVA_OPTS`가 실제로 읽힌다는 것이다.**
> 2026-08-06 이전에는 `Dockerfile`의 ENTRYPOINT가 exec 형식이라 셸을 거치지 않아
> 변수가 확장되지 않았고, **GC 로그를 켤 방법 자체가 없었다**(P2-10-1).

## 9. 아직 안 본 것

- **API 트래픽 하의 pause 분포** — 6절은 색인 부하에서만 쟀다 `[실측 필요]`
- **G1로 바꿨을 때의 실제 차이** — 힙 400M에서 G1이 나을지는 재보기 전에는 모른다.
  region 관리 오버헤드가 상대적으로 커서 **오히려 나쁠 수도 있다** `[실측 필요]`
- **메타스페이스 실사용량** — `Metadata GC Threshold` Full GC가 8회 났다는 것은
  초기값이 실제 필요보다 작다는 뜻일 수 있다. `-XX:MetaspaceSize`로 줄일 여지 `[실측 필요]`
- **`-XX:MaxRAMPercentage`** — 지금은 `-Xmx400M`으로 절대값을 박아두었다.
  비율 지정으로 바꾸면 컨테이너 제한을 바꿀 때 힙이 따라온다. 다만 **컬렉터 선택 규칙과
  얽히므로**(5절) 함께 봐야 한다

## 10. 그래서 지금 무엇을 할 것인가

**당장 컬렉터를 바꾸자는 결론이 아니다.** 확인된 것은 둘이다.

1. 의도하지 않은 컬렉터(Serial)가 선택되어 있다
2. 그것이 문제라는 근거는 **아직 없다** — 힙은 여유롭고 Full GC도 힙 때문이 아니다

힙 400M에서 Serial은 비상식적인 선택이 아니다. 힙이 작으면 오히려 단순하고 오버헤드가 적다.
**문제는 성능이 아니라 아무도 고른 적이 없다는 것이다.**

> **가장 나쁜 것은 "환경이 알아서 고르게 두는" 지금 상태다.**
> 최소한 `-XX:+UseSerialGC`를 `JAVA_OPTS`에 적어 **선택을 기록**해야 한다.
> 그러지 않으면 컨테이너 메모리 제한을 올리는 순간 컬렉터가 조용히 G1로 바뀐다.
> **컨테이너 메모리 설정과 GC 컬렉터가 연결되어 있다는 사실이 지금 어디에도 적혀 있지 않다.**

이 문서가 그 자리를 메운다. 바꿀지 말지는 9절의 `[실측 필요]`를 채운 뒤에 정한다.
