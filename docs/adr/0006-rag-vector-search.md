# ADR-0006: RAG / 벡터 검색 도입 (Phase 1)

- 상태: **Phase 1 구현 및 실측 완료.** Phase 2(ANN 도입) 판단은 아래 8절의 트리거에 따름
- 대상 코드: `rag/*`, `ai/controller/AiController`, `ai/service/fastApiService`, `compose.yaml`
- 관련 문서: `docs/SERVICE-SCALE-ASSUMPTIONS.md`(규모 가정·실측), `docs/adr/0003`(검색 도메인 확장), `docs/PROJECT-SCOPE.md`(담당 범위)
- 작성 목적: 챗봇이 근거 없이 답하던 구조에 검색 단계를 넣으면서 내린 결정과 그 근거를 남긴다. ADR-0001과 동일하게 **숫자를 지어내지 않으며**, 측정한 값과 가정한 값을 구분한다.

---

## 1. 배경 — 챗봇에 R이 없었다

`fastApiService.chatBotFromSpringToFastApi()`는 사용자 질문을 팀원 FastAPI로 그대로 넘기고 답변을 받아 저장만 했다. **검색 단계가 통째로 비어 있었다.** 즉 RAG가 아니라 R 없는 G였고, 모델이 사내 작업일지나 안전교육 내용을 알 리 없으므로 답변에 근거가 없었다.

한편 코퍼스는 이미 DB에 있었다 — `work_logs.log_text`, `safety_courses.description`, `checklist_items`. 그리고 `work_log_translations`에는 같은 문서의 다국어 버전이 `log_id`로 묶여 있어, **교차언어 검색의 정답 라벨이 이미 존재한다.**

ADR-0003은 검색 확장 로드맵을 ngram FULLTEXT → Elasticsearch 순으로 잡아뒀다. 이 문서는 **그 로드맵에 벡터 검색을 어떻게 놓을지**에 대한 결정이다(9절 참고).

## 2. 결정 요약

| 항목 | 결정 | 근거 |
|---|---|---|
| 저장소 | **MySQL 8.0 유지** (3절) | 9.0은 커뮤니티에 ANN 인덱스 없음. PostgreSQL 이전은 실측 후 판단 |
| 임베딩 | **별도 컨테이너**(TEI) + `multilingual-e5-small` (4절) | JVM 힙 400M에 모델 적재 불가. 다국어로 교차언어 검색 확보 |
| 검색 방식 | **브루트포스(정확 최근접)** (5절) | 챗봇 0.02 TPS. recall 100%라 Phase 2의 정답 기준선이 됨 |
| 권한 | **선필터** (6절) | 후필터는 문서 존재 여부가 유출됨 |
| 장애 대응 | **키워드 폴백 + 모드 기록** (7절) | 부가 컴포넌트 장애가 챗봇을 멈추면 안 됨 |
| 오케스트레이션 | **Spring** | 권한·감사·트랜잭션이 이미 백엔드 자산. FastAPI 계약 불변 |

## 3. 저장소 — MySQL 8.0 유지

**MySQL 9.x 업그레이드는 선택지가 아니다.** `VECTOR` 타입과 `DISTANCE()`는 제공되지만 **ANN 인덱스는 HeatWave(유료) 전용**이라, 커뮤니티 에디션에서는 8.0 + `VARBINARY` 브루트포스와 성능이 같다. innovation 릴리스라 지원 주기도 짧다(LTS는 8.4). 문법적 편의만 얻고 스택을 흔드는 셈이다.

**PostgreSQL 전면 이전은 Phase 2로 미룬다.** 이전 비용 자체는 당초 예상보다 훨씬 작다 — `spring.sql.init.mode=never`라 `schema.sql`은 실행되지 않고 Hibernate가 엔티티에서 방언에 맞는 DDL을 생성하며, JPQL은 방언 독립이다. 실제로 손볼 곳은 `DocumentChunk.embedding`의 `columnDefinition = "VARBINARY(4096)"` → `BYTEA` 한 줄이다.

미루는 이유는 비용이 아니라 **순서**다. 브루트포스의 한계를 실측하기 전에 ANN을 도입하면 ADR-0002 2-3에서 스스로 경계한 "실측 없이 튜닝했다" 패턴이 된다.

> **이전 시 부수적으로 해결되는 것:** MySQL은 시퀀스가 없어 `AUTO_INCREMENT`(IDENTITY)를 쓸 수밖에 없고,
> 그 때문에 JDBC 배치 INSERT가 동작하지 않는다(8절 검증 결과). PostgreSQL로 가면
> `GenerationType.SEQUENCE` + pooled allocation을 쓸 수 있어 **배치가 정상 동작한다.**
> ANN 인덱스와 별개로 이전의 이득에 포함된다.

## 4. 임베딩 — 별도 컨테이너

JVM 힙이 400M(`JAVA_OPTS=-Xmx400M`)이라 모델을 애플리케이션 프로세스에 적재할 수 없다. 또한 모델을 분리하면 교체가 배포와 무관해지고 독립적으로 스케일할 수 있다 — 추론 서버를 따로 두는 것이 일반적인 구성이다.

**직접 구현하지 않고 HuggingFace TEI 이미지를 그대로 쓴다.** 배칭·큐잉을 다시 만들 이유가 없고, 이 프로젝트의 실질은 Spring 쪽 오케스트레이션에 있다.

**모델은 `intfloat/multilingual-e5-small`**(118M / 384차원). 다국어를 지원해 `work_log_translations`를 활용한 교차언어 검색이 가능하고, **언어별 analyzer 구성(ADR-0003 3-3의 Nori/ICU) 없이도 교차언어가 성립한다.** `bge-m3`(568M)는 i3-6100 2코어 환경에서 인덱싱 처리량이 나오지 않아 제외했다.

> **e5 계열 주의:** 질의는 `query: `, 문서는 `passage: ` 프리픽스가 필요하다. 어겨도 **에러 없이 품질만 떨어져** 추적이 어렵다. `EmbeddingClient`에서 메서드를 질의용/문서용으로 나눠 호출자가 직접 다루지 못하게 강제했다.

## 5. 검색 — 브루트포스(정확 최근접)

Phase 1은 ANN 인덱스 없이 후보 전체와 코사인 유사도를 계산한다. 근거는 둘이다.

1. **챗봇 트래픽이 약 0.02 TPS**라 지연시간 요구가 사실상 없다(`SERVICE-SCALE-ASSUMPTIONS.md` 3-2).
2. **근사가 아니므로 recall이 100%다.** Phase 2에서 ANN을 도입할 때 이 결과가 그대로 **정답(ground truth) 기준선**이 된다. 벡터DB부터 시작했다면 비교 기준을 따로 만들어야 했다.

### 스키마 설계

`document_chunks`는 여러 원본을 `(source_type, source_id)`로 **다형 참조**하므로 FK를 걸 수 없다. 정리는 `IndexingService` 책임이다.

| 컬럼 | 이유 |
|---|---|
| `content_hash` (SHA-256) | 재색인 멱등성. 10만 청크 인덱싱에 약 20분이 걸려 중단될 수 있고, 해시가 같으면 임베딩을 건너뛰어 이어서 진행한다 |
| `embedding VARBINARY(4096)` | 브루트포스가 전체를 훑으므로 BLOB의 오프페이지 저장을 피한다. 가변 길이라 384차원이면 1536바이트만 쓰고, 1024차원까지 `ALTER` 없이 수용한다 |
| `embedding_dim` / `embedding_model` | 모델 교체 과도기에 차원이 다른 청크가 공존할 수 있다. 비교 불가한 청크를 걸러내고 구버전을 식별·삭제하는 근거 |
| `visibility` / `owner_user_id` | 권한 선필터용 비정규화 (6절) |

### 청킹

모델 입력 상한이 **512 토큰**이며 이는 학습 시 위치 임베딩 개수로 고정된 **구조적 상한**이다. 실측한 한국어 토큰 비율은 0.56~0.73 토큰/글자로 **영어의 약 2배**다(`SERVICE-SCALE-ASSUMPTIONS.md` 6-1).

최악값 0.73 기준 **500자 ≈ 365토큰**으로 잡았다. 상한에 맞춰 700자로 하지 않은 이유는 숫자·기호가 섞이면 비율이 더 오를 수 있고, **잘린 내용은 오류 없이 유실되기 때문**이다. 청크가 다소 늘어나는 편이 낫다.

소스마다 적절한 절단 기준이 달라 `ChunkingStrategy` 인터페이스로 분리했다. 사내 규정 문서(Phase 1.5)는 조/항 경계를 지켜야 하므로 별도 구현체가 필요하다.

## 6. 권한 — 후필터가 아니라 선필터

**벡터 유사도만으로는 접근 제어를 할 수 없다.** 검색 결과가 그대로 챗봇 프롬프트에 들어가므로, 권한 처리가 빠지면 남의 작업일지 내용이 답변에 녹아 나간다.

**후필터(top-k 후 걸러내기)를 쓰지 않은 이유:**

1. **존재 여부가 유출된다.** k=5로 요청했는데 3건만 돌아오면 "내가 못 보는 문서가 2건 있다"를 알 수 있고, 검색어를 바꿔가며 반복하면 내용 없이도 문서의 윤곽을 그릴 수 있다.
2. **실수하면 그대로 샌다.** 후필터를 한 군데라도 빠뜨리면 LLM이 내용을 답변에 섞는다. 선필터는 데이터가 애초에 들어오지 않아 그 실수가 불가능하다.

선필터이므로 over-fetch도 불필요하다.

### 메모리 — 본문을 후보에 싣지 않는다

브루트포스는 후보 전체를 메모리에 올린다. 엔티티를 통째로 읽으면 청크당 벡터 1.5KB + 본문 약 1.5KB로 10만 청크에서 300MB에 달해 `Xmx400M`에서 위험하다. `ChunkVector` 투영으로 **벡터만 읽어 점수를 매기고, 본문은 최종 top-k에 대해서만 조회**한다.

### 결과 다양성

원본 문서당 최대 2청크로 제한한다. 긴 작업일지 하나가 top-k를 독식하면 근거가 한쪽으로 쏠린다.

## 7. 폴백 — 장애 시에도 권한은 느슨해지지 않는다

임베딩 서버는 나중에 붙인 부가 컴포넌트다. 그것이 죽었다고 챗봇 전체가 멈추면 안 된다 — **ADR-0001의 "Redis가 죽어도 DB가 최종 방어선"과 같은 사고방식**이다.

키워드(LIKE) 검색으로 떨어지되, **같은 `document_chunks`에 같은 선필터를 적용한다.** 기존 `Work_logsRepository.searchWorkLogs`는 소유자 필터가 없어 그대로 폴백에 쓰면 **장애 상황에서만 남의 작업일지가 새어 나가는** 사고가 된다.

폴백은 **등급이 내려간 서비스**이지 동등한 대체가 아니다. 벡터 검색은 "안전벨트"로 물어도 "추락 방지 장비"를 찾지만 LIKE는 글자가 일치해야 한다. 따라서 `chat_history.retrieval_mode`에 `VECTOR`/`KEYWORD`/`NONE`을 남겨 **"요즘 답변이 이상하다"가 아니라 "언제부터 폴백이었다"로 추적**할 수 있게 했다.

`source_chunk_ids`도 함께 남긴다. 잘못된 답변이 나왔을 때 모델 문제인지 검색 문제인지 가르는 유일한 단서다.

## 8. 실측과 Phase 2 트리거

전체 수치와 측정 조건은 `SERVICE-SCALE-ASSUMPTIONS.md` 6절에 있다. 결정에 직접 쓰인 것만 옮긴다.

| 측정 | 값 |
|---|---|
| 임베딩 처리량 (배치 32건) | **12 ms/건** — 단건(99ms) 대비 약 8배. 인덱싱은 반드시 배치 |
| 브루트포스 10만 청크 / 일반 사용자 | **1,485 ms** |
| 브루트포스 10만 청크 / 관리자 전체 | **5,165 ms** |
| 10만 청크 벡터 크기 | **146.5 MB** (추정 154MB와 일치) |
| INSERT 방식 (JDBC 수준, 1만 건) | 건별 24,081ms vs 배치 5,887ms — **4.1배** |

### 인덱싱 배치 — 검증에서 드러난 두 가지

**① JDBC 배치 INSERT는 현재 동작하지 않는다.** `hibernate.jdbc.batch_size`를 켜도 `DocumentChunk.chunkId`가
`GenerationType.IDENTITY`라 Hibernate가 INSERT 직후 생성 키를 읽어야 해서 문장을 묶지 못한다.
MySQL `Com_insert`로 확인한 결과 10,000건 저장에 INSERT 문장이 **정확히 10,000개**였다(문장당 1행).
**에러 없이 설정이 무시된다.**

> **JdbcTemplate 벌크 INSERT로 우회하지 않기로 했다.** 전체 인덱싱에서 임베딩이 지배적이라 체감이 약 13%에 그치고,
> **PostgreSQL 이전 후 `GenerationType.SEQUENCE`로 전환하면 근본 해결**되기 때문이다(시퀀스는 INSERT 전에
> 키를 받아오므로 배치가 정상 동작한다). 임시 우회는 Phase 2에서 걷어내야 할 부채가 된다.
> 대신 `HibernateBatchInsertVerificationTest`를 남겨, **이전 후 같은 방법으로 배치가 켜졌는지 확인**할 수 있게 했다.
> UPDATE는 IDENTITY 제약과 무관하므로 재색인 시에는 배치가 유효하다 — 설정은 유지한다.

**② 인덱싱 순회를 OFFSET에서 커서(keyset)로 바꿨다.** 처음에는 `PageRequest.of(pageNo++, 100)`을 썼으나,
대용량 배치에 웹 화면용 페이징 관용구를 그대로 가져온 것이었다. 문제가 셋이었다.

- `OFFSET`은 앞의 행을 읽고 버린다. 1,000페이지 순회 시 누적 스킵이 약 5천만 행
- 정렬을 주지 않아 **페이지 경계에서 행이 중복·누락**될 수 있었다
- 인덱싱이 도는 20분 동안 새 작업일지가 INSERT되면 뒤 페이지가 밀려 **건너뛰는 행**이 생긴다

`WHERE id > :lastId ORDER BY id LIMIT n`은 PK 인덱스로 시작점을 찾아 셋 다 해결한다.
(참고: `ChatMessagesRepository.findChatHistory`는 이미 커서 방식이었다 — 인덱싱만 일관성이 어긋나 있었다.)

**진짜 병목은 DB가 아니라 전송이었다.** `EXPLAIN ANALYZE` 기준 서버 내부 실행은 925ms인데 JDBC 왕복은 4,882ms로, **차이의 81%가 146MB를 애플리케이션으로 가져와 `byte[]`로 만드는 비용**이다.

`EXPLAIN`으로 확인한 또 하나는 권한 조건의 `OR`가 `idx_chunk_visibility`를 **전혀 타지 않는다**는 점이었다(10만 행을 모두 읽은 뒤 Filter에서 10,020건으로 축소, 약 90%를 헛읽음). 두 조회로 분리해 인덱스를 타게 고쳤으나 **개선은 770 → 659ms(14%)에 그쳤다.** 인덱스는 "어떤 행을 찾을지"의 비용을 줄일 뿐, 찾은 데이터를 옮기는 비용은 그대로이기 때문이다.

> ### Phase 2 전환 트리거
>
> 아래 중 하나라도 해당하면 ANN 도입을 착수한다.
>
> 1. **청크 수가 10만을 넘을 때** — `Xmx400M` 기준 브루트포스 적재 상한(실측 146.5MB)
> 2. **검색 지연이 사용자 체감을 해칠 때** — 10만 관리자 경로가 이미 5.2초
>
> **해결 방향은 쿼리 튜닝이 아니다.** 병목의 81%가 전송이므로, **유사도 계산을 DB 안으로 옮겨 top-k만 전송하는 구조**로 가야 한다. pgvector가 빠른 이유도 ANN 인덱스만이 아니라 이 전송 제거에 있다.
>
> **다만 pgvector가 만능은 아니다.** ANN 인덱스와 권한 필터의 결합은 알려진 난제다 — 선필터를 걸면 HNSW 그래프 탐색이 부분집합에서 헛돌아 recall이 떨어지고, 후필터는 6절에서 거부한 방식이다. **이 결합 설계가 Phase 2의 핵심 과제**이며, 이번에 만든 브루트포스 결과가 그때 recall을 재는 정답 기준선이 된다.

## 8-1. Phase 2b 착수 — `vector` 타입 매핑 (완료)

8절이 예고한 "유사도 계산을 DB 안으로" 중 **첫 단계로 컬럼 타입만 먼저 바꿨다.** 검색 쿼리는 아직 그대로이며,
따라서 이 단계만으로는 성능이 달라지지 않는다. 인덱스와 쿼리 이전의 토대를 놓는 작업이다.

### 8절의 전제 하나가 틀렸다

이 문서와 백로그는 매핑을 "Hibernate가 모르는 타입 — 커스텀 `UserType` 또는 네이티브 쿼리"로 적어뒀다.
**Hibernate 6.4부터 `hibernate-vector` 모듈이 공식 지원한다.** 현재 7.2.0.Final이고 Spring Boot BOM이
버전까지 관리하므로 의존성 한 줄과 애노테이션 두 줄로 끝난다. 난이도를 "높음"으로 잡았던 것은
조사 없이 추정한 결과였다.

### 그 대신 드러난 것들

**① 차원이 스키마가 됐다.** HNSW 인덱스는 차원이 고정된 컬럼에만 만들 수 있다(pgvector는 차원 없는
`vector`도 허용하지만 그러면 인덱스를 걸 수 없어 ANN 도입 자체가 무의미하다). 그 결과 5절에서
`embedding_dim`을 둔 근거였던 **"모델 교체 과도기에 차원이 다른 청크가 공존한다"가 성립하지 않는다.**
가변 길이인 `VARBINARY`/`BYTEA`였기에 가능했던 성질이고, 차원이 다른 모델로 바꾸려면 컬럼 마이그레이션이 따라온다.
`embedding_dim`은 이제 "몇 차원 모델로 만든 행인가"의 기록으로만 남는다.

**② 확장 등록은 이미지와 별개다.** `pgvector/pgvector:pg17`에 확장 파일은 들어 있으나 데이터베이스에
등록되어 있지는 않다. `CREATE EXTENSION`이 없으면 Hibernate가 `vector(384)` 컬럼을 만들다 실패하는데,
**`ddl-auto=update`가 DDL 오류를 로그만 남기고 기동을 막지 않아** 앱은 정상 기동한 것처럼 보인다
— 2a에서 `SafetyCourse.createdAt`이 숨었던 것과 정확히 같은 방식이다. 같은 함정에 두 번 걸린 셈이라
`db/init/`을 마운트해 신규 환경에서는 자동 실행되게 했다. 다만 그 스크립트는 데이터 디렉터리가 비어
있을 때만 돌기 때문에 기존 볼륨에는 `docs/migration/2b-pgvector.sql`을 직접 실행해야 한다.

**③ `ALTER`가 행 0건에서도 거부된다.** `bytea → vector`는 자동 변환 규칙이 없어 `USING`을 요구한다.
값을 옮기지 않겠다는 뜻으로 `USING NULL::vector(384)`를 썼고, 이는 **행이 남아 있으면 `NOT NULL`
위반으로 실패**하므로 실수로 실제 임베딩을 날리는 것을 막아준다.

**④ 벡터가 TOAST로 나간다 — `VARBINARY` 선택의 근거가 그대로 따라왔다.**
5절에서 `embedding`을 BLOB이 아닌 `VARBINARY`로 둔 이유는 InnoDB의 오프페이지 저장을 피하기 위해서였다.
PostgreSQL의 대응물이 TOAST이며, 같은 문제가 재현된다.

| 측정 | 값 |
|---|---|
| `vector(384)` 크기 | **1,544 bytes** (4 × 384 + 8 헤더) |
| `attstorage` | **EXTERNAL** (pgvector 기본값 — float32는 압축률이 없어 압축을 포기하고 이동만 허용) |
| TOAST 임계 | 행 약 2,032 bytes |
| 실측 (본문 1,400 bytes, 비압축성 / 1,000행) | 메인 힙 1,600 kB + **TOAST 힙 1,600 kB**. TOAST에 들어간 값의 길이가 **1,540 bytes**로 `content`(1,408)가 아닌 **벡터**였다 |
| 실측 (본문이 압축 가능한 경우) | TOAST **0 bytes** — 본문이 압축되어 행이 임계 아래로 내려가면 벡터가 인라인으로 남는다 |

즉 **본문의 압축률에 따라 벡터의 저장 위치가 갈린다.** 브루트포스 전체 스캔에서는 밖으로 나간 행마다
TOAST 조회가 한 번 더 붙으므로, 6-3에서 측정한 전송 병목에 이 비용이 섞여 있었을 가능성이 있다.
대응 수단은 `ALTER TABLE ... ALTER COLUMN embedding SET STORAGE PLAIN`이며(1,544 bytes라 8KB 페이지에 무리 없이 들어간다),
**HNSW 도입 후에는 인덱스가 벡터 사본을 갖고 스캔이 인덱스에서 끝나므로 영향이 줄어든다.**
따라서 지금 바꾸지 않고 인덱스 단계에서 함께 판단한다 — 근거 없이 먼저 튜닝하지 않는다는 2-3의 원칙을 따른다.

### 검증

`VectorTypeMappingTest` — 엔티티 왕복, `ChunkVector` 투영 왕복, 차원 불일치 거부.
**투영을 따로 검증하는 이유**는 검색 경로가 엔티티가 아니라 생성자 투영으로 벡터만 뽑아 오기 때문이다(6절의 메모리 설계).
`HibernateBatchInsertVerificationTest`도 `vector(384)` 컬럼에 대해 그대로 통과한다(10,000건 / `nextval` 200회).

## 9. ADR-0003과의 관계

벡터 검색은 ADR-0003의 로드맵을 **대체하지 않는다.**

| ADR-0003 단계 | 이 결정과의 관계 |
|---|---|
| 3-1 ngram FULLTEXT | **살아 있다.** 현재 키워드 폴백이 양쪽 와일드카드 LIKE라 인덱스를 못 탄다. 이 쿼리가 FULLTEXT 전환 대상이며, 나아가 BM25 + 벡터의 **하이브리드 검색**으로 합류한다 |
| 3-3 Elasticsearch | **우선순위가 내려간다.** 다국어 모델이 언어별 analyzer 없이 교차언어를 해결하므로, ES를 도입할 근거가 약해졌다 |
| 3-4 정합성 설계 | **PostgreSQL 전면 이전을 택하면 소멸한다.** 원본과 벡터가 한 트랜잭션에 묶이기 때문이다. pgvector 사이드카를 택하면 그대로 남는다 |

## 10. 의도적으로 하지 않은 것

근거 없이 도입하지 않았다는 점을 남긴다. 면접에서 "왜 안 썼나"에 답할 수 있는 것이 쓴 것보다 낫다.

- **리랭커(cross-encoder)** — 실무 정석이지만 i3-6100에서 지연 부담이 크다. Phase 1 유사도 분포를 실측한 뒤 판단
- **하이브리드 검색(BM25 + 벡터)** — ADR-0003 3-1과 합류하는 별도 단계
- **질의 재작성, multi-hop, agentic RAG** — 현재 코퍼스 규모에서 근거 없음
- **Redis 캐시** — 챗봇이 0.02 TPS라 반복 질의가 없어 캐시 히트가 나지 않는다. 참조 데이터 캐시는 별개 사안이며, **단일 인스턴스에서는 Redis가 아니라 로컬 캐시가 맞다**(ADR-0002 2-4 판단 유지)
- **규정 문서(PDF/HWP) 적재** — 오프라인 파싱 단계가 추가된다. Phase 1.5로 분리
## 12. 교차언어 색인 (완료)

**선결 과제였던 테이블 불일치를 정리했다.** `TranslateLog` 엔티티가 `translate_logs`에 매핑되어 있었는데 `schema.sql`과 이 문서·ADR-0003은 모두 `work_log_translations`를 가리키고 있었다. 정리 시점에 `translate_logs`는 0행이라 데이터 이전은 없었다.

동시에 **`UNIQUE(log_id, language_code)`를 추가했다.** 제약이 없어 같은 작업일지를 같은 언어로 다시 번역하면 중복 행이 쌓였고, 그대로 색인하면 **같은 문서가 여러 번 검색 결과에 올라 상위를 오염**시킨다. 재번역은 새 행이 아니라 기존 행 갱신으로 처리한다.

**권한은 원본을 그대로 따른다.** 번역본이라고 아무나 볼 수 있으면 원문의 접근 제어가 무의미해지므로, 색인 시 원본 작성자를 `owner_user_id`로 복사한다.

### 실측 — 전제가 확인됐다

한국어 5건을 코퍼스로 두고 같은 의미의 베트남어·영어 질의를 넣었다(`CrossLingualRetrievalTest`).

| 질의 언어 | recall@1 | 정답 평균 | 오답 평균 | 격차 |
|---|---|---|---|---|
| 영어 | 5/5 | 0.840 | 0.779 | 0.061 |
| 베트남어 | 4/5 | 0.828 | 0.800 | 0.028 |

**언어별 analyzer 없이 교차언어가 성립한다**는 4절·9절의 전제가 확인됐다. 표본 5쌍이라 방향 확인이며, 실데이터 recall@k는 `(log_id, language_code)`를 정답 라벨로 별도 측정한다.

두 가지가 함께 드러났다.

- **절대 유사도로 임계값을 정하면 안 된다.** 오답 평균이 0.800이고 정답과의 격차가 0.028이다. 0.7 임계값은 아무것도 못 거르고 0.82는 정답 절반을 버린다. `rag.search.min-score=0.0`(비활성) 판단의 근거가 됐다
- **언어별 성능 격차가 크다.** 영어 0.061 대 베트남어 0.028. **실사용 비중이 높을 언어가 오히려 약하다**

- 유사도 분포 → `rag.search.min-score` 임계값 결정. **현재 0.0(비활성)이며, e5는 무관한 문장 사이에서도 코사인이 높게 나와 감으로 정하면 정상 근거를 버린다**
