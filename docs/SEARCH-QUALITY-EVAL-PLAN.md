# 검색 품질 평가 계획 — 맞는 작업일지를 찾는가

> 이슈 #170. 작성 2026-11-15. 이 문서는 **계획**이다. 결과는 측정 후 별도 절로 덧붙인다.

## 0. 왜 하는가

지금까지 잰 recall은 전부 **ANN이 브루트포스를 얼마나 따라가는가**였다.

| 이미 잰 것 | 값 | 출처 |
|---|---|---|
| 실데이터 20,313청크, 필터 없는 recall@5 | 0.840 → `ef_search`=100에서 0.930 | ADR-0006 8-4 |
| 선필터 위험 구간 recall@5 | 0.460 → `iterative_scan`으로 0.970 | ADR-0006 8-4 |
| 교차언어 recall@1 (한국어 5문장) | 영어 5/5, 베트남어 4/5 | ADR-0006 12절 |

앞의 둘은 정답이 "브루트포스가 고른 5개"다. 브루트포스가 엉뚱한 문서를 골랐어도 recall은 1.0이 된다.
**질문에 맞는 작업일지를 찾는지**는 한 번도 재지 않았다.

세 번째는 관련성을 재긴 했지만 방향 확인에 그친다.

- 후보가 5개라 무작위로 골라도 top-1이 20% 맞는다.
- 질의가 질문이 아니라 원문의 직역이다("용접할 때 보호구를 착용해야 한다" ↔ "Phải đeo thiết bị bảo hộ khi hàn").
- 다섯 문장의 주제(용접·크레인·밀폐공간·고소·도장)가 서로 겹치지 않아 헷갈릴 후보가 없다.
- 약어·호기 번호 같은 용어형 질의가 없다.

그래도 신호 하나는 남았다. **베트남어의 정답·오답 격차가 0.028로 영어(0.061)의 절반 이하**다.
실사용 비중이 높을 언어가 더 약하다는 뜻인데, 5건으로는 확인할 수 없다. 이 계획의 첫 질문이 이것이다.

## 1. 답할 질문

| # | 질문 | 무엇을 바꾸나 |
|---|---|---|
| Q1 | 지금 벡터 검색은 언어별·유형별로 얼마나 맞히는가 | 질의 언어(ko/en/vi) × 유형(2절) |
| Q2 | 베트남어가 정말 약한가. 약하다면 번역본 색인이 얼마나 회복시키는가 | `WORK_LOG_TRANSLATION` 청크 포함/제외 |
| Q3 | ANN(`ef_search`=100)이 관련성 기준으로 얼마를 잃는가 | 정확 최근접 vs HNSW |
| Q4 | 임베딩 서버가 죽었을 때 KEYWORD(LIKE) 폴백은 얼마나 맞히는가 | 검색 경로 |
| Q5 | 하이브리드가 필요한가 | Q1에서 용어형이 지는지 보고 결정 |

Q3·Q4는 이미 있는 결정의 **비용을 관련성 단위로 다시 매기는 것**이다. 새 기능이 아니다.
Q5는 Q1 결과가 나오기 전에는 착수하지 않는다(5절).

## 2. 코퍼스 — 무엇을 검색하는가

`CorpusSeedGeneratorTest`가 만든 **설비 정비 작업일지**다. 안전수칙 문서가 아니다.
질문도 이 내용에 맞춰야 한다 — "용접 안전수칙" 같은 질문은 코퍼스에 답이 없다.

본문은 슬롯 조합이다.

```
{설비} {호기}호기 {부품}에서 {증상}. 점검 결과 {원인} … {조치}. 조치 후 N분간 시운전 … {후속}
```

| 슬롯 | 개수 | 예 |
|---|---|---|
| 설비 | 12 | CO2 용접기, 겐트리 크레인, 플라즈마 절단기, 지게차 |
| 호기 | 1~9 | 3호기 |
| 부품 | 10 | 유압 실린더, 송급 롤러, 베어링부, 안전 스위치 |
| 증상 | 12 | 누유가 확인되었다, 간헐적으로 정지했다, 과전류로 차단되었다 |
| 원인 | 10 | 윤활 부족, 필터 막힘, 절연 저하 |
| 조치 | 12 | 그리스를 보충했다, 개스킷을 신품으로 교체했다 |

- 원문은 전부 한국어다. 30%에 같은 조합으로 만든 베트남어 번역본이 있다(`work_log_translations`).
- 다섯 건 중 하나는 긴 본문이라 부품·증상이 두 쌍 들어간다(2청크 이상).
- `R__seed_sample.sql`의 손으로 쓴 시드는 소수라 이번 평가에서 뺀다. 안전교육·체크리스트 청크도 뺀다(`source_type IN ('WORK_LOG','WORK_LOG_TRANSLATION')`).

### 이 코퍼스가 주는 이점 — 정답을 손으로 고르지 않아도 된다

본문이 슬롯 조합이므로 **"이 일지가 질문에 맞는가"를 슬롯 일치로 정의할 수 있다.**
예를 들어 "겐트리 크레인 유압 실린더 누유" 질문이면 정답은 (설비=겐트리 크레인, 부품=유압 실린더, 증상=누유)인 일지 전부다.
한국어 원문의 슬롯 문자열로 SQL을 걸면 정답 집합이 나온다. 사람이 문서를 하나씩 보며 표시하는 비용이 없다.

조합 수는 12×10×12 = 1,440개다. 2만 건이면 (설비, 부품, 증상) 하나당 정답이 평균 십여 건이다.
**정답이 여러 개인 평가**라는 뜻이고, 지표를 그에 맞게 골라야 한다(4절).

### 이 코퍼스의 한계 — 숫자를 어떻게 읽어야 하나

| 한계 | 어느 쪽으로 치우치나 |
|---|---|
| 어휘가 슬롯 목록으로 닫혀 있다. 질문에 슬롯 단어를 그대로 쓰면 글자가 일치한다 | 용어형 질문의 점수가 **부풀려진다**. 키워드 검색(Q4)에 특히 유리하다 |
| 문서끼리 실제보다 비슷하다(같은 문장 틀) | 최근접 거리 차가 작아져 **낮게** 나온다(생성기 주석 한계 1) |
| 베트남어 슬롯은 기계가 지었고 원어민 검수가 없다 | Q2의 크기는 믿기 어렵고 **방향만** 읽는다 |

그래서 이 평가의 결론은 "벡터 검색이 Hit@5 0.9다" 같은 절대값이 아니라
**같은 조건에서 방식 A가 B보다 어디서 얼마나 나은가**라는 상대 비교로만 쓴다.

## 3. 평가셋

### 3-1. 규모

한국어 기준 질문 **100개**를 쓰고 영어·베트남어로 옮겨 **총 300개**.

- 정답은 기준 질문에 한 번만 붙이고 세 언어가 공유한다. 라벨링은 100건분이고, 언어 비교는 같은 질문끼리 하게 된다.
- 칸 6개(3언어 × 2유형)가 50개씩이다. Hit@5가 0.8 근처면 95% 오차 범위는 칸당 ±0.11, 언어당(100개) ±0.08이다.
- 방식 비교는 같은 질문에서 짝지어 하므로(4절) 이보다 작은 차이도 잡힌다.

**파일럿 30개를 먼저 한다.** 형식·라벨 SQL·하네스가 돌아가는지 확인하고 100개로 늘린다.

### 3-2. 유형

| 유형 | 정의 | 예 | 노리는 것 |
|---|---|---|---|
| **T 용어형** | 슬롯 단어나 식별자를 그대로 쓴다 | "겐트리 크레인 3호기 유압 실린더 누유" / "CO2 용접기 송급 롤러" | 글자 일치가 유리한 질의. 특히 **호기 번호**는 임베딩이 3과 5를 구분하기 어렵다 |
| **S 의미형** | 슬롯 단어를 쓰지 않고 현장 말투로 묻는다 | "크레인 실린더에서 기름 새면 뭐 했어?" / "용접기가 자꾸 멈춰" | 벡터가 유리한 질의. 키워드는 거의 못 찾아야 정상이다 |

50/50으로 나눈다. 설비 12종이 고르게 들어가게 하고(설비당 8~9문항), 원인·조치를 묻는 질문도 섞는다("필터 막혀서 교체한 기록").

### 3-3. 작성 규칙

1. **원문을 보지 않고 쓴다.** 슬롯 목록만 보고 질문을 쓴다. 생성된 본문을 보고 쓰면 지난번 5건처럼 직역이 된다.
2. 의미형은 슬롯 문자열을 하나도 포함하지 않는지 스크립트로 검사한다.
3. 영어·베트남어는 한국어 질문을 옮긴다. **누가·무엇으로 옮겼는지** 파일에 적는다(기계번역이면 그렇다고). 베트남어 원어민 검수가 가능하면 일부라도 받는다.
4. 질문마다 정답 조건을 슬롯으로 적는다. 호기를 지정한 질문만 호기까지 조건에 넣는다.

### 3-4. 파일 형식

`docs/eval/search-quality/queries.tsv` (UTF-8, 탭 구분)

```
qid	type	lang	query	equipment	unit	part	symptom	cause	action	translator
q001	T	ko	겐트리 크레인 3호기 유압 실린더 누유	겐트리 크레인	3	유압 실린더	누유가 확인되었다			-
q001	T	vi	Rò rỉ dầu xi lanh thủy lực cần trục giàn số 3	…	…	…	…			MT(모델명)
```

- 정답 조건 칸이 빈 것은 조건이 아니다(와일드카드).
- 정답 집합(qid → log_id 목록)은 이 파일에서 SQL로 **매번 계산**한다. 코퍼스를 다시 만들면 log_id가 바뀌기 때문이다. 계산 결과는 측정 산출물로 함께 남긴다.

## 4. 지표

정답이 질문당 십여 건이므로 "정답을 몇 % 찾았나"(전통적 Recall@5)는 상한이 5/정답 수로 막힌다. 그래서 다음 셋을 쓴다.

| 지표 | 정의 | 왜 |
|---|---|---|
| **Hit@5** | 상위 5개에 정답이 하나라도 있으면 1 | 챗봇은 상위 5개를 근거로 답한다. 하나라도 맞으면 답이 된다 |
| **MRR@10** | 첫 정답 순위의 역수(10위 밖이면 0) | 정답이 몇 위에 처음 나오는가 |
| **Precision@5** | 상위 5개 중 정답 비율 | 근거에 엉뚱한 일지가 섞이는 정도. 환각과 직결된다 |

- 결과는 **원본 일지 단위로 중복 제거** 후 센다. 같은 일지의 청크 두 개, 또는 원문과 번역본이 함께 나오면 한 건이다(번역 청크는 `source_id` → `log_id`로 되짚는다).
- 칸별 값에 **부트스트랩 95% 구간**을 붙인다.
- 방식 비교는 같은 질문 쌍으로 **짝지은 부트스트랩**(또는 Hit@5는 McNemar)으로 차이의 구간을 낸다.
- NDCG는 쓰지 않는다. 정답에 등급이 없어 Precision과 사실상 같은 정보다.

## 5. 실험

모두 6-12와 같은 코퍼스(약 2만 청크) 위에서 돌린다. 권한 필터는 **관리자 경로(전체 열람)** 로 끈다 — 권한은 품질과 별개로 이미 검증했고(ADR-0006 6절·8-4), 필터를 걸면 질문마다 볼 수 있는 정답 집합이 달라져 비교가 흐려진다.

| 실험 | 내용 | 답하는 질문 | 조건 |
|---|---|---|---|
| **E0 파일럿** | 30문항 × 3언어, 벡터 기준선만 | 하네스·라벨 SQL 검증 | 먼저 |
| **E1 기준선** | 100 × 3언어, 운영 경로 그대로(HNSW, `ef_search`=100, `iterative_scan`) | Q1 | E0 뒤 |
| **E2 번역본 on/off** | E1에서 `WORK_LOG_TRANSLATION` 청크를 뺀 것과 비교 | Q2 | E1과 같은 실행 |
| **E3 정확 vs ANN** | 같은 질의를 정확 최근접으로 | Q3 | E1과 같은 실행 |
| **E4 키워드 폴백** | `RetrievalService`의 LIKE 폴백을 같은 질의로 | Q4 | E1과 같은 실행 |
| **E5 하이브리드** | 한국어 전문 검색 + 벡터, RRF로 합침 | Q5 | **E1에서 T(용어형)가 S보다 뚜렷이 질 때만** |

### E2에서 볼 것

번역본은 30%의 일지에만 있으므로, 베트남어 질의의 정답 중 번역본이 있는 것과 없는 것을 나눠 본다.
"번역본이 있는 일지만 더 잘 찾게 된다"면 회복이 아니라 **번역된 일지 쪽으로 쏠린 것**이다.
번역 비용은 저장·임베딩 2배로 이미 알려져 있어(AWS-MEASUREMENT-PLAN), 이 실험으로 그 비용의 대가가 처음 숫자로 나온다.

### E4에서 예상하는 것

의미형 질의는 거의 0이어야 하고, 베트남어 질의는 한국어 원문과 글자가 겹치지 않으니 **번역본 청크로만** 맞힐 수 있다.
장애 시 베트남어 사용자가 사실상 검색을 못 한다면, 그건 폴백 설계(ADR-0006 7절)의 알려지지 않았던 비용이다.

### E5에 들어가기 전에 정할 것

PostgreSQL 기본 전문 검색에는 한국어 형태소 분석기가 없다. 후보는 `pg_trgm`(기본 확장, 트라이그램), `pg_bigm`(바이그램, 한국어에 흔히 쓴다), mecab-ko 기반 사전이다.
설치·운영 부담과 인덱스 크기가 다르므로 **고르는 것 자체를 ADR로 남긴다.** 2글자 한국어 용어(누유·감속기 등)를 트라이그램이 못 잡는 문제가 판단 기준 중 하나가 된다.

### 하지 않는 것

| 하지 않는 것 | 이유 |
|---|---|
| IVFFlat 비교 | 보존 정책(ADR-0007)으로 데이터가 계속 지워지고 바뀌어 리스트 학습이 금방 낡는다. 비교 실험보다 이 이유 한 줄로 충분하다 |
| 리랭커 | E5 다음 문제다. 하이브리드 필요 여부도 아직 모른다 |
| 임베딩 모델 교체 | 차원이 384로 고정돼 있어(V1) 교체는 재색인을 뜻한다. 품질 기준선이 생긴 뒤에야 비교할 수 있다 |
| AWS 측정 | 로컬 Docker로 충분하다. 품질은 하드웨어와 무관하고, 지연은 E1의 부산물로만 적는다 |

## 6. 하네스

`AnnRecallMeasurementTest`·`CrossLingualRetrievalTest`와 같은 방식으로 **측정용 테스트**를 하나 둔다.

- DB·임베딩 서버가 없으면 skip한다(기존 측정 테스트와 같다).
- `queries.tsv`를 읽어 정답 집합을 SQL로 계산하고, 질의마다 각 방식의 상위 10개를 받아 지표를 낸다.
- 질의별 원 결과(qid, 방식, 순위, log_id, 정답 여부)를 TSV로 쓴다. 칸별 집계만 남기면 **어느 질문이 왜 틀렸는지** 다시 볼 수 없다.
- 운영 경로와 같은 SQL을 쓰기 위해 `RetrievalService`를 직접 부르되, E2·E3·E4의 변형은 측정 쪽에서 SQL로 만든다. 운영 코드에 측정용 스위치를 넣지 않는다.

| 3 | 100문항으로 확장 + E1~E4 결과 | `measure/…` |
| 4 | (조건부) 전문 검색 ADR + E5 | `feat/…` |

결과는 이 문서 끝에 "결과" 절로 덧붙이고, 조건(코퍼스 크기·생성 시드·임베딩 모델·`ef_search`·실행 일시)을 함께 적는다.
틀린 질문 몇 개는 실제 상위 5개를 그대로 옮겨 **왜 틀렸는지**를 적는다 — 숫자보다 이게 다음 결정의 근거가 된다.

## 8. 아직 모르는 것

- 베트남어 질문을 사람이 옮길 수 있는가. 못 하면 기계번역 질문 × 기계번역 코퍼스가 되어, 둘이 같은 번역 습관을 공유해 점수가 오를 수 있다 `[추측]`.
- 슬롯 일치 정답이 실제 관련성과 어긋나는 경우. 예를 들어 같은 부품·증상이지만 조치가 정반대인 일지도 정답으로 센다. 파일럿에서 틀린 결과를 직접 읽어 이런 경우가 얼마나 되는지 본다.
- 실데이터가 생기면 이 평가셋을 그대로 쓸 수 없다. 슬롯 정답이 없으므로 그때는 사람이 라벨을 붙여야 한다(TREC식 풀링: 여러 방식의 상위 결과를 모아 판정).
