# 재순위를 켤 수 있나 — CPU 지연(밤 23)과 근거 없음 문턱 (2026-11-28)

Refs #225(이 문제), #213(재순위), #220(품질 측정), #203(엉뚱한 근거로 답을 지음), #222(정답 라벨)

## 결론

**CPU에서는 켤 수 없다.** 재순위 서버가 메모리 3G에서 뜨지 않고, 뜨게 맞춰도 CPU에서 질문당 약 15초가 걸려 클라이언트 타임아웃(5초)을 매번 넘는다. 넘으면 `RerankClient`는 재순위 없이 답하므로 **켜도 품질 이득은 0이고 응답만 5초 늦어진다.**

- 메모리: 운영 상한 3G에서 기본 설정은 워밍업 중 OOM. 배치 토큰을 1024까지 줄여야 뜬다. 기본 설정은 6G로도 OOM이다.
- 지연: 후보 20개 p50 15초, 10개 8.6초, **5개도 5.3초** — 어느 설정도 타임아웃(5초) 안에 들지 않는다.

품질 근거(PR #220)는 충분하다. 막는 것은 하드웨어다. **품질 이득까지 가져가려면 재순위를 GPU에서 돌려야 하고**, 이것은 자체 호스팅 LLM의 GPU 결정(ADR-0013)과 같은 결정이다. 선택지는 4절.

## 1. 메모리 — 운영 상한(3G)에서 뜨지 않는다

`compose.rerank.yaml`과 같은 상한(`cpus 2.0`, `memory 3G`), TEI `cpu-latest`, `BAAI/bge-reranker-v2-m3`.

| 배치 토큰 상한(`--max-batch-tokens`) | 결과 |
|---|---|
| 기본(16384) | 워밍업 중 cgroup OOM — anon-rss 3.13GB (`dmesg`) |
| 4096 | OOM |
| 2048 | OOM |
| **1024** | 뜸. 워밍업 뒤 2.6GB, 측정 중 2.6~2.7GB |
| 기본, 상한 6G(비교) | **OOM** — anon-rss 6.27GB |
| 4096, 상한 6G(비교) | 뜸. 측정 중 최대 4.57GB |

- 같은 날 로컬에서 같은 설정으로 띄운 컨테이너도 워밍업 중 OOM으로 죽었다(`OOMKilled=true`).
- PR #220은 GPU라 이 문제가 보이지 않았다. **`compose.rerank.yaml`의 3G는 지금 이미지로는 성립하지 않는다.**

## 2. 지연 — 질문 하나, 후보 N개를 한 요청으로

입력: E1 평가셋 질문 + 후보 청크(PR #220 `vector`가 실제 고른 근거 5개 + 같은 코퍼스 무작위, 500자로 자름 — 운영 청크 길이). `make_inputs.py`·`bench.py`.

| 설정 | 후보 | 질문 수 | p50 | p95 | 최대 |
|---|---|---|---|---|---|
| 3G · 배치 1024 | 20 (운영 기본) | 47 | **15.0초** | **20.4초** | 21.9초 |
| 3G · 배치 1024 | 10 | 60 | 8.6초 | 11.3초 | 11.5초 |
| 3G · 배치 1024 | 5 | 60 | **5.3초** | 5.7초 | 5.8초 |
| 6G · 배치 4096 | 20 | 30 | 16.3초 | 21.7초 | 22.7초 |
| 6G · 배치 4096 | 5 | 30 | 5.3초 | 5.6초 | 5.7초 |

- **지연은 후보 수에 거의 비례한다** — 후보 하나에 약 0.75초. 후보 5개도 p50 5.3초로 타임아웃(5초)을 넘는다.
- **배치를 키워도 빨라지지 않는다**(1024 → 4096: 후보 20개 15.0 → 16.3초). 3G에 맞추려고 배치를 줄인 탓이 아니다 — CPU 계산 자체가 느리다.
- 비교: PR #220의 GPU(T4)는 질문당 +0.2~0.35초였다. 약 50배.
- 후보 20개는 전체(360질문)를 돌리면 watchdog(2시간) 안에 끝나지 않아 47개에서 멈추고, 나머지는 60질문(평가셋 6개마다 1개, `remote3.sh`)과 30질문(그 절반, `small_bench.py` — 6G·배치 4096)으로 줄였다.

### 후보를 줄이면 품질은

- **후보 5개는 품질 이득이 0이다.** 재순위는 후보 안의 순서만 바꾼다. 상위 5개 안에서만 바꾸면 Hit@5·P@5는 그대로고, 1위만 바뀐다.
- 후보 10개의 품질은 재지 않았다. 벡터 6~10위에 정답이 있던 질문만 살릴 수 있다 — 파일럿에서 그런 질문은 실패 질문의 일부였다(실패 분류, #219 근거) `[미측정]`.

## 3. 켠다면 — 근거 없음 문턱(`rag.search.rerank.min-score`)

PR #220 `per_query.tsv`의 `top_rerank`(근거 1위의 재순위 점수, 0~1)로 골랐다. 1위 점수가 문턱 아래면 전 후보가 아래라 운영은 근거 없음(NONE)으로 답한다. 정답 라벨은 #222(사건 단위).

질문을 셋으로 나눴다.

| 그룹 | 뜻 | 바라는 것 |
|---|---|---|
| G 좋은 근거 | 답 있음, 근거 5개에 정답 있음 | 살린다 |
| M 틀린 근거 | 답 있음, 근거 5개에 정답 없음 | 걸러도 된다 — 이 근거로 답하면 충실도 0.66~0.72(#203) |
| N 답 없음 | 코퍼스에 답 없음 | 거른다 |

교차 검증(질문을 반씩 나눠 한쪽에서 문턱을 고르고 다른 쪽에서 잼, 200회 평균), `rerank` 방식:

| 고르는 기준 | 문턱 | G 잃음 | M 거름 | N 거름 |
|---|---|---|---|---|
| G를 5% 이하로, 세 언어 공통 | 약 0.01 | 6% | 31% | 60% |
| G를 10% 이하로, 세 언어 공통 | 약 0.05 | 11% | 46% | 74% |
| G를 5% 이하로, 베트남어만 | 약 0.13 | 6% | 19% | 85% |

- **켠다면 0.01부터.** 0(꺼짐)보다 확실히 낫다 — 답 없는 질문의 60%, 틀린 근거의 31%를 "찾지 못했다"로 바꾸고 좋은 근거는 6% 잃는다.
- **ADR-0013 3절의 두 목표(답 없음 처리 ≥ 90%, 답 있는 질문 거부 ≤ 10%)는 한 문턱으로 함께 못 맞춘다.** N 90%는 문턱 0.2이고 그때 G를 18% 잃는다.
- **ADR-0013의 "답 있는 질문 거부율"은 정의를 바꿔야 한다.** 지금 정의는 M을 거른 것도 나쁜 거부로 센다. 거르는 게 맞는 경우다 — "좋은 근거 거부율"(G)로 바꾼다.
- 베트남어는 점수가 언어 안에서 잘 갈린다(언어별 문턱이면 N 85~92%). 한국어·영어는 좋은 근거인데도 1위 점수가 0에 가까운 질문이 있어 잘 안 갈린다.
- 이 분석의 숫자는 GPU에서 낸 점수다. CPU에서 배치 상한을 바꿔도 점수는 같아야 한다(같은 모델·같은 입력) `[추측]`.

## 4. 선택지

| | 지연 | 품질 | 비용·작업 |
|---|---|---|---|
| A. 후보 5개로 줄임 | p50 5.3초 — **타임아웃(5초)을 넘는다** | **이득 0** (순서만 바뀜) — min-score 판정만 남는다 | 설정 하나 |
| B. 후보 10개 | p50 8.6초 | 일부 `[미측정]` | 설정 하나 + 품질 재측정 |
| C. 더 작은 다국어 재순위 모델 | 재야 함 | 재야 함 | 모델 비교 측정 |
| D. 재순위만 GPU | +0.2~0.35초(PR #220) | PR #220 그대로 | GPU 호스트. ADR-0013 7절 — 자체 호스팅 LLM도 GPU가 먼저라는 결론과 같은 결정 |
| E. CPU 최적화 백엔드(ONNX 등) | 재야 함 `[추측: 2~3배]` | 같은 모델이면 같음 | 이미지·변환 |

**CPU에서는 A도 안 된다.** 후보 5개도 타임아웃을 넘어서, 지금 설정이면 매번 재순위 없이 답한다. 타임아웃을 7초쯤으로 올리면 돌기는 하지만, 품질 이득 없이(Hit@5 그대로) min-score 판정 하나를 얻으려고 **모든 질문에 5초 넘게** 붙는다. 자체 호스팅 LLM 생성이 이미 p95 10~39초(#202)인데 거기에 더해지는 값이라 맞바꿀 만하지 않다.

근거 없음 판정(#203)만 따로 원하면 재순위 말고 더 싼 신호를 먼저 본다 — 코사인 유사도의 언어별 문턱(E1에서 언어마다 AUROC 0.73~0.88, `docs/SEARCH-QUALITY-EVAL-PLAN.md` 9절)은 추가 지연이 0이다.

**품질 이득까지 가져가려면 D**이고, 자체 호스팅 LLM의 GPU 결정(ADR-0013 3단계)과 함께 정한다.
