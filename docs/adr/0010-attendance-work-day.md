# ADR-0010: 근무일은 벽시계 날짜가 아니라 교대 기준일이다

- 상태: **결정.** 2026-09-19. 코드는 PR #119(`fix/attendance-work-day`, #98). 결정은 규칙 한 줄이고, 나머지는 그 규칙이 닿는 자리다
- 대상 코드: `attendance/model/WorkDay`(규칙), `member/model/WorkShift`(`dayBoundary`), `Attendance.clockIn`·`clockOut`, `AttendanceService.clockin`·`clockout`, `AttendanceRepository`(열린 기록 조회), `V10__attendance_work_shift_and_seconds.sql`
- 관련 문서: `docs/adr/0001`(출근 락 — 키의 날짜는 그대로다, 4절), `docs/adr/0005` 2-1(근무 정책 엔진 — 이 ADR은 그것을 대신하지 않는다), `docs/WORK-BACKLOG.md` P2-17-4(교대별 집계), 이슈 #98·#105
- 작성 목적: "근무일"은 급여·지각·결근·집계가 전부 매달리는 축인데, 정의가 없었다 — `LocalDate.now()`가 정의였다. 3교대 중 하나가 그 정의로는 퇴근을 못 찍었다. 규칙을 한 곳에 적어 두고, 하지 않은 것과 되돌릴 조건을 남긴다.

---

## 1. 무엇이 깨져 있었나

`work_date = LocalDate.now()`. 주간(06:00)·오후(14:00) 교대는 하루 안에 끝나므로 이것으로 충분했고, 그래서 아무도 못 봤다.
야간(22:00~06:00)은 자정을 걸친다.

| 야간조의 하루 | 예전 동작 | 왜 |
|---|---|---|
| D일 22:00 출근 | 행 생성, `work_date = D` | — |
| D+1일 06:00 퇴근 | **404 `ATTENDANCE_NOT_CHECKED_IN`** | `findByMemberAndWorkDate(D+1)` — D의 행을 못 찾는다 |
| D+1일 00:30 출근 (2시간 30분 지각) | **NORMAL** | `00:30.isAfter(22:00) = false`. 시각만 비교했다 |
| 자정 배치 | 그럭저럭 | "어제"를 세는데 야간조의 어제는 새벽까지 이어진다. 결과는 맞았지만 우연이다 |

즉 야간조는 **퇴근 기록이 하나도 없고, 지각도 하나도 없는** 상태로 운영됐을 것이다. 시드의 worker03(야간)에 퇴근 시각이 있는 것은 손으로 넣었기 때문이다.

## 2. 결정 — 규칙 한 줄

```
work_date = (now.time < shift.dayBoundary) ? now.date − 1 : now.date
```

| 교대 | 시작 | `dayBoundary` | 뜻 |
|---|---|---|---|
| MORNING | 06:00 | 00:00 | 근무일 = 날짜. **바뀌는 것 없음** |
| AFTERNOON | 14:00 | 00:00 | 같음 |
| NIGHT | 22:00 | **12:00** | 정오 이전 이벤트는 전날 근무일 |

정오인 이유: 22:00을 가운데 두고 앞뒤로 10~14시간이 한 근무일에 들어간다. 조기 출근(21:00)·지각(00:30)·정시 퇴근(06:00)·잔업(11:00)이 전부 같은 행에 붙고, 다음 근무일은 12:00부터라 어제 잔업과 오늘 조기 출근이 겹칠 틈이 없다.
"교대 시작 − N시간"으로 교대마다 계산할 수도 있었지만, 상수 하나가 읽기 쉽고 주간·오후를 건드리지 않는다. 경계 시각 자체(12:00:00)는 그날이다 — `isBefore`.

지각은 같은 규칙에서 나온다: 출근 시각이 속한 근무일의 `workDate.atTime(startTime)`보다 늦으면 지각. 야간 00:30 출근은 근무일이 전날이므로 전날 22:00과 비교된다. 유예는 0분(5절).

이 규칙은 `WorkDay` 한 클래스에 있고 순수 함수다. 출근·퇴근·결근 배치·휴가 반영이 날짜를 스스로 정하지 않는다 — `Attendance.clockIn(member, now, ...)`이 받는 것은 시각이지 날짜가 아니다. 호출자가 날짜를 넘기게 두면 `LocalDate.now()`를 넣는 호출자가 다시 생긴다.

## 3. 퇴근은 날짜로 찾지 않는다

근무일을 다시 계산해 `findByMemberAndWorkDate(WorkDay.of(...))`로 찾아도 된다. 그러지 않고 **"출근은 있고 퇴근은 없는 가장 최근 행"**을 직접 묻는다(`findFirstByMemberAndClockInTimeIsNotNullAndClockOutTimeIsNull...`, 부분 인덱스 `idx_attendance_open`).
닫을 대상은 결국 열린 행 하나이고, 그렇게 물으면 퇴근 경로가 근무일 규칙에 묶이지 않는다 — 규칙이 바뀌어도(정책 테이블, ADR-0005) 퇴근은 그대로다.

**열린 행이 너무 오래됐으면 닫지 않는다.** 출근 뒤 16시간(`WorkDay.MAX_OPEN_SPAN`)이 지난 행에 퇴근이 오면 409 `ATTENDANCE_CLOCK_IN_STALE`. 어제 퇴근을 잊은 사람이 오늘 퇴근을 누르면 30시간 근무 행이 생기는데, 그것은 데이터가 아니라 오염이고 집계(P2-17-4)에 그대로 들어간다. 16시간은 8시간 교대 + 잔업을 넉넉히 덮는 값이다. 잊힌 행의 정리는 관리자 수정 또는 미퇴근 배치의 일이다(5절).

열린 행이 없을 때는 둘을 가른다 — 오늘 근무일의 행이 있고 퇴근 시각이 있으면 `ALREADY_CHECKED_OUT`, 아니면 `NOT_CHECKED_IN`. 앱 메시지가 다르다.

## 4. 행에 남기는 것 — V10

| 컬럼 | 왜 |
|---|---|
| `work_shift varchar(20) NOT NULL` | **판정 교대의 스냅샷.** `users.work_shift`는 바뀐다. 석 달 전 행이 어느 교대 기준으로 지각인지는 그때의 교대가 답이다. 교대별 집계(P2-17-4)도 사용자의 현재 교대가 아니라 이 컬럼을 봐야 한다 — 지금 `summarizeByAreaAndDate`는 `m.workShift`를 보는데, 이 컬럼으로 옮기는 것은 #78 후속 |
| `work_seconds integer` | `total_work_time varchar`를 대체. 서비스는 `"HH:mm:ss"`, 시드는 `"9h12m"`을 넣고 있었다 — 같은 컬럼에 표기가 둘, 어느 쪽도 SUM이 안 된다. 백필은 문자열 파싱이 아니라 `clock_out − clock_in`이다. 응답의 `totalWorkTime` 문자열은 DTO가 초에서 만들어 계약을 지킨다 |
| 야간조 기존 행 재배정 | 정오 이전 출근 행을 `work_date − 1`로. 유니크와 겹치면 RAISE로 멈춘다(V5·V3의 장치). 한 문장 UPDATE가 아니라 근무일 오름차순으로 한 행씩 — 유니크는 행마다 즉시 검사되므로 D+2 → D+1이 D+1 → D보다 먼저 가면 거기서 실패한다 |
| `idx_attendance_open` | 부분 인덱스. 사용자당 열린 행은 0~1개 |

응답에는 `workDate`·`workShift`·`workSeconds`가 **추가**된다(기존 필드는 그대로). 앱이 "어느 날의 기록인가"를 `clockInTime`의 날짜로 짐작하면 야간조에서 하루 어긋난다 — `workDate`를 써야 한다(#81에 얹는다).

출근 락 키 `attendance:lock:{userId}:{날짜}`의 날짜는 **벽시계 날짜 그대로**다(ADR-0001·0009). 근무일은 사용자의 교대를 알아야 계산되는데 락은 DB를 보기 전에 잡는다. 키는 더블클릭을 3초 안에서 가르는 용도라 무엇으로 나누든 상관없고, 자정을 걸치는 두 요청이 다른 키를 받는 경우는 DB 유니크(2차 방어선)가 받는다.

## 5. 하지 않은 것

| 항목 | 왜 지금 안 하나 | 자리 |
|---|---|---|
| 조퇴(`LEFT_EARLY`) | `status` 하나에 지각과 조퇴를 같이 담을 수 없다(지각+조퇴인 날). `late`·`left_early`를 따로 두는 스키마 결정이 먼저다. enum 값은 시드가 쓰고 있어 남긴다 | `WorkShift.getEndTime()`(시작+8h)만 만들어 뒀다 |
| 지각 유예 | 규정이 없다. 06:00:01도 지각이다 | `WorkDay.LATE_GRACE = ZERO` — 숫자 하나 |
| 교대를 정책 테이블로 | ADR-0005 2-1, 백로그 P3. `dayBoundary`도 enum에 있다 | 옮길 때 `WorkDay`는 그대로, `WorkShift`만 바뀐다 |
| 미퇴근 배치 | 16시간 지난 열린 행을 무엇으로 닫을지(자동 퇴근? 결근? 관리자 확인 대기?)는 규정 문제 | P3. 지금은 409로 막고 로그만 |
| 결근 배치의 "어제" | 00:10에 D−1을 처리한다. 야간 D−1은 06:00 D에 끝났으므로 안전. 바꿀 것 없음 | 대상에서 ADMIN을 빼는 것은 #105, 별도 PR |
| 교대별 집계 컬럼 | `summarizeByAreaAndDate`가 `m.workShift`(현재)를 본다 | `a.workShift`(스냅샷)로 — #78 후속 |

## 6. 검증

- `WorkDayTest` 20건 — 야간조의 하루를 9개 시각으로(21:30 → 12:00 경계 → 다음 21:50), 주간·오후는 "안 바뀐다" 5개, 지각 경계, 16시간 경계, `endTime`.
- `AttendanceServiceTest` — 야간 00:30 출근 = 전날 근무일 + LATE, 다음날 06:10 퇴근이 전날 행을 닫고 날짜 조회를 안 함, 33시간 전 출근에 퇴근 = 409. 기존 13건은 그대로 통과(주간 동작 불변).
- V10은 Testcontainers에서 실제로 돌았다(`AttendanceDailySummaryTest`가 `ddl-auto=validate`로 뜬다). 야간 재배정은 빈 테이블이라 0건 — 데이터 있는 DB에서의 첫 실행은 RAISE 조건을 본다.

## 7. 되돌릴 조건

- 야간조가 정오 이후에 출근하거나(예: 12:30 잔업 시작) 정오 이전에 다음 근무를 시작하는 패턴이 실제로 있으면 `dayBoundary = 12:00`이 틀린 것이다. 그때는 교대별 경계를 정책 테이블로(ADR-0005)이지 규칙 자체를 버리는 것이 아니다.
- 잔업이 16시간을 넘는 것이 정상 운영이면 `MAX_OPEN_SPAN`을 올린다. 409가 로그에 쌓이는지 본다.
