### P0-4 — `Work_logs` → `WorkLog` (완료)

클래스를 **테이블 이름대로 지은** 것이 문제의 본질이다. 자바 클래스는 `PascalCase` 단수,
테이블은 `snake_case` 복수라는 서로 다른 관례가 있는데 후자가 코드로 새어 나와 있었다.

| 변경 | |
|---|---|
| `Work_logs` → `WorkLog` | 엔티티 |
| `Work_logsRepository` → `WorkLogRepository` | 리포지토리 |
| `Work_logsDto` → `WorkLogDto` | DTO (백로그에 없었으나 같은 문제였다) |
| 지역변수 `work_logs` → `workLog` / `workLogs` | 변수까지 스네이크였다 |

**DB는 건드리지 않았다.** `@Table(name="Work_logs")`를 `@Table(name = "work_logs")`로 바꿨는데
매핑은 동일하다 — PostgreSQL이 따옴표 없는 식별자를 소문자로 접기 때문에 원래도 `work_logs`였다.
표기만 실제 테이블명과 일치시켰다.

**함께 바꿔야 했던 것 — JPQL은 테이블이 아니라 엔티티 이름을 쓴다.**
`@Query("SELECT w FROM Work_logs w ...")`가 두 곳 있었고, 클래스명만 바꾸면
**컴파일은 통과하고 실행 시점에 깨지는** 종류다. 함께 `FROM WorkLog w`로 바꿨다.

> **주석에 남은 `work_logs`는 그대로 뒀다.** 그것들은 클래스가 아니라 **테이블**을 가리킨다
> (`TranslateLog`, `SourceType`의 설명). 일괄 치환했으면 오히려 틀린 문서가 됐을 것이다.

검증: `SchemaValidationTest`가 통과했다는 것이 **매핑이 그대로임을 증명**한다 —
어긋났다면 `validate`가 테이블을 못 찾아 실패했을 것이다.

**P1-4 / P1-5에서 잡은 함정 세 가지** (면접에서 설명 가능한 지점)

1. **자기호출로 인한 `@Transactional` 무효화** — 페이지 단위 커밋이 재시작 가능성의 핵심인데,
   같은 클래스 안에서 호출하면 프록시를 거치지 않아 트랜잭션이 걸리지 않는다. **에러도 나지 않는다.**
   `ChunkIndexWriter`를 별도 빈으로 분리해 트랜잭션 경계를 클래스 경계와 일치시켰다.
2. **배치에는 OSIV가 없다** — `workLog.getMember()`가 지연 로딩이라 트랜잭션 밖에서 접근하면
   `LazyInitializationException`이 난다. 트랜잭션 안이었어도 작업일지마다 쿼리가 더 나가 N+1이 된다.
   `findAllForIndexing()`에 페치 조인을 추가해 둘 다 해결.
3. **e5 프리픽스 누락은 조용히 품질만 떨어뜨린다** — 에러가 나지 않아 추적이 어렵다.
   호출자가 프리픽스를 직접 다루지 못하게 API를 나눴다.

> **미포함:** `work_log_translations`(교차언어 검색용)는 아직 색인하지 않는다.
> `TranslateLog` 엔티티가 `translate_logs` 테이블에 매핑되어 있어 `schema.sql`의
> `work_log_translations`와 어긋나 있다. **이 불일치 정리가 교차언어 검색의 선결 과제다** (신규 P0-6).
| P1-6 | `RetrievalService` — 코사인 유사도 top-k (브루트포스 = 정확 최근접) | **완료** — 원본 문서당 최대 2청크 제한 포함 |
| P1-7 | 권한 필터 — 검색 대상 제한 | **완료** — **선필터**로 구현(아래) |

**P1-7은 over-fetch 후 필터링이 아니라 선필터로 구현했다.** 후필터는 요청한 k보다 적게 반환되어
"내가 못 보는 문서가 존재한다"는 사실이 유출되고, 검색어를 바꿔가며 반복하면 문서의 존재 윤곽을
그릴 수 있다. 선필터는 SQL 단계에서 후보에 아예 넣지 않으므로 존재 여부도 새지 않고, over-fetch도 불필요하다.

**메모리 관련 설계 하나** — 브루트포스는 후보 전체를 메모리에 올린다. 엔티티를 통째로 읽으면
청크당 벡터 1.5KB + 본문 약 1.5KB로 10만 청크에서 300MB에 달해 `Xmx400M`에서 위험하다.
`ChunkVector` 투영으로 **벡터만 읽어 점수를 매기고, 본문은 최종 top-k에 대해서만 조회**한다.

### P1-11 — Phase 2 전환 판단 (실측 이후)

**Phase 1 완주 + 브루트포스 한계 실측 전에는 착수하지 않는다.** 근거 없이 벡터DB를 도입하면
ADR-0002가 스스로 경계한 "실측 없이 튜닝했다" 패턴이 된다.

실측 후 선택지는 둘이며, **현재로서는 PostgreSQL 전면 이전이 유력하다.**

| 선택지 | 장점 | 단점 |
|---|---|---|
| pgvector **사이드카** (MySQL 원본 + PG 벡터) | 기존 스택 유지 | **두 저장소 정합성 문제를 새로 만든다** — 동기화 지연, 실패 시 재색인, 장애 폴백 (ADR-0003 3-4) |
| PostgreSQL **전면 이전** | 원본과 벡터가 한 트랜잭션 → **정합성 문제 자체가 소멸**. HNSW 인덱스 | 스택 변경. Real MySQL 매핑(ADR-0002 3절) 무의미해짐, ngram FULLTEXT 계획은 pg_trgm/tsvector로 대체 |

> **이전 비용은 당초 예상보다 훨씬 작다.** `spring.sql.init.mode=never`라 `schema.sql`은 실행되지 않고
> Hibernate가 엔티티에서 방언에 맞는 DDL을 생성한다. JPQL은 방언 독립이다.
> 실제로 손볼 지점은 **`DocumentChunk.embedding`의 `columnDefinition = "VARBINARY(4096)"` → `BYTEA`** 한 줄이다.
> (MySQL에서 VARBINARY를 고른 것은 브루트포스 전체 스캔에서 오프페이지 저장을 피하기 위한 의도적 선택이므로 Phase 1에서는 그대로 둔다.)

#### 이전 시 함께 검증할 항목 — **2a 완료, 실측으로 채움**

| 항목 | MySQL 실측 | PostgreSQL 실측 | 예상과의 차이 |
|---|---|---|---|
| 배치 INSERT | ❌ `IDENTITY`가 막음 (문장 10,000개) | ✅ `SEQUENCE`로 해결. `nextval` **200회** (`increment_by=50`) | 예상대로 |
| 권한 `OR` 인덱스 | ❌ 미사용, 10만 행 전부 읽음 (770ms) | ✅ **BitmapOr 사용** (41.5ms). 선필터 경로 1,485ms → **424ms** | 예상대로 |
| 락 타임아웃 조정 | 서버/세션 단위까지 | ✅ `lock_timeout` 파라미터. **`SET LOCAL`로 트랜잭션 단위 가능** | 예상대로 |
| 락 타임아웃 힌트 | ❌ 무시 (50,850ms) | 미검증 — 서버 파라미터로 해결해 확인 불필요 | — |
| 벡터 컬럼 | `VARBINARY(4096)` | `BYTEA` (2b에서 pgvector `vector`로) | 애노테이션 한 줄 |

**예상 밖이었던 것** — `SafetyCourse.createdAt`의 `columnDefinition = "DATETIME"`이 MySQL 전용 타입이라
`type "datetime" does not exist`로 **테이블 생성이 실패했다.** 그런데 `ddl-auto=update`가 DDL 오류를
로그만 남기고 기동을 막지 않아 **앱이 정상 기동한 것처럼 보였다.** 전수 조사로 잡았다.

> **`OR` 분리는 되돌리지 않는다.** BitmapOr가 확인됐지만 단일 쿼리 41.5ms 대 분리 18.5ms로
> 분리가 여전히 조금 빠르다(힙 접근량은 동일, 차이는 BitmapOr 오버헤드).
> 코드 단순화와 성능을 맞바꾸는 셈이라 현 구조를 유지한다.

#### 2b — pgvector 도입 (남은 작업)

**이관의 본래 목적이다.** 브루트포스는 여전히 벡터를 애플리케이션으로 전부 가져와 계산한다
(10만 청크 관리자 경로 4,059ms). 유사도 계산을 DB 안으로 옮겨야 6-3의 전송 병목이 사라진다.

| 작업 | 난이도 | 상태 |
|---|---|---|
| `vector` 타입 매핑 | ~~높음~~ **낮았음** | **완료** (아래) |
| HNSW 인덱스 생성 | 보통 | **완료** — `docs/migration/2b-hnsw-index.sql` |
| `RetrievalService`의 코사인 계산을 DB 쿼리로 이동 | 높음 | **완료** — ADR-0006 8-3 |
| **ANN recall 측정** — Phase 1 브루트포스 결과를 정답 기준선으로 비교 | 보통 | 실데이터 색인 후 |
| 권한 선필터와 ANN 결합 (알려진 난제 — ADR-0006 8절) | 높음 | **실측으로 재현됨** (아래) |

**인덱스보다 계산 위치를 옮기는 것이 먼저다 — 실측이 순서를 바꿨다.**
10만 청크 top-5 기준(ADR-0006 8-2):

| 경로 | 지연 |
|---|---|
| Phase 1 — 애플리케이션에서 계산 | 4,059 ms |
| **인덱스 없이** DB 안에서 정확 최근접 | **약 57 ms** |
| HNSW (워밍) | 약 1.7 ms |

인덱스를 하나도 안 만든 상태에서 이미 **약 70배**다. 전송이 병목의 81%라던 진단이 확인된 셈이고,
HNSW의 추가 이득은 그 위에 얹히는 두 번째 층이다. 그래서 다음 작업은 인덱스 튜닝이 아니라
`RetrievalService`를 `ORDER BY embedding <=> :q`로 옮기는 것이다.

**권한 선필터를 걸면 HNSW가 무너진다.** 일반 사용자 경로(후보의 약 10%)에서 top-5 요청 시:

| 방식 | 반환 | 지연 |
|---|---|---|
| HNSW 기본 | **1 / 5** | 1.6~2.3 ms |
| HNSW + `iterative_scan` | 5 / 5 | 3.9~5.4 ms |
| 정확 최근접 + 선필터 | 5 / 5 | 15.2~22.6 ms |

기밀성이 아니라 **완전성**이 깨진다(필터는 여전히 SQL 안에서 걸린다). 그리고 필터가 붙으면
HNSW의 우위가 32배에서 약 4배로 줄어든다 — **일반 사용자 경로에서는 인덱스를 안 쓰는 게
나을 수도 있다.** 실데이터 recall 측정 전에는 결론 내지 않는다.

| 빌드에서 걸린 것 | 내용 |
|---|---|
| `maintenance_work_mem` 64MB | 10만 건 중 **28,363건**에서 넘쳐 디스크 빌드로 전환(NOTICE로 알려준다). 4분 56초 |
| 256MB + 병렬 끔 | **3분 09초** |
| 256MB + 병렬 켬 | **실패** — Docker `/dev/shm` 기본 64MB에 DSM이 안 들어감. `shm_size`를 키우는 대안은 512MB 컨테이너 OOM 위험 때문에 택하지 않음 |
| 인덱스 크기 | **195MB** — 테이블(195MB)과 맞먹는다. `shared_buffers` 128MB에 둘 다 상주 불가 |

> **잊으면 조용히 잘못되는 것이 둘로 늘었다.** `CREATE EXTENSION`과 HNSW 인덱스 모두
> Hibernate 관리 밖이고 `db/init/`으로도 해결되지 않는다(컨테이너 최초 기동 시점에는
> 테이블이 아직 없다). 새 환경 구축 절차에 `docs/migration/` 실행이 반드시 들어가야 한다.

**타입 매핑 — "커스텀 `UserType`이 필요하다"는 전제가 틀렸다.**
Hibernate 6.4부터 `hibernate-vector` 모듈이 `SqlTypes.VECTOR`를 제공하고 PostgreSQL 방언에서
pgvector의 `vector`로 내보낸다. 현재 Hibernate 7.2.0.Final이라 애노테이션 두 줄로 끝났다.
버전도 Spring Boot BOM이 관리해 명시할 필요가 없다.

```java
@JdbcTypeCode(SqlTypes.VECTOR)
@Array(length = EMBEDDING_DIM)   // 이 값이 곧 컬럼의 vector(384)
private float[] embedding;
```

| 발견 | 내용 |
|---|---|
| **차원이 스키마가 됐다** | HNSW는 고정 차원 컬럼에만 걸린다. 그 대가로 차원이 다른 모델의 청크가 공존할 수 없다 — 가변 길이 `BYTEA` 시절에는 가능했던 일이다. 모델을 바꾸면 컬럼 마이그레이션이 따라온다 |
| **`ALTER`에 `USING`이 필요하다** | `bytea → vector` 자동 변환 규칙이 없어 PostgreSQL이 거부한다. **행이 0건이어도** DDL 시점에 검사한다. `USING NULL::vector(384)`로 명시했고, 행이 남아 있으면 `NOT NULL` 위반으로 실패해 실수로 임베딩을 날리지 못한다 |
| **확장 등록은 이미지와 별개** | `pgvector/pgvector:pg17`에 확장 파일은 있으나 `CREATE EXTENSION`은 따로 실행해야 한다. `db/init/`을 마운트했지만 **데이터 디렉터리가 비어 있을 때만 돌므로** 기존 볼륨에는 `docs/migration/2b-pgvector.sql`을 직접 실행한다 |
| **벡터가 TOAST로 나간다** | `vector(384)` = 1544 bytes, `attstorage=EXTERNAL`. 본문과 합쳐 행이 약 2KB를 넘으면 벡터가 행 밖으로 빠진다(실측: TOAST에 들어간 값이 1540 bytes로 `content`가 아닌 벡터였다). **ADR-0006이 `VARBINARY`를 고르며 피하려던 InnoDB 오프페이지 저장과 같은 문제가 PostgreSQL에서 재현된다.** `SET STORAGE PLAIN`이 대응 수단이며, HNSW 도입 후에는 인덱스가 벡터 사본을 갖기 때문에 영향이 줄어든다 — 인덱스 단계에서 함께 판단한다 |

검증: `VectorTypeMappingTest`(엔티티 왕복 / `ChunkVector` 투영 왕복 / 차원 불일치 거부).
**투영 왕복을 따로 보는 이유**는 검색 경로가 엔티티가 아니라 생성자 투영으로 벡터만 뽑아 오기 때문이다.

**MySQL 9.0 업그레이드는 선택지가 아니다** — `VECTOR` 타입은 있으나 ANN 인덱스가 HeatWave(유료) 전용이라
커뮤니티 에디션에서는 8.0 + BLOB 브루트포스와 성능이 같다. innovation 릴리스라 지원 주기도 짧다.

## P2 — 휴가↔근태 연동 (반나절)

`AbsenceRequestService.approveRequest()`가 상태만 `APPROVED`로 바꾸고 끝난다. `absence` 패키지 전체에 `Attendance` 참조가 **0건**이며, `AttendanceStatus.VACATION`은 **정의만 되고 아무도 사용하지 않는다.** 즉 휴가를 승인받아도 근태에 반영되지 않는다.

| # | 항목 | 동시에 닫히는 ADR-0005 항목 |
|---|---|---|
| ~~P2-1~~ | ~~휴가 승인 시 해당 기간 근태를 `VACATION`/`SICK`으로 반영~~ | **완료** — "휴가 관리 절반만 충족" 해소 |
| ~~P2-2~~ | ~~승인 이벤트를 `ApplicationEvent`로 발행 → 근태 모듈이 수신~~ | **완료** — "이벤트 기반 설계 없음" 해소 |
| ~~P2-3~~ | ~~자정 배치로 미체크 인원 `ABSENT` 처리~~ | **완료** — "배치/스케줄링 없음" 해소 |
| ~~P2-4~~ | ~~연차 잔여일수 차감~~ | **이미 구현되어 있었음** — `Member.useLeaveDays()` + `INSUFFICIENT_LEAVE_DAYS` 검증. 백로그 작성 시 오기 |

**설계 판단**

- **이벤트로 분리하되 트랜잭션은 분리하지 않았다.** 비동기나 `AFTER_COMMIT`으로 두면 근태 반영이
  실패했을 때 승인만 남아 **승인된 휴가인데 결근 처리**되는 상태가 된다. `@EventListener`(동기)라
  같은 트랜잭션에서 실행되고 실패 시 함께 롤백된다. 결합도만 낮추고 원자성은 유지한다.
- **`Attendance.clockInTime`을 nullable로 바꿨다.** `NOT NULL`은 "출근한 날"만 상정한 제약이라
  휴가·결근을 담을 수 없었다. 더미 시각을 넣으면 "0시에 출근한 기록"이 되어 근무시간 집계를 오염시킨다.
- **소급 승인 시 기존 기록을 덮어쓰지 않는다.** 이미 출근한 날에 휴가가 승인되면 실제 출퇴근 기록이
  사라지므로, 덮어쓰기는 관리자의 명시적 수정으로 다룰 문제다.
- **배치가 `Clock`을 주입받는다.** `LocalDate.now()`를 직접 부르면 "어제"가 실행 시각에 따라 달라져
  테스트가 불가능하다. 근태는 날짜 경계가 곧 비즈니스 규칙이다.

### P2-6 — 근무일 캘린더

**1단계 완료.** `work_calendar` 테이블 + `WorkCalendarService`로 결근 배치가 근무일을 판단한다.
"공휴일에 전원 결근" 사고는 막혔다.

| 설계 | 근거 |
|---|---|
| **날짜를 PK로 (자연키)** | 같은 날이 두 번 등록될 수 없어야 한다. 대리키 + 유니크 제약보다 의도가 직접 드러난다 |
| **미등록 = 기본 규칙** (평일 근무, 주말 휴무) | 캘린더를 비워둬도 기존 동작이 유지되어 점진 도입이 가능하다. 반대로 "미등록=휴무"로 잡으면 캘린더를 채우기 전까지 **결근 배치가 조용히 무력화**된다 |
| **양방향 예외 표현** | 평일인데 쉬는 날(공휴일)과 주말인데 일하는 날(특근)이 둘 다 존재한다. `DayType.WORKDAY`를 주말에 등록하면 특근일이 된다 |
| **근무일 판단을 한 곳으로** | 초과근무 계산·월말 집계도 같은 판단이 필요해진다. 각자 요일을 보게 두면 곧 어긋난다 |

**남은 것 — 등록 수단이 없다.** `WorkCalendarService.register()` / `registerAll()`은 있으나
**HTTP 엔드포인트가 없어 현재는 SQL로만 넣을 수 있다.** 관리자 컨트롤러가 필요하고,
공공데이터 API(한국천문연구원 특일 정보) 연동으로 법정공휴일을 연 1회 자동 적재하면 손이 덜 간다.

**2·3단계는 P3(근무 정책 엔진)** — 교대조별 휴무 패턴, 개인별 예외.
이 캘린더는 **전사 공통 휴무일만** 다룬다.

작업량 대비 닫히는 항목이 많다. P1 완주 후 착수한다.

### P2-5 — `JwtBlacklist` Redis 이관

`JwtBlacklist`가 `ConcurrentHashMap` **인메모리**다(`JwtBlacklist.java:11`). 단일 인스턴스에서도 문제가 된다:
**재배포하면 블랙리스트가 통째로 사라져, 로그아웃했던 토큰이 만료 전까지 되살아난다.**

Redis는 이미 분산락으로 도입되어 있으므로 저장소를 추가할 필요는 없다. 다중화 시에도 선결 과제이므로
스케일아웃 로드맵(ADR-0004)보다 앞선다.

> 참고 — 인스턴스를 2대 이상으로 늘릴 경우 함께 깨지는 것:
> - `JwtBlacklist` 인메모리 → 인스턴스별로 갈림 (보안)
> - `WebSocketConfig.enableSimpleBroker` → 프로세스 내부 브로커라 인스턴스 간 메시지 전달 불가 (기능)
> - 로컬 캐시 도입 시 정합성
>
> 다만 **MAU 5,000 기준 피크가 약 10 TPS라 성능 목적의 스케일아웃 근거는 없다**(`SERVICE-SCALE-ASSUMPTIONS.md`).
> 늘린다면 이유는 처리량이 아니라 가용성(무중단 배포)이며, 그 전에 ADR-0002 2-2의 채팅 N+1을 먼저 고쳐야 한다
> — N+1이 남은 채로 인스턴스를 늘리면 DB 쿼리만 2배가 된다.

## P2-7 — 코퍼스 보존 정책 (ADR-0007)

작업일지는 **4,000건/일 → 100만 건/년**이고 청크는 1년 200~300만이다. 만료 개념이 없어
코퍼스가 단조 증가한다. ADR-0006은 이 증가를 Phase 2 전환 트리거로만 다뤘고
**2년차 이후를 다룬 적이 없다.**

결정은 ADR-0007에 있다 — **원본은 남기고 색인만 만료시킨다.** 만료는 `DELETE`가 아니라
range 파티션 + `DROP PARTITION`이며, 이유는 HNSW가 대량 삭제와 궁합이 나쁘기 때문이다.

| # | 항목 | 상태 |
|---|---|---|
| P2-7-1 | `DocumentChunk.source_created_at` 추가 — 원본 작성일 비정규화 | **가장 먼저.** 나머지가 의존. 생성 코퍼스가 작성일을 2년에 걸쳐 만들므로 이제 측정 대상이 있다 |
| P2-7-2 | 채택 근거의 원본 작성일 분포 측정 → 만료 기간 `N` 결정 | 챗봇 로그 축적 후 |
| P2-7-3 | HNSW 대량 `DELETE` 후 recall/인덱스 크기 실측 | ADR-0007 5-1의 [검증 필요] |
| P2-7-4 | 파티션 전환 | 1·2 이후 |

> **`created_at`이 기준일이 될 수 없다.** 청크가 **색인된** 시각이라 모델 교체로 전체 재색인하면
> 전부 리셋된다. 3년 전 작업일지가 "오늘 만들어진 것"이 되어 만료를 빠져나간다.
> 지금은 처음 색인하는 중이라 둘이 우연히 비슷해서 드러나지 않는다 —
> **보존 정책을 붙이는 순간 조용히 틀리는 종류다.**

**지금 결정해둔 이유** — 파티셔닝은 소급이 비싸다. 900만 행이 쌓인 뒤 옮기려면 전량 복사이고,
그 시점엔 디스크와 시간이 둘 다 부족하다. `source_created_at`도 지금 채우는 게 정확하다.

## P0-14 — `@Lob`이 PostgreSQL에서 작업일지 읽기를 통째로 깨뜨리고 있었다 (완료)

시드를 넣고 **색인을 처음 돌린 순간** 드러났다.

```
Bad value for type long : 오전 작업 시작 직후부터 용접 와이어가 간헐적으로 멈추는...
```

`WorkLog.logText`에 `@Lob`이 붙어 있었다. `@Lob String`은 Hibernate가 `Types.CLOB`으로
매핑하는데 **PgJDBC는 CLOB을 Large Object의 OID(숫자 참조)로 취급한다.** 그래서 `text` 컬럼을
읽으면서 그 내용을 `long`으로 파싱하려다 실패한다. MySQL에서는 `LONGTEXT`로 매핑되어 잘 돌았다 —
`SafetyCourse.createdAt`의 `columnDefinition = "DATETIME"`과 같은 **이관 잔재**다.

**색인만의 문제가 아니었다. JPA로 작업일지를 읽는 모든 경로가 깨져 있었다** — 목록도 상세도.

두 겹으로 가려져 있었다:

| 왜 안 드러났나 |
|---|
| `columnDefinition = "TEXT"`가 DDL을 강제하므로 **테이블은 정상적으로 `text`** 다. `validate`는 컬럼 타입만 보고 JDBC 바인딩은 보지 않아 통과한다 — `SchemaValidationTest`도 마찬가지다 |
| `work_logs`가 계속 비어 있어 **조회가 행을 하나도 반환한 적이 없었다.** 터지려면 실제 행을 읽어야 한다 |

> **"시드 수단이 없다"(P0-13-4)가 실제로 무엇을 가리고 있었는지 보여주는 사례다.**
> 표본 데이터가 있었다면 이관 직후에 드러났을 결함이고, 없었기 때문에 아무도 몰랐다.

조치: `@Lob` 제거. `columnDefinition = "TEXT"`가 DDL을 결정하므로 스키마는 그대로이고
바인딩만 일반 문자열로 돌아온다.

| # | 후속 | 근거 |
|---|---|---|
| P0-14-1 | `validate`가 못 보는 것 목록에 **JDBC 바인딩**을 추가 | P0-13-3이 "nullability·기본값·인덱스·FK·잉여 항목"을 적었으나 이 항목이 빠져 있었다. 타입이 맞아도 읽지 못할 수 있다 |

시드를 만들면서 RAG 경로를 훑다가 나온 것들이다. **어느 것도 시드 때문에 생긴 문제가 아니라,
데이터가 없어서 지금까지 드러나지 않았던 것들이다.**

| # | 항목 | 근거 |

| P2-8-1 | **`RagChatService.buildPrompt()`가 한국어 지시문을 하드코딩한다** | `ChatDomain.Request.lang()`과 `users.language_code`가 둘 다 있는데 프롬프트에 반영되지 않는다. 베트남어로 물어도 지시문과 근거가 한국어로 가고 **답변 언어는 FastAPI 쪽 모델이 알아서 정한다.** 즉 검색은 교차언어인데 생성은 제어되지 않는다 |

### P2-8-3 — 번역본 색인은 교차언어의 "성립 조건"이 아니다

`IndexingService` 주석이 **"번역본까지 같은 벡터 공간에 넣어 교차언어 검색이 성립한다"** 고 적고 있으나,
바로 옆의 `CrossLingualRetrievalTest`가 이를 반증한다 — **한국어 코퍼스만 두고** 영어 5/5,
베트남어 4/5로 통과했다. 번역본 없이도 교차언어는 이미 성립한다.

즉 번역본 색인은 **성립 조건이 아니라 품질 보강**이다. 그리고 보강에는 값이 붙는다:
저장·임베딩 비용이 배로 늘고, P2-8-2의 중복 점유가 생긴다.

> **"없으면 안 되는 것"이면 감수할 비용이지만 "있으면 좋은 것"이면 얼마나 좋아지는지를 재고 판단할 문제다.**
> 지금은 그 수치가 없다. 주석의 인과 표현부터 고쳐야 한다.

측정 항목 — 시드 코퍼스로 가능해졌다:

| 재는 것 | 방법 |
|---|---|
| 번역본 색인 on/off의 recall@5 차이 | 보강 효과의 크기 |
| 원문+번역본이 top-k에 함께 뽑히는 비율 | 중복 점유의 실제 손해 |

결과가 "이득 큼"이면 유지하되 `sourceKey`를 원본 기준으로 묶어 중복만 제거하고,
"이득 작음"이면 번역본 색인을 끈다.

### P2-8-6 — 색인 반영 지연: CDC 말고 중간 선택지가 있다

ADR-0003 3-3은 동기화 방식을 **배치 vs CDC(Debezium)** 둘로 놓고 배치를 골랐다.
그 판단 자체는 유효하지만 **전제가 지금과 다르다** — 3-3은 "MySQL 원본 → 별도 저장소 ES"를
가정한 항목이고, 지금은 원본도 색인도 **같은 PostgreSQL 안**에 있다.

그래서 ADR에 없는 선택지가 하나 생겼다:

| 방식 | 지연 | 추가 인프라 | 놓치는 것 |
|---|---|---|---|
| 현재 — 배치 pull | 최대 1주기(하루) | 없음 | — |
| **애플리케이션 이벤트** | 즉시 | **없음** | DB를 직접 고친 변경 |
| CDC(Debezium) | 즉시 | Kafka + 커넥터 | — |

이벤트 방식은 P2-1/P2-2에서 휴가 승인 → 근태 반영에 이미 쓴 패턴이고 인프라가 늘지 않는다.
CDC의 장점은 "애플리케이션을 우회한 변경도 잡는다"인데, **작업일지는 API로만 들어온다.**

### P2-9-2~4 — 한도가 두 곳에 있으면 "누가 거절하는가"를 정해야 한다 (완료)

셋을 한 묶음으로 고쳤다. 서로 다른 증상이지만 **원인이 하나**였기 때문이다 —
같은 한도가 nginx와 애플리케이션 양쪽에 있는데 **어느 쪽이 판단 주체인지 정해진 적이 없었다.**
그래서 매번 우연히 앞에 선 프록시가 이겼다.

**정한 규칙: 애플리케이션이 거절 주체이고, nginx는 그보다 느슨한 바깥 울타리다.**
그래야 클라이언트가 받는 것이 nginx 기본 HTML이 아니라 `ErrorResponseDto`가 된다.

| 항목 | 전 | 후 |
|---|---|---|
| 업로드 | nginx 10M / Spring 10MB → **프록시가 먼저 자름** | nginx **20M** / Spring 10MB → 앱이 자르고 `MaxUploadSizeExceededException` |
| 타임아웃 | nginx 미설정(60s) / Spring 120s → **120초는 도달 불가** | nginx **125s** / Spring 120s → 앱이 끊는다 |

#### 고치기 전 상태를 그대로 재현했다

**설정을 넣고 "됐다"고 적지 않았다.** 임시 네트워크에 에코 업스트림을 `dockin-app` 이름으로 띄우고
**고치기 전 설정과 고친 설정을 나란히** 올려 같은 요청을 보냈다.

| 검증 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `/ws` 업그레이드 요청이 업스트림에 도달할 때 | `upgrade`·`connection` 헤더 **소실** | `upgrade: websocket` / `connection: upgrade` **도달** |
| 응답 없는 업스트림에 요청 | **504 / 60.2초** | 90초까지 **안 끊김**(125초 설정) |
| 15MB 업로드 | **413** — 앱에 닿지도 못함 | **200** — 앱까지 전달 |
| 25MB 업로드 | nginx 기본 HTML | `{"status":413,"message":...,"timestamp":...}` |

> **"기본 60초"는 문서에 적혀만 있고 아무도 확인한 적이 없던 값이다.** 60.2초에 504가
> 나오는 것을 보고서야 그 진술이 사실이 됐다. P0-7의 "DB 없이도 안전하게 돌릴 수 있다"가
> 확인해보니 아니었던 것과 같은 자리다 — **적혀 있다는 것과 그렇다는 것은 다르다.**

#### `Sec-WebSocket-*` 헤더는 통과한다 — 그래서 조용하다

재현에서 눈에 띈 것 하나. 고치기 전 설정에서도 `sec-websocket-key`·`sec-websocket-version`은
**멀쩡히 업스트림에 도달했다.** 걷어내지는 것은 `Upgrade`와 `Connection`뿐이다(hop-by-hop 헤더).

즉 서버가 받는 요청은 **거의 맞아 보이는데** 핸드셰이크만 성립하지 않는다.
`@Lob`이 `validate`를 통과하던 것, `batch_size`가 `IDENTITY`에 막히던 것과 같은 종류다 —
**틀린 곳이 로그에 남지 않는다.**

#### 하지 않은 것과 그 이유

| 항목 | 판단 |
|---|---|
| **`.withSockJS()` 폴백** | 붙이지 않았다. 클라이언트가 SockJS 라이브러리를 써야 하는 **계약 변경**이라 프록시 정합성 수정과 섞을 문제가 아니다. 다만 nginx의 `Connection` 헤더를 `map`으로 처리해 **나중에 붙여도 깨지지 않게** 해뒀다(업그레이드가 아닌 요청에는 `close`가 간다) |
| **8080 포트 노출 제거** | 유지했다. 팀 프론트엔드가 그 주소를 쓰고 있어 닫는 것은 별개 결정이다. 대신 `chat_test.html`을 80으로 옮겨 **고친 프록시 경로가 실제로 한 번은 돌게** 했다 — 아무도 안 쓰는 경로는 고쳐도 깨져 있는지 알 수 없다 |
| **동기 컨트롤러 타임아웃** | `spring.mvc.async.request-timeout`은 비동기 경로에만 적용된다. 동기 경로에는 Spring 쪽 한도가 없어 **여전히 nginx가 유일한 천장**이고, 그 값이 60초에서 125초로 늘어났다. 별도 항목(N6와 같은 자리) |
| **STOMP heartbeat** | `/ws`의 `proxy_read_timeout`을 3600초로 둔 것은 임시방편이다. heartbeat(N5)가 붙으면 훨씬 작게 줄일 수 있다. 지금은 "조용한 연결"과 "죽은 연결"이 구분되지 않는다 |

#### nginx의 413에는 한계가 남는다

바깥 울타리(20M)에 걸리는 요청에 `error_page 413`으로 같은 형식의 JSON을 내도록 했지만
두 가지가 완전하지는 않다. **적어두지 않으면 나중에 "왜 형식이 미묘하게 다르지"가 된다.**

- `timestamp`가 `$time_iso8601`이라 **오프셋이 붙는다**(`+09:00`). Jackson의 `LocalDateTime`에는 없다
- 클라이언트가 본문을 다 보내기 전에 nginx가 끊으므로, 업로드 중인 클라이언트는 응답 대신
  **커넥션 리셋을 볼 수 있다.** 앱이 거절하는 10~20M 구간에는 이 문제가 없다

### P2-11-2/3 — 관측을 붙이자 관측 대상이 고쳐졌다 (완료)

둘을 함께 했다. **하나만 하면 반쪽이기 때문이다** — 메트릭만 있으면 "무언가 느리다"까지고,
추적 ID만 있으면 "이 요청이 느렸다"까지다. 둘이 있어야 "이 요청이 느렸고 그때 풀이 말라 있었다"가 된다.

| 붙인 것 | 무엇을 답하게 됐나 |
|---|---|
| `/actuator/health` + compose `healthcheck` | **"떴는가"를 기계가 판정한다.** 이전에는 `Started ...` 로그 문자열이 유일한 신호였고, 그마저 `com.DOCKin` 로거라 warn 설정에 묻혀 사라진 적이 있다(이슈 #30) |
| `/actuator/metrics` (ADMIN) | `hikaricp.connections.*` / `jvm.gc.*` / `jvm.memory.*`. **P2-9-1이 막으려던 풀 고갈을 실제로 확인할 수단** |
| `/actuator/info` (ADMIN) | 빌드 버전 + **커밋 해시**. P2-13-1의 "지금 도는 코드가 무엇인지 물을 수 없다"에 답이 생겼다 |
| 로그 패턴 `%X{traceId}` | DB에 남은 `trace_id`로 그 요청의 로그를 찾아갈 수 있다 |

#### 추적 ID는 새로 만든 개념이 아니다 — 끊긴 자리를 이었다

`traceId`는 이미 있었다. DTO 필드로 FastAPI에 넘어가고 `chat_history.trace_id`,
`translate_logs.trace_id`에도 저장된다. **없던 것은 그 사이의 로그뿐이다** — 양 끝은 있고
가운데가 비어 있었다.

그래서 값의 출처에 우선순위를 뒀다. **본문 `traceId` > `X-Trace-Id` 헤더 > 서버 생성.**
본문이 이기는 이유는 그 값이 DB에 저장되기 때문이다. 로그가 다른 값을 쓰면 이을 수 없다.

| 조용히 잘못될 수 있던 것 | 조치 |
|---|---|
| **MDC 누수** — 톰캣이 스레드를 재사용하므로 안 지우면 **다음 요청이 앞 요청의 ID를 달고 로그를 남긴다.** 추적 ID가 아예 없는 것보다 나쁘다(무관한 두 요청이 하나로 읽힌다). 그리고 **부하가 있어야 드러나** 개발 중에는 정상으로 보인다 | `finally`에서 제거. 체인이 예외를 던지는 경우까지 테스트로 고정 |
| **로그 위조** — 헤더는 클라이언트가 정한다. 줄바꿈을 넣으면 로그에 가짜 줄을 만들 수 있고, 응답 헤더로 되돌려주므로 헤더 인젝션도 된다 | 문자 집합·길이 제한. 어긋나면 서버 생성값 |
| **`%X{traceId}`의 기본값 누락** — `:-`가 없으면 요청 밖(배치 스레드)의 로그 줄에 `traceId_IS_UNDEFINED`가 **리터럴로** 찍힌다 | `%X{traceId:-}`. 실제 기동 로그에서 `INFO []`로 렌더링되는 것을 확인했다 |

> **안 되는 것도 적어둔다 — 리액티브 경로에서는 끊긴다.** MDC는 `ThreadLocal`이라
> `/api/ai/rt-translate`(`Mono` 반환)의 WebClient 호출 이후는 Reactor 스레드로 넘어가
> 추적 ID가 따라가지 않는다. **서블릿 스레드 구간까지만 이어진다.**
> 리액터 컨텍스트 전파는 별도 작업이며, 지금은 "안 되는 줄 알고 안 하는 것"으로 둔다.

#### 노출 범위는 "전부 열기"와 "기본값"의 중간이다

기본값(health만)으로는 P2-11-2가 지목한 풀/GC/힙을 볼 수 없고, 전부 열면 `env`(설정값 전체)와
`heapdump`까지 딸려 나온다. `health,info,metrics` 셋만 내보내고 그 위에 권한을 나눴다.

| 경로 | 누구에게 | 이유 |
|---|---|---|
| `/actuator/health` | 익명 | 로드밸런서와 compose 헬스체크가 토큰 없이 닿아야 한다 |
| health의 **세부 항목** | 인증된 사용자만 | `components`에 db·redis·diskSpace가 이름 그대로 있다. 익명에게는 UP/DOWN만 |
| `/actuator/metrics`·`/actuator/info` | ADMIN | 힙·GC·풀 수치와 빌드 커밋 해시. **어느 버전이 도는지를 공격자가 먼저 알 이유가 없다** |

`ActuatorEndpointTest`가 이 경계를 통째로 고정한다. **단위 테스트로는 볼 수 없는 것**이라
전체 컨텍스트를 띄운다 — 검증 대상이 자바 코드가 아니라 **노출 목록과 `requestMatchers` 순서의
상호작용**이고, 한쪽만 고치면 조용히 어긋나기 때문이다.

#### 예정에 없던 것 — JWT 원문이 로그에 남고 있었다

`JwtAuthFilter`가 요청마다 `log.info("Request URI: {}, Authorization Header: {}", path, authHeader)`
였다. **`authHeader`는 `Bearer <JWT 원문>`이다.** 로그를 읽을 수 있으면 만료 전까지 아무
사용자로든 로그인할 수 있다.

P0-9에서 **"값을 에코하면 비밀번호 같은 입력이 응답과 로그에 남는다"** 고 적고 응답 쪽만
지켰다. 원칙은 있었고 **로그 쪽은 보지 않았다.**

**보안 점검으로 찾은 것이 아니다.** 헬스체크가 10초마다 두드리게 되자 이 필터가 로그를
뒤덮을 것이 분명해졌고, 그래서 처음으로 그 줄을 들여다봤다. 값 대신 "있었는가"만 남기고
`debug`로 내렸다. `Authorization 헤더가 없다`의 `warn`도 함께 내렸다 — 로그인·정적 리소스·
헬스체크가 전부 그 경로이고, **정상 트래픽에 쌓이는 경고는 사람이 경고를 안 보게 만든다.**

#### 남은 것

| 항목 | 왜 지금 안 하나 |
|---|---|
| Prometheus/Grafana | 시계열 수집과 알람은 다음 층이다. **먼저 필요한 것은 수집기가 아니라 물어볼 수 있는 상태**였고 그것이 생겼다 |
| 구조적(JSON) 로깅 | 로그 수집기를 정할 때 함께 결정할 문제다 |
| 리액터 컨텍스트 전파 | 위 참고 |
| `userId`를 MDC에 | 추적 ID로 이미 요청은 묶인다. 사용자 축 집계가 필요해지면 그때 |

## P2-12 — 채팅 정합성 (2026-08-05 점검에서 발견)

**채팅은 얕지 않다.** STOMP `CONNECT`의 JWT 검증, `lastReadTime` 기반 읽음 처리,
안읽음 카운트, `last_message_*` 비정규화, `(room_id, sent_at)` 인덱스가 모두 있다.
문제는 깊이가 아니라 **정합성이 어긋나 있다는 것**이다.

| # | 항목 | 근거 | 급함 |
|---|---|---|---|
| P2-12-1 | **방 목록 N+1 (확정)** | `ChatRoomService`가 `chatRoomsPage.map(room -> countByChatRoomsRoomIdAndCreatedAtAfter(...))`로 **방마다 COUNT**를 날린다. 방 20개면 21쿼리. ADR-0002 2-2가 진단만 하고 방치한 그것 | ★ |
| P2-12-2 | **시계가 둘이다** | `ChatMessages.sentAt`은 `@PrePersist`의 **애플리케이션 시각**, `last_message_at`·`last_read_time`은 네이티브 쿼리의 **DB `NOW()`**. 두 시계가 어긋나면 읽음 경계와 최신 메시지가 함께 틀어진다 | ★ |
| P2-12-3 | **읽음 기준이 시각이다** | `createdAt > lastReadTime`으로 안읽음을 센다. 같은 시각 메시지의 경계가 모호하고 P2-12-2와 겹치면 **읽은 것을 안 읽었다고 세거나 그 반대**가 된다. 기준을 `last_read_message_id`(단조 증가 PK)로 바꿔야 한다 | ★ |
| P2-12-4 | **`last_message_content` 경합** | 동시에 두 메시지가 오면 UPDATE 순서 보장이 없어 방 목록의 "마지막 메시지"가 실제 마지막이 아닐 수 있다 | ☆ |
| P2-12-5 | 재연결 시 유실 | STOMP heartbeat 미설정이고, 끊긴 동안의 메시지를 따라잡는 경로가 없다. 마지막 수신 `message_id` 기준 동기화가 필요 | ☆ |
| P2-12-8 | **방 목록에 정렬이 없다** | `ChatRoomController#findAllRooms`의 `@PageableDefault`에 `sort`가 비어 있다 — 작업일지에서 고친 P2-15-3과 같은 결함이다. **거기서 함께 고치지 않은 이유는 정렬 키가 제품 결정이기 때문**이다. `last_message_at`이 자연스럽지만 그 컬럼은 **P2-12-4가 경합으로 실제 마지막이 아닐 수 있다고 지목한 자리**라, 순서의 기준으로 삼기 전에 P2-12-4를 먼저 정해야 한다. `PageableSortDefaultTest`가 이 한 건을 `KNOWN_UNSORTED`로 들고 있다 | ★ |

> **P2-12-2·3은 "시각으로 상태를 판단하면 안 된다"는 한 문제다.** 근태 배치에 `Clock`을
> 주입한 판단과 같은 계열이고, 해법(단조 증가 ID 기준)은 인덱싱에서 OFFSET을 커서로 바꾼
> P1-13과 같은 발상이다.

### P2-12-7 — `message_id`를 커서로 삼으면 구멍이 생긴다 (선결 확인)

**P2-12-3·5가 전제하는 "ID를 신뢰의 축으로"가 그대로는 성립하지 않는다.**
`message_id`가 `IDENTITY`라 시퀀스가 트랜잭션 밖에서 발급되므로 **커밋 순서와 ID 순서가 다를 수 있다.**

```
트랜잭션 A:  id=10 발급 → (느림) ─────────→ 커밋
트랜잭션 B:  id=11 발급 → 커밋                      ← 11이 먼저 보인다
```

이때 조회하면 11까지 받고 `lastSeen = 11`이 된다. **그 뒤에 커밋되는 10은 영영 못 받는다.**
재연결 커서를 ID로 잡았는데 **그 커서가 구멍을 만드는** 구조다.

| 대응 | 대가 |
|---|---|
| 방 단위 시퀀스를 **트랜잭션 안에서** 부여 | 방마다 직렬화 → 경합. 채팅방은 원래 순서가 필요하므로 받아들일 만하다 |
| 따라잡기에 안전 여유(watermark) | 단순하지만 지연이 붙는다 |
| 갭 감지 후 재조회 | 클라이언트 복잡도 |

> **먼저 실측한다** — 동시 전송 부하에서 커밋 순서와 ID 순서를 비교해 **실제로 역전이 나는지**
> 확인한 뒤 대응을 고른다. 나지 않는다면 그것도 결과다. 이 프로젝트가 `SENTENCE_LOOKBACK`과
> `HibernateBatchInsertVerificationTest`에서 한 것과 같은 방식이다.

### P2-12-6 — FCM 도입 (없으면 채팅이 반쪽이다)

푸시 알림이 전혀 없다(의존성·코드 모두 확인). **WebSocket은 앱이 떠 있을 때만 동작**하므로
앱을 내리면 메시지를 받지 못한다. 조선소 현장에서 앱을 계속 켜두지 않는다.

| 다뤄야 할 것 | 내용 |
|---|---|
| **트랜잭션 경계** | 메시지 저장 트랜잭션 안에서 FCM을 호출하면 **롤백돼도 알림은 이미 나간다.** `@TransactionalEventListener(AFTER_COMMIT)`이 답이다 |
| 중복 알림 | WebSocket으로 이미 받았는데 FCM도 오면 두 번. `StompHandler`가 `CONNECT`/`DISCONNECT`를 잡고 있어 연결 상태를 둘 자리가 이미 있다 |
| 토큰 생명주기 | 기기별 토큰, 만료·갱신, 로그아웃 시 삭제, 다기기 |
| 도메인 연결 | `WorkShift` → 야간 근무자에게 새벽 알림을 보낼 것인가. `language_code` → 알림 본문 다국어 |

> **트랜잭션 경계가 P2-2와 정반대라는 점이 이 항목의 핵심이다.** 휴가 승인 → 근태 반영은
> **동기 리스너로 같은 트랜잭션**에 뒀다(실패하면 함께 롤백돼야 하므로). FCM은 반대다.
> 같은 `ApplicationEvent`를 반대로 쓰는 기준은 하나 — **"함께 실패해야 하는가."**

## P2-13 — 부분 색인 준비 중 드러난 것 (2026-08-06)

ANN recall 측정(A1)을 위해 코퍼스를 채우려고 컨테이너를 올리다 나왔다.

| # | 항목 | 근거 | 급함 |

| P2-13-2 | **원본 1건당 청크 수가 1.22다** | 문서가 **2~3배로 가정**하던 값이다. 4,300건 색인 표본에서 `WORK_LOG` 청크 5,227개 → **1.22**. 평균 청크 길이 254자와도 앞뒤가 맞는다(작업일지 본문이 대개 한 청크에 들어간다) | ☆ |

### P2-13-1 상세 — 이것은 P2-11의 배포 항목이 구체화된 형태다

로드맵 7-5가 "CI는 있고 CD는 없다"고 적어둔 것이 **추상적 부채가 아니라 지금 실제로
낡은 코드가 돌고 있다**는 형태로 확인됐다. `compose.yaml`의 `build: .`가 주석 처리되어
있고 레지스트리 이미지를 쓰므로, **소스를 고쳐도 컨테이너에는 반영되지 않는다.**

> **이 프로젝트가 계속 잡아온 것의 한 변종이다.** 지금까지는 전부
> **"설정은 있는데 안 먹는다"** 였다(`batch_size` ↔ `IDENTITY`, JPA 락 힌트 ↔ MySQL,
> `@Lob` ↔ `validate`, `JAVA_OPTS` ↔ `ENTRYPOINT`). 이번엔 한 칸 더 나간
> **"코드는 고쳤는데 올라가 있지 않다"** 이고, 층위가 설정에서 **배포 산출물**로 옮겨갔다.

### P2-14-1 상세 — 없는 것과 고장난 것을 구분하지 못한다

**클라이언트가 잘못한 것(404)과 서버가 잘못한 것(500)은 대응이 다르다.**
전자는 요청을 고쳐야 하고 후자는 서버를 고쳐야 한다. 지금은 둘이 같은 코드로 나간다.

| 영향 | 내용 |
|---|---|
| 운영 | **로드밸런서가 `/`를 헬스체크로 때리면 서버를 죽은 것으로 판정한다.** 실제로는 멀쩡하다 |
| 관측 | 5xx 알람을 걸면 정상 트래픽에 계속 울린다. 알람을 끄게 되고, 그러면 진짜 500을 놓친다 |
| 첫인상 | 저장소를 처음 여는 사람이 루트로 접속하면 서버 오류를 본다 |

`GlobalExceptionHandler`에 `NoResourceFoundException` 처리를 더해 404로 내리는 것이
직접적인 수정이다. 다만 **같은 형태로 잘못 승격되는 예외가 더 있는지** 함께 봐야 한다 —
Spring이 던지는 클라이언트 오류 계열(`MethodArgumentTypeMismatchException`,
`HttpRequestMethodNotSupportedException`, `HttpMessageNotReadableException`)이 전부 같은 자리다.

> **"처리되지 않은 예외"를 전부 500으로 접는 catch-all은 그 자체가 결함이 아니다.**
> 마지막 방어선은 있어야 한다. 문제는 **그 그물이 너무 위쪽에 쳐져 있어서**
> 클라이언트 오류까지 걷어 올린다는 것이다.

### P2-14-2 상세 — 처음엔 "`Started` 로그가 없다"로 보였다

기동을 기다리는데 `Started DocKinSpringApplication in N seconds`가 끝내 안 나왔다.
`log-startup-info`를 끈 적이 없고 `main`은 정상 종료했으며 앱도 잘 돌았다.

**그 다음 색인을 돌렸을 때 러너의 `[RAG]` 로그도 안 나왔다.** 색인은 확실히 돌고 있었다 —
스레드 덤프에서 `main`이 `SeedIndexingRunner → IndexingService → ChunkIndexWriter.flush
→ EmbeddingClient.embedPassages → Mono.block`에 있었고 `document_chunks`도 늘고 있었다.
두 번째 사례가 나오고서야 공통점이 보였다. **둘 다 `com.DOCKin`의 INFO였다.**

```
logging.level.root=info
logging.level.com.DOCKin=warn      <-- .env 27번 줄
```

`root`가 `info`라 **로그가 비어 보이지 않는다.** Tomcat, Hikari, Flyway, Hibernate의
INFO는 그대로 흐르고 우리 코드의 INFO만 빠진다. 그래서 오래 눈에 띄지 않았다.

| 가려진 것 | 내용 |
|---|---|
| 기동 완료 | `Started ...`의 로거 이름이 `com.DOCKin.DocKinSpringApplication`이라 같이 걸린다. **"떴다"를 기계가 판정할 신호가 없다.** CD를 붙이면 그 시점에 바로 걸리고, compose에 앱 헬스체크가 없는 것과도 겹친다 |
| 배치 진행률 | **수 시간 걸리는 색인이 아무것도 남기지 않는다.** 진행 확인에 DB를 직접 세거나 스레드 덤프를 떠야 했다 |

> **정할 것은 "지우자"가 아니라 "의도였나"다.** 로그가 시끄러워 줄인 것이라면 `.env`가
> 아니라 `application.properties`에 이유와 함께 두어야 한다. **`.env`는 커밋되지 않으므로
> 지금 이 설정은 사람마다 다르게 동작한다** — 누구는 로그가 보이고 누구는 안 보인다.

P2-11-2(Actuator)와도 이어진다. `/actuator/health`가 있으면 기동 판정을 로그에
의존하지 않아도 된다.

> **2026-08-07에 그렇게 했다.** compose의 `dockin-app`에 `/actuator/health` 헬스체크가 붙었고,
> nginx는 앱이 **건강해진 뒤에** 뜬다. 기동 판정이 더는 로그 문자열 하나에 걸려 있지 않다 —
> 이 절이 기록한 사고(설정 하나로 그 문자열이 통째로 사라진 것)가 다시 나도 판정은 멀쩡하다.

### P2-14-3 상세 — 컬렉터를 환경이 고르고 있다

JVM은 실행 환경이 server-class인지 보고 컬렉터를 정한다. 조건은 **CPU 2개 이상 AND
메모리 1792MB 이상**이다. 2×2로 갈랐다.

| | 메모리 512M | 메모리 2G |
|---|---|---|
| **CPU 무제한** | Serial | **G1** |
| **CPU 1.0** | Serial | Serial |

**메모리 512M만으로 이미 Serial이었다** — CPU 상한(P2-10-3)을 넣기 전부터다.
다만 그 상한이 **두 번째 독립 원인을 추가**해서, 이제는 메모리를 올려도 Serial이다.
손잡이 하나가 가려졌다.

색인 부하 13분간 실측:

```
Young GC 132회   pause  min 2.3ms / median 12.9ms / max 132.6ms
Full  GC   8회   전부 (Metadata GC Threshold) — 기동 90초 안에 몰려 있다
힙 점유          124M -> 55M (247M)   최대 400M 중 247M만 커밋
```

**`Allocation Failure`로 인한 Full GC는 한 번도 없었다. 힙 400M이 좁다는 근거는 없다.**
눈에 띄는 것은 Young pause 최댓값 132.6ms로, 중앙값의 10배다.

> **당장 바꿀 일은 아니지만 "환경이 알아서 고르게 두는" 지금이 가장 나쁘다.**
> 최소한 `-XX:+UseSerialGC`를 명시해 **선택을 기록**해야 한다. 그러지 않으면
> 컨테이너 메모리 제한을 올리는 순간 컬렉터가 조용히 바뀐다. G1로 갈지는 재본 뒤에 정한다.

### P2-15-1 — 가설은 행당 3이었고 실측은 행당 1이었다

`WorkLogDto.from`이 지연 로딩을 **세 번** 건드린다고 읽었다.

```java
entity.getMember().getUserId()          // @ManyToOne(LAZY)
entity.getEquipment().getEquipmentId()  // @ManyToOne(LAZY)
entity.getImages().stream()             // @OneToMany(LAZY)
```

페이지 크기 20이면 지연 로딩이 60번이어야 한다. **Hibernate가 센 값은 20번이었다.**

| 엔드포인트 | 페이지 크기 | 반환 행 | JDBC 문장 | 고정 비용 | 컬렉션 페치 |
|---|---|---|---|---|---|
| 전체 목록 | 10 | 10 | **14** | 4 | 10 |
| 전체 목록 | 20 | 20 | **24** | 4 | 20 |
| 타인 목록 | 20 | 20 | **24** | 4 | 20 |
| 키워드 검색 | 20 | 20 | **22** | 2 | 20 |

**앞의 둘이 식별자만 읽기 때문이다.** `getUserId()`와 `getEquipmentId()`는 각 엔티티의
`@Id`이고, FK 값은 이미 `work_logs` 행 안에 있다. 지연 프록시는 만들어질 때 식별자를 함께
받으므로 **그 값을 답하는 데 쿼리가 필요 없다.** `getMember().getName()`이었다면 달랐다.

남는 것은 `getImages()` 하나다. 컬렉션은 식별자로 답할 수 없어 **행마다 정확히 한 번** 나가고,
**이미지가 없는 행도 나간다** — 비어 있다는 것을 확인하려면 조회해야 한다.

고정 비용이 엔드포인트마다 다른 것도 그 자체로 정보다.

| 엔드포인트 | 고정 4 또는 2의 내역 |
|---|---|
| 전체 목록 | 내 정보 / **구역 사용자 전체** / 본문 / COUNT |
| 타인 목록 | 내 정보 / 대상자 정보 / 본문 / COUNT |
| 키워드 검색 | 본문 / COUNT |

전체 목록의 두 번째가 `findByShipYardArea`다. 쿼리 **개수**로는 1이라 여기서는 작아 보이지만
**구역 사용자를 전부 메모리로 올린 뒤 `IN` 절에 통째로 넣는다.** 개수를 재는 측정이
크기를 재는 측정을 대신할 수 없는 지점이다.

> **처음 측정은 표본이 잘못돼 있었다.** 작성자 5명으로 시드했더니 여러 행이 같은 프록시를
> 공유해서, 쿼리가 안 나간 이유가 "식별자만 읽어서"인지 "공유해서"인지 구별되지 않았다.
> 작성자와 장비를 **행마다 모두 다르게** 만든 뒤에야 주장이 성립했고, 그 전제가 되돌아가면
> 숫자는 그대로인 채 **의미만 잃으므로** `표본_전제_검사`를 따로 뒀다.

### P2-15-2 — 장비 없는 일지 하나가 페이지 전체를 500으로 만든다 (완료)

`WorkLogDto.from`(`WorkLogDto.java:51`)이 `entity.getEquipment().getEquipmentId()`를
**무조건** 불렀다. `equipment_id`는 `V2__baseline_existing_tables.sql`에서 **nullable**이고,
`@ManyToOne(LAZY)`는 FK가 NULL이면 프록시가 아니라 **null을 넣는다.**
P2-15-1이 "식별자만 읽으니 쿼리가 안 나간다"고 한 그 접근이, NULL 앞에서는 반대로 터진다 —
**안전한 이유와 터지는 이유가 같은 자리에 있다.**

**생성 API로는 이 상태가 만들어지지 않는다.** `createWorklog`가
`equipmentRepository.findById(...)`로 장비를 필수로 요구하기 때문이다. 그래서
**API만 두드려서는 영영 드러나지 않는다.** 반면 컬럼은 NULL을 허용하고, 코퍼스 생성기는
여섯 건 중 하나를 장비 없이 넣는다 — **현재 로컬 DB에 3,331건 있다.**

> **스키마가 허용하는 상태를 코드가 가정으로 배제하고 있었다.** 이 저장소가 반복해서 잡아 온
> "선언과 실제의 불일치"와 같은 부류다(`@Lob`↔`validate`, `JAVA_OPTS`↔`ENTRYPOINT`).

영향 범위가 행 하나가 아니라 **페이지**라는 점이 핵심이다. `Page.map`은 한 행에서 터지면
거기서 멈추므로, 장비 없는 일지 하나가 그 페이지를 통째로 못 보게 만든다.
그리고 P2-14-1로 `NoResourceFoundException`을 404로 내려보냈지만 이건 **진짜 500**이다.

#### 고친 방향 — 계약이 이미 답을 갖고 있었다

`equipmentId`는 이 DTO에서 **`requiredMode`가 붙지 않은 선택 필드**다. 즉 스키마도 계약도
"장비 없는 작업일지"를 허용하고 있었고 **구현만 그것을 배제했다.** 그래서 예외를 새로
정의하거나 행을 걸러내지 않고, 없는 것을 없다고 답하게 했다.

```java
.equipmentId(entity.getEquipment() == null ? null : entity.getEquipment().getEquipmentId())
```

**쓰기 경로 안에서도 이미 갈려 있었다** — 같은 서비스의 `updateWorklog`는
`dto.getEquipmentId() != null`로 장비를 **선택**으로 다루는데 `createWorklog`는 필수로 요구한다.
읽기 쪽만의 문제가 아니라 **필수/선택이 한 도메인 안에서 합의된 적이 없다.**
(둘 중 어느 쪽으로 통일할지는 이 수정의 범위 밖이다.)

#### 결함을 고정하던 테스트를 뒤집었다

`WorkLogListQueryCountTest.장비가_없으면_목록이_죽는다`가 `assertThrows(NullPointerException)`으로
**깨진 상태를 못 박고** 있었다. 그것을 `장비가_없어도_목록이_나온다`로 바꿨고, 단언을 셋으로 나눴다 —
**"예외가 안 난다"만 보면 그 행을 응답에서 빼버리는 것으로 고쳐도 통과하기 때문이다.**

| 단언 | 막는 것 |
|---|---|
| 반환 행 = 1 | 행을 조용히 걸러내는 수정 |
| `equipmentId`가 null | 0이나 -1 같은 값을 채워 넣는 수정 |
| `userId`·`title`이 멀쩡 | 장비와 무관한 필드까지 비우는 수정 |

**쿼리 수는 변하지 않았다** — 고친 뒤에도 `4+10 / 4+20 / 4+20 / 2+20`으로 P2-15-1의 식이
그대로다. null 검사는 프록시를 건드리지 않으므로 당연하지만, 같은 테스트 클래스가 둘을
함께 재고 있어 **성능을 대가로 고친 것이 아님이 자동으로 확인된다.**

#### `member`는 함께 고치지 않았다 — 방향이 반대다 (→ P2-15-6)

`user_id`도 스키마상 nullable이라 바로 위 줄(`entity.getMember().getUserId()`)이 같은 자리에 있다.
그런데 **고칠 방향이 반대다.**

| | 계약 | NULL이면 |
|---|---|---|
| `equipmentId` | 선택 필드 | null이 **정당한 값** → 가드가 맞다 |
| `userId` | `requiredMode = REQUIRED` | 가드를 두면 **필수 필드에 null을 담은 응답**을 조용히 내보낸다 |

저쪽의 답은 가드가 아니라 **컬럼을 `NOT NULL`로 만드는 것**이고, 그건 마이그레이션과
기존 행 점검이 딸린 별개 결정이다. `IndexingService`는 이미 `getMember() == null`을
방어하고 있어 **같은 코드베이스 안에서 두 경로가 서로 다른 전제를 갖고 있다.**

### P2-15-3 — 목록에 정렬이 없다 (완료)

```java
@PageableDefault(size = 20, direction = Sort.Direction.DESC) Pageable pageable
```

`sort` 속성이 비어 있었다. **방향만으로는 정렬이 만들어지지 않으므로** 이 Pageable은
unsorted다. 즉 `GET /api/work-logs`와 `/others/{id}`는 **정해지지 않은 순서로** 응답했다
(`/search`만 `sort = "createdAt"`이 있었다).

정렬이 없는 OFFSET 페이징은 **페이지 경계에서 행이 중복되거나 누락된다** — DB가 순서를
보장하지 않으므로 1페이지와 2페이지가 같은 행을 담거나 어떤 행도 담지 않을 수 있다.
`WorkLogRepository.findForIndexingAfter`가 **커서 방식을 고르며 적어 둔 이유가 바로 이것**인데
(정렬이 불안정하면 중복·누락), 목록 API는 그 지적을 받지 않은 채 남아 있었다.

#### `createdAt` 하나로는 못 고친다

세 엔드포인트를 `sort = {"createdAt", "logId"}`로 맞췄다. **`/search`도 함께 고쳤다** —
거기엔 `sort`가 있었으므로 원래 P2-15-3의 대상이 아니었지만, `created_at`은 **유니크하지 않다.**
같은 시각의 행이 둘 이상이면 그들 사이 순서가 다시 정해지지 않아 **같은 중복·누락이
그 경계에서 재현된다.** PK를 뒤에 붙여 전순서로 만들었고, 이는 `findForIndexingAfter`가
"정렬 키가 유니크(PK)라 중복·누락도 발생하지 않는다"고 적은 것과 같은 판단이다.

> **정렬이 "있다"와 "충분하다"는 다르다.** 애노테이션만 보면 `/search`는 이미 고쳐진 것처럼
> 보인다 — 이 항목을 `sort`가 비었는지로만 닫았다면 그 자리는 남았을 것이다.

#### 고정한 것이 둘이다 — 선언과 동작을 따로 본다

| 테스트 | 무엇을 막나 | 어디서 도나 |
|---|---|---|
| `PageableSortDefaultTest` | **선언** — `Pageable`을 받는 컨트롤러 메서드에 `sort`가 있는가 | 컨텍스트를 안 띄운다. 바이트코드 스캔이라 수 ms |
| `WorkLogListQueryCountTest.정렬이_실제로_먹는다` | **동작** — 그 이름이 쿼리로 번역되는가 | Testcontainers |

**둘을 나눈 이유가 이 저장소의 반복 주제다.** 선언 검사만으로는 "애노테이션은 멀쩡한데 안 먹는"
경우를 못 잡는다 — `searchWorkLogs`는 `@Query`(JPQL)라 Spring Data가 정렬을 **문자열로 덧붙이고**,
속성 이름이 엔티티 필드와 어긋나면 런타임에 터진다. `batch_size`↔`IDENTITY`, `@Lob`↔`validate`와
같은 자리다.

동작 쪽 테스트는 **시각이 같은 세 건을 일부러 심는다.** 표본의 `createdAt`이 전부 다르면
두 번째 정렬 키가 **한 번도 쓰이지 않은 채** 통과하기 때문이다. 실행 결과 `logId [89, 88, 87]`로
갈렸다.

#### 컨트롤러 전체를 훑은 결과

한 곳을 고치는 것으로 끝낼 문제가 아니라 판단해 `PageableSortDefaultTest`가 `com.DOCKin`
아래 컨트롤러를 전부 검사한다. 정렬 없는 페이징은 **예외를 내지 않는다** — 목록이 나오긴
나오므로 틀린 곳이 로그에 남지 않는다.

| 결과 | |
|---|---|
| 안전·확인됨 | 안전교육 6곳(`courseId`), 휴가 2곳(`requestId`), 채팅 메시지 2곳(`messageId`) — 전부 유니크 PK |
| 고침 | 작업일지 3곳 |
| **남음** | `ChatRoomController#findAllRooms` → **P2-12-8** |

알고 둔 위반은 `KNOWN_UNSORTED` 목록으로 두되 **양방향으로** 단언한다 — 새 위반이 생겨도,
목록에 적힌 것이 고쳐졌는데 목록이 남아 있어도 실패한다. 한쪽만 보면 **이 목록이 조용히 낡는다.**

### P2-15-4 — 자식 테이블 셋의 FK 컬럼에 인덱스가 없다 (완료)

**벤치 행을 지우다가 드러났다.** 98만 행 `DELETE` 하나가 **24분을 넘겼다.**

```
child                 | fk_col      | has_index
----------------------+-------------+-----------
log_images            | log_id      |     0
work_log_comments     | log_id      |     0
work_log_images       | work_log_id |     0
work_log_translations | log_id      |     1
```

부모 행을 지울 때 PostgreSQL은 "이 행을 참조하는 자식이 있는가"를 확인한다. 인덱스가 없으면
**자식 테이블을 통째로 훑는다.** 삭제하는 행마다, 자식 테이블마다.

`work_log_images`는 살아 있는 행이 **0건인데 힙이 26MB**였다 — 방금 지운 33만 건의 죽은
튜플이 남아 있었고, 순차 스캔은 그 페이지를 전부 읽는다. `VACUUM`으로 잘라내려 했으나
**실행 중인 삭제가 잠금을 쥐고 있어 truncate가 거부됐다.**

> **이건 벤치마크만의 문제가 아니다.** `work_log_images.work_log_id`에 인덱스가 없다는 것은
> P2-15-1이 센 **행당 1쿼리가 매번 순차 스캔**이라는 뜻이다. 즉 쿼리 개수와 쿼리 비용이
> 같은 한 곳에서 만난다. `DELETE /api/work-logs/{logId}`도 같은 경로를 탄다.

#### 실측 — 조회는 893배, 삭제는 22배

로컬 DB(`work_logs` 100만, `work_log_images` 33.3만 = 실제 비율 1/3)에서 같은 문장을
인덱스 전후로 나란히 쟀다. 삭제는 **코퍼스를 건드리지 않으려고 측정용 부모 2,000건을
따로 만들어** 지웠다 — 자식이 없는 행이라 순수하게 FK 검사 비용만 남는다.

| 재는 것 | 인덱스 없음 | 있음 | |
|---|---|---|---|
| **이미지 조회 ×20** (목록 한 페이지분) | **1,964.8 ms** | **2.2 ms** | **893배** |
| **부모 2,000건 DELETE** | **103,139 ms** (행당 51.57ms) | **4,691 ms** (행당 2.35ms) | **22배** |
| 단건 조회가 읽은 버퍼 | 3,788 | 4 | |
| 계획 | Parallel Seq Scan (필터로 버린 행 111,111 ×3) | Index Scan | |

**목록 쪽이 훨씬 크다.** 삭제는 원래 이 항목이 발견된 계기였지만, 22배는 부모 테이블
순차 스캔 같은 다른 비용이 함께 들어 있어 희석된 값이다. 조회는 그렇지 않다 —
`WHERE work_log_id = ?` 하나뿐이라 인덱스 유무가 그대로 드러난다.

> **1,965ms는 페이지 하나를 그리는 데 드는 시간이다.** P2-15-1이 "행당 1쿼리"라고 셀 때
> 그 1쿼리의 값이 얼마인지는 세지 않았다. 쿼리 **개수**를 재는 측정이 쿼리 **비용**을
> 재는 측정을 대신할 수 없다던 자리에 실제 숫자가 들어왔다.

인덱스 크기는 **7.3MB**(테이블 30MB), 생성 시간 **0.96초**다.

#### 셋 중 하나는 인덱스가 아니라 삭제였다

`log_images`를 조사하다 **엔티티가 자기 파일 밖에서 참조 0건**인 것을 발견했다.

| 근거 | |
|---|---|
| 대체된 시점 | 2026-02-07 `b67134f`가 "사진 여러 장 저장을 위해" `work_log_images`를 새로 만들며 대체했다. **앞의 것을 지우지 않아 같은 개념의 테이블이 둘 남았다** |
| 참조 | `LogImage`를 쓰는 리포지토리도 서비스도 없다. `WorkLogImage`만 쓰인다 |
| 행 수 | 로컬 DB에 **0건** |
| 오타 | 컬럼명이 `imgae_id`(`image` 오타)다. 엔티티 필드 `imgaeId`가 그대로 내려온 것으로, **한 번도 쓰이지 않았다는 방증**이다 |

P0-2에서 지운 `ChatHistory`와 같은 형태다. **안 쓰는 테이블에 인덱스를 붙이면 다음 사람에게
쓰이는 것처럼 보인다** — 이 저장소가 계속 잡아 온 "선언과 실제의 불일치"를 하나 더 만드는 셈이라
인덱스 대신 삭제했다.

> **처음엔 이 테이블도 그냥 인덱스 대상이었다.** 세 줄짜리 작업으로 보였는데, 대상을 실제로
> 열어보고서야 하나가 다른 종류였다는 것이 나왔다.

`work_log_translations.log_id`에는 아무것도 만들지 않았다. `uk_log_lang UNIQUE (log_id,
language_code)`의 **선두 컬럼이 `log_id`라 FK 검사에 그대로 쓰인다** — 만들면 같은 일을 하는
인덱스가 둘이 된다.

#### 정리 도구가 만든 인덱스가 남아 있었다

측정하려고 DB를 열었더니 **네 자식 테이블 모두 `has_index = true`** 였다. 앞선 벤치마크
실행이 뒷정리용으로 만든 `cleanup_idx_*` 셋이 **지워지지 않고 남아 있었다**(실행이 중간에 끊겼다).

> **그대로 쟀다면 "인덱스 없음"을 인덱스 있는 상태에서 재고 아무 차이가 없다고 적었을 것이다.**
> 그리고 이건 아무도 알려주지 않는다 — `ddl-auto=validate`도 `SchemaValidationTest`도
> **인덱스는 보지 않는다.** P0-13-3이 "validate가 못 보는 것" 목록을 만든 이유가 여기서 한 번 더 나왔다.

`V3`가 이 셋을 `DROP INDEX IF EXISTS`로 걷어낸다.

#### 마이그레이션 (`V3__work_log_child_fk_indexes.sql`)

| 대상 | 조치 |
|---|---|
| `work_log_images.work_log_id` | `idx_work_log_images_work_log` 생성 |
| `work_log_comments.log_id` | `idx_work_log_comments_log` 생성 |
| `work_log_translations.log_id` | **없음** — `uk_log_lang`의 선두 컬럼 |
| `log_images` | **테이블 삭제** + `LogImage` 엔티티 삭제 |
| `cleanup_idx_*` 셋 | `DROP INDEX IF EXISTS` |

**`DROP TABLE`은 행이 있으면 실패하게 했다.** 로컬이 0건인 것은 확인했지만 이 마이그레이션은
내가 못 보는 환경에서도 돈다. 행이 남아 있으면 `RAISE EXCEPTION`으로 멈추고 "판단이 틀렸다"고
말한다 — 2b의 `ALTER ... USING`이 "행이 남아 있으면 `NOT NULL` 위반으로 실패해 실수로 임베딩을
날리지 못한다"고 한 것과 같은 장치다.

`CONCURRENTLY`는 쓰지 않았다. **Flyway가 마이그레이션을 트랜잭션 안에서 돌리는데
`CREATE INDEX CONCURRENTLY`는 트랜잭션 안에서 실행할 수 없다.** 두 테이블 모두 자식이라
작고(0.96초) 배포 중 짧은 쓰기 잠금은 감수할 수 있다. **`work_logs` 본체에 인덱스를 만들 때는
이 판단을 다시 해야 한다 — 100만 행이다.**

#### 벤치마크의 전제가 둘 바뀌었다

| | 전 | 후 |
|---|---|---|
| `CLEANUP_FK_INDEXES` | 지우기 전에 임시 인덱스 셋을 만들고 끝나면 없앴다 | **걷어냈다.** 스키마에 들어갔으므로 만들 것이 없다. `log_images` 항목은 두면 `relation does not exist`로 죽는다 |
| `bench_idx_work_log_images_log` | 이 테스트가 만드는 인덱스 | **뺐다.** V3와 같은 인덱스라 두면 같은 컬럼에 둘이 되고, "인덱스 없음" 열이 실제로는 있는 상태를 잰다 |

그 결과 **⑥의 두 열은 이제 같은 상태를 잰다.** 비슷하게 나오는 것이 고장이 아니라는 것을
주석에 적었다. 인덱스 유무의 차이는 위 실측이 대신한다.

### P2-15-5 — 규모별 지연시간 (측정 완료, 정리 미완)

`WorkLogListBenchmarkTest`가 10만 / 100만 건에서 여섯 쿼리를 **인덱스 없음 ↔ 있음**으로
나란히 잰다. 두 규모 모두 측정은 끝났고 **뒷정리(P2-15-4)에서 걸려 숫자를 아직 못 옮겼다.**

| # | 쿼리 | 왜 재는가 |
|---|---|---|
| ① | 구역 목록 1페이지 | `LIMIT 20`이 문제를 가려줄 것으로 예상 |
| ② | 그 COUNT | 가려지지 않는다 — MVCC라 전부 세야 한다 |
| ③ | 500페이지 | `OFFSET 10000`이 앞의 1만 행을 읽고 버린다 |
| ④ | 정렬 붙은 1페이지 | 정렬하려면 전부 읽어야 한다 |
| ⑤ | `LIKE %kw%` | 양쪽 와일드카드 → B-tree 불가. **인덱스로 안 변하는 것이 `pg_trgm`의 근거** |
| ⑥ | 이미지 조회 ×20 | P2-15-1이 센 N+1의 실제 시간 |

**분포는 측정 대상이 아니라 조건이다.** 두 곳을 의도적으로 고정했다.

1. **소유자** — 500명을 6구역에 나눠 `IN` 절에 84명이 들어간다(코퍼스 생성기와 같은 분포).
   여기를 3명으로 두면 필터가 1/3을 통과해 "인덱스가 있으나 없으나 비슷하다"가 나온다.
2. **검색어 빈도** — 1만 행에 하나만 심는다. 처음엔 모든 행에 같은 단어를 넣었는데,

   "`LIKE %kw%`는 빠르다"는 거짓 결론**이 나온다.

**다음 실행 전에 고칠 것**

| 항목 | 내용 |
|---|---|
| ~~뒷정리~~ | **해소됨** — P2-15-4가 FK 인덱스를 스키마(V3)에 넣었다. 부모 삭제가 행당 51.6ms → 2.35ms이므로 뒷정리가 측정보다 오래 걸리던 상태가 아니다. `cleanUp`의 임시 인덱스 장치도 함께 걷어냈다 |

### 로드맵 2-3의 진단과 대조

2-3이 지목한 다섯 지점 중 **쿼리 개수 측면에서** 확인된 것과 아닌 것.

| 2-3의 지적 | 지금까지의 실측 |
|---|---|
| `findByMemberIn`이 구역 사용자를 통째로 `IN`에 넣는다 | **맞다.** 다만 쿼리 **개수**로는 1이라 여기서는 크기가 안 보인다 → P2-15-5 |
| `Page<>`의 COUNT가 매 요청 나간다 | **맞다.** 고정 비용 4개 중 하나로 확인 |
| OFFSET 페이징 | **맞고, 그보다 앞에 정렬이 없다**(P2-15-3). 순서가 없으면 페이징 자체가 성립하지 않는다 |
| `ORDER BY created_at DESC` 인덱스 없음 | 목록 API는 **애초에 정렬을 걸지 않는다.** `/search`만 해당 |
| `LIKE %kw%` | → P2-15-5 |

> **2-3이 못 본 것이 둘이다** — 행당 1쿼리(P2-15-1)와 자식 FK 인덱스(P2-15-4).
> 둘 다 인덱스를 추가해도 줄지 않거나, 인덱스를 **다른 테이블에** 넣어야 하는 것들이다.
> 2-3이 `work_logs` 한 테이블만 보고 있었기 때문이다.

### P0-9 — 예외 처리 표준화 (완료)

`BusinessException` 하나만 처리하고 있어 **`@Valid` 검증 실패가 500으로 나갔다.**
클라이언트가 "내가 잘못 보낸 것"과 "서버가 고장난 것"을 구분할 수 없는 상태였다.

추가: `MethodArgumentNotValidException`, `ConstraintViolationException`,
`MethodArgumentTypeMismatchException`, `HttpMessageNotReadableException`,
`HttpRequestMethodNotSupportedException`, `AccessDeniedException`, `Exception`(캐치올).

**설계 판단**

- **응답 형태를 바꾸지 않았다.** `ErrorResponseDto`는 `status/message/timestamp` 세 필드이고
  `ErrorCode`의 `C001` 같은 코드는 응답에 없다. 넣으면 프론트엔드 계약이 바뀌므로
  예외 처리 보강과 별개의 결정으로 남긴다. 코드는 로그에만 남는다.
- **캐치올이 403을 500으로 바꾸는 함정이 있다.** `AccessDeniedException`은 `RuntimeException`이라
  `Exception` 핸들러가 삼킨다. 명시적 핸들러를 두어 막았고, **지우면 조용히 권한 오류가 서버 오류가 된다**는
  주석을 남겼다.
- **검증 실패 응답에 입력값을 넣지 않는다.** 필드명과 위반 사유만 보낸다.
  값을 에코하면 비밀번호 같은 입력이 응답과 로그에 남는다.
- **500 응답에 예외 메시지를 노출하지 않는다.** 파서 메시지에는 클래스명·패키지 구조가 들어 있다.
  스택 트레이스는 로그에만 남긴다.

### P0-10 — `SENTENCE_LOOKBACK` 실측 (완료, 값은 유지)

`SentenceLookbackMeasurementTest`로 탐색 거리를 스윕했다. 전문은 `SERVICE-SCALE-ASSUMPTIONS.md` 6-6.

**측정이 가설 하나를 뒤집었다.** "창을 넓히면 청크가 짧아진다"고 보고 어서션을 걸었는데 실패했다.
탐색이 뒤에서부터 훑어 **가장 가까운** 경계를 쓰기 때문에, 이미 경계를 찾은 절단은 창을 넓혀도
위치가 그대로다. 작업일지 문투에서 120과 400의 결과가 **완전히 동일**하다(448자, 401청크).
대가는 **강제 절단이 실제로 구제되는 경우에만** 붙는다(긴 서술 120→200에서 평균 8% 감소).

| 발견 | 내용 |
|---|---|
| 필요한 거리 = **평균 문장 길이 × 약 1.7** | 35자→80, 70자→120, 140자→200에서 0% |
| **120은 "평균 문장 길이 70자" 가정값이다** | 감이 아니었지만, 근거는 값이 아니라 **가정**에 있었다 |
| **STT 텍스트에서는 무의미** | 종결 부호가 없어 어떤 값이든 100% 강제 절단. 이 프로젝트에 STT 경로가 있다 |

> **값은 바꾸지 않았다.** 바뀐 것은 근거다. 남은 실측은 `SENTENCE_LOOKBACK`이 아니라
> **실제 작업일지의 평균 문장 길이**이며, 100자를 넘으면 120은 부족하다.

`ddl-auto=update`가 스키마를 만드는 구조라 애초에 파일이 존재한 적이 없다.

**2026-08-05에 한 것**

| 항목 | 내용 |
|---|---|
| `docs/db/postgresql-schema.sql` | 실제 DB에서 뽑은 덤프(24테이블). **생성물이며 소스 오브 트루스가 아니다** |
| `SchemaValidationTest` | `ddl-auto=validate`로 엔티티↔DB 일치를 검증. **통과했다** |
| `schema.sql` stale 경고 헤더 | 열어보면 알 수 있게 됐다. 이전에는 파일 안에 아무 표시가 없었다 |

> **drift가 없는 이유는 보호 장치가 아니라 우연이다.** DB가 **2026-08-04 23:24 생성**,
> 즉 PostgreSQL 이관 때 통째로 새로 만들어져 현재 엔티티와 일치할 수밖에 없었다.
> 앞으로 엔티티에서 컬럼을 지우거나 타입을 바꾸면 `update`는 반영하지 않으므로 그때부터 어긋난다.

**`validate`가 보지 않는 것** — 테이블/컬럼 존재와 타입만 본다.
**nullability, 기본값, 인덱스, FK 제약, 그리고 DB에만 있고 엔티티에 없는 잉여 항목은 잡지 못한다.**
실제로 `bench_leave_balance`(`LeaveBalanceConcurrencyTest`가 만드는 벤치마크 테이블)가 잉여로 남아 있으나
검증을 통과한다.

#### P0-13-4 상세 — 시드 수단 복구 (완료)

수단을 **둘**로 나눴다. 하나로는 안 되는 것이 분명했기 때문이다.

| 수단 | 무엇 | 목적 |
|---|---|---|
| `db/seed/R__seed_sample.sql` | 손으로 쓴 표본 (사용자 4 / 작업일지 16 / 번역본 7 / 근태 16 / 휴가 3 / 캘린더 6 / 안전교육 5) | **화면을 돌려보기 위한 것.** 읽을 수 있고 앞뒤가 맞는 데이터 |
| `CorpusSeedGeneratorTest` | 템플릿 조합으로 수천~수만 건 생성 | **측정을 위한 것.** 작업일지 16건으로는 ANN recall을 잴 수 없다 |

**운영에 섞이지 않게 하는 방식이 이전과 반대다.** 시드를 기본 Flyway location(`db/migration`)이 아니라
`db/seed`에 두고, `application-seed.properties`가 `spring.flyway.locations`에 그 경로를 **추가할 때만**
보이게 했다. 프로파일을 안 켜면 Flyway가 디렉터리를 **스캔조차 하지 않는다.**

> 삭제한 `data.sql`은 구조가 반대였다 — 기본 경로에 놓여 있고 스위치 하나(`spring.sql.init.mode`)로만
> 막혀 있어서, 그 스위치를 켜는 순간 어디서든 돌 수 있는 상태였다.

**시드가 원본만 넣는 이유** — `document_chunks`는 임베딩이 있어야 채워지고 그것은 `IndexingService`의
일이다. 손으로 `vector(384)` 리터럴을 적는 것은 가능하지도, 의미가 있지도 않다. 다만 색인 배치는
기본이 매일 03:00이라 시드를 넣고 앱을 띄워도 **다음 새벽까지 RAG가 빈손**이다. 그래서
`SeedIndexingRunner`(`local` 프로파일 + `rag.indexing.on-startup=true`)로 기동 직후 한 번 돌릴 수 있게 했다.

**잊으면 조용히 잘못되는 것 — 시퀀스**

PK를 명시해 넣었는데 `GENERATED BY DEFAULT AS IDENTITY`는 명시된 값을 **받아주기만 하고 시퀀스를 올리지 않는다.**
빠뜨리면 시드는 성공하고 화면도 잘 뜨는데 **앱이 처음 저장하는 순간** 같은 PK를 발급받아 터진다.
원인이 시드에 있다는 것을 그 시점에 떠올리기 어렵다. 9절의 `setval`이 그것이고,
`SeedDataTest`가 "PK를 명시한 표에 `setval`이 있는가"를 빌드에서 검사한다.

`attendance`만 방식이 다르다 — IDENTITY가 아니라 `attendance_seq`(`INCREMENT BY 50`)를 쓰므로
Hibernate의 pooled 옵티마이저 구간을 피해 1000으로 올려둔다.

**검증 — 임시 컨테이너에서 실제로 적용했다** (P0-13-2와 같은 방식)

| 확인 | 결과 |
|---|---|
| V1+V2+시드 적용 (`ON_ERROR_STOP=1`) | ✅ 종료코드 0 — 컬럼명·문법 이상 없음 |
| 시퀀스 보정 | ✅ 새 작업일지가 `log_id=17`을 받음 (보정 없으면 1을 받아 충돌) |
| 재실행 멱등성 | ✅ 2회차에도 행 수 불변, 앱이 넣은 행도 보존 |
| FK 무결성 | ✅ 고아 참조 0 |
| 휴가 승인 ↔ 근태 | ✅ APPROVED 건에 `VACATION` 근태가 짝으로 존재 |
| 생성기 2,000건 | ✅ 457ms, 재실행 시 총량 불변 |
| **실제 앱 기동 + 색인** | ✅ Flyway가 시드 적용 → 30청크 임베딩 / 6,836ms. 전문은 `SERVICE-SCALE-ASSUMPTIONS.md` 6-7 |

**시드를 고쳐도 이미 시드가 들어간 DB에는 반영되지 않는다.** 체크섬이 바뀌어 Flyway가 다시
실행하고 로그에 "Successfully applied 1 migration"까지 찍히지만, 모든 INSERT가
`ON CONFLICT DO NOTHING`이라 **기존 행은 그대로 두고 아무 일도 하지 않는다.**

이것은 결함이 아니라 의도다 — `DO UPDATE`로 바꾸면 앱을 띄울 때마다 시드가 사용자 데이터를
덮어쓴다. 보호받아야 하는 쪽은 앱이 만든 데이터다(실제로 앱이 넣은 `log_id=17`이 재실행에서
살아남는 것을 확인했다). 다만 그 사실이 어디에도 없어서 **고쳐놓고 왜 안 바뀌나 하게 되므로**,
초기화 절차를 시드 파일 헤더에 적었다. `document_chunks`는 FK가 없어 원본만 지우면 고아가
남으므로 함께 지우는 것까지 포함한다.

> **`SeedDataTest`는 DB를 건드리지 않는다.** 시드를 실제로 적용하는 테스트를 만들면
> `DB_PASSWORD`만 있으면 도는 테스트가 개발자 DB에 표본 데이터를 밀어 넣게 되고,
> CI에 DB를 붙이는 순간(P0-11) CI DB에도 들어간다. 대신 파일을 읽어 정적으로 검사한다 —
> **BCrypt 해시가 문서화된 비밀번호와 맞는가**(틀리면 로그인만 조용히 안 된다)와
> **`setval` 누락**만 본다. 문법·컬럼명은 못 잡으므로 그쪽은 위의 컨테이너 검증이 담당한다.

**표본을 눈으로 보고 잡은 생성기 결함 넷** — 코드가 도는 것과 쓸모 있는 데이터를 만드는 것은 다르다.

| 결함 | 왜 문제인가 |
|---|---|
| 제목은 "무인 도장설비 2호기", 본문은 "플라즈마 절단기 4호기" | `toTarget`이 **제목+본문을 함께 임베딩**한다. 한 청크에 다른 설비가 섞이면 그 벡터는 어느 쪽도 가리키지 않는다 |
| `"케이블을 교체했다 조치 후"` — 마침표 누락 | 청킹이 **종결 부호로 문장 경계를 찾는다.** 없으면 강제 절단 — 6-6이 STT에서 지적한 것과 같은 상황 |
| 본문 최대 334자 → 전부 1청크 | "문서당 최대 2청크" 제한과 `chunk_index >= 1` 경로가 한 번도 실행되지 않는다. 669~730자를 21.8% 섞어 해결 |
| `"측정값은 67.2으로"` 조사 오류 | 2,000건 **전부**에 같은 문구가 들어간다. 코퍼스 전체에 공통 흔적이 박힌다 |

**생성 코퍼스로 잴 수 있는 것과 없는 것**

작성일을 **2년(729일)에 걸쳐** 펼친다. 간격을 고정하면 기간이 건수에 따라 달라져
(2,000건이면 50일, 20,000건이면 500일) ADR-0007의 만료 기간 `N` 측정이 성립하지 않는다.

> **다만 이것은 "실데이터"가 아니다.** 문형이 여섯 개뿐인 슬롯 조합이라 실제 작업일지보다
> 어휘가 좁고 서로 더 비슷하다. 임베딩 공간에서 실제보다 조밀하게 뭉치면 최근접 이웃 사이의
> 거리 차가 작아져 **recall이 실제보다 낮게(보수적으로) 나오는 방향**으로 치우친다.
> 그래서 여기서 얻은 recall은 **하한선으로만** 읽어야 한다 — "HNSW를 켜도 되는가"의 판단에는
> 쓸 수 있어도 "recall이 몇 퍼센트인가"의 답으로 인용해서는 안 된다.

#### P0-13-3 상세 — `ddl-auto=update` → `validate` (완료)

`V2__baseline_existing_tables.sql`로 나머지 21개 테이블을 전부 옮기고 `ddl-auto`를 내렸다.
**이제 스키마 정의가 전부 SQL 파일에 있고, 엔티티와 어긋나면 기동이 실패한다.**

**손으로 옮기지 않았다.** Hibernate가 실제로 만든 DDL을 `pg_dump`로 뽑아 스크립트로 변환했다.
컬럼 하나만 어긋나도 `validate`가 터질 때까지 알 수 없으므로 사람이 옮길 일이 아니다.

| 형태에 대한 결정 | 이유 |
|---|---|
| PK·UNIQUE·CHECK·IDENTITY를 `CREATE TABLE` 안으로 인라인 | `IF NOT EXISTS` 하나로 멱등해진다. 분리해두면 문장마다 멱등 처리가 따로 필요하다 |
| FK만 맨 뒤에 분리 | 인라인이면 참조 대상이 먼저 생성돼야 해서 테이블 생성 순서를 맞춰야 한다 |
| CHECK을 `IN (...)` 형태로 변환 | `pg_dump`가 뱉는 `= ANY ((ARRAY[...])::text[])`를 그대로 다시 넣으면 **PostgreSQL이 다른 형태로 재정규화**해 향후 덤프 diff에 노이즈가 된다. `IN` 형태는 Hibernate가 만든 것과 정확히 같은 형태로 저장된다(실측 확인) |

**작업 중 잡은 것 — `IDENTITY` 17개가 통째로 빠질 뻔했다.**
`pg_dump`는 IDENTITY를 `CREATE TABLE` 안이 아니라 **별도 `ALTER TABLE`로** 내보낸다.
첫 변환에서 이 문장을 파싱하지 않아 17개 PK의 자동 생성이 사라졌고, **새 환경에서만 INSERT가 실패하는**
형태로 숨을 뻔했다. 기존 DB에는 이미 있으니 아무 증상이 없었을 것이다.

**검증 — 3단계로 봤다.**

| 단계 | 방법 | 결과 |
|---|---|---|
| 1. 구조 대조 | 별도 컨테이너에 V1+V2 적용 후 실제 DB와 대조 | 컬럼 144 / 제약 59 / 인덱스 32 / 시퀀스 19 **전부 일치** |
| 2. 빈 DB 기동 경로 | 빈 DB로 갈아끼우고 `SchemaValidationTest` 실행 | Flyway가 23테이블 생성 → `validate` 통과 |
| 3. 실제 앱 기동 | `DocKinSpringApplicationTests.contextLoads()` | **통과** — `validate`로 전체 컨텍스트가 뜬다 |

**함께 고친 것** — `FlywayMigrationTest`가 "최신 버전은 1"을 박아두고 있어 V2 추가로 깨졌다.
버전 번호를 박으면 마이그레이션을 추가할 때마다 기대값만 고치게 되므로,
**클래스패스에 있는 것이 전부 성공으로 적용됐는가**로 바꿨다.

> **앞으로 달라지는 것:** 엔티티에 필드를 추가하면 `V3__*.sql`도 함께 써야 한다.
> 빠뜨리면 기동이 실패한다. 그게 비용이 아니라 목적이다 — 스키마 변경이 리뷰 대상이 되고,
> `update`가 반영하지 못하던 컬럼 삭제·타입 변경이 실제로 적용된다.

#### `data.sql` — 세 겹으로 죽어 있었다 (삭제)

`src/main/resources/data.sql`(28줄)은 사용자 2명·장비 2대·작업일지 5건의 시드 데이터였다.
**세 가지가 동시에 틀려 있었다.**

| # | 문제 |
|---|---|
| 1 | **실행되지 않았다** — `spring.sql.init.mode=never`이고 `data-locations`는 주석 처리 상태 |
| 2 | **MySQL 문법** — `USE Dockin`, `SET FOREIGN_KEY_CHECKS`, `REPLACE INTO`, `INSERT IGNORE`, 불리언 `1`/`0` |
| 3 | **없는 컬럼을 참조** — `attendance (…, role, …)`에 INSERT하는데 **`attendance.role`은 존재하지 않는다**(실제 DB 확인) |

즉 문법을 고쳐도 실패한다. 실행된 적이 없어서 아무도 몰랐다.

> **시드 데이터 자체는 지금 오히려 필요하다.** `document_chunks`가 **0건**이라
> ADR-0007의 만료 기간 `N` 측정도, ADR-0006이 남긴 **ANN recall 측정**도 실데이터가 없어 못 한다.
> 다만 `data.sql`을 되살리는 것은 답이 아니다 — **Flyway repeatable 마이그레이션(`R__seed.sql`)이나
> 테스트 픽스처**가 맞는 자리이며, 운영 DB에 섞이지 않도록 프로파일로 분리해야 한다(P0-13-4).

#### P0-13-2 상세 — 같은 일을 하는 SQL이 셋이었다

Flyway V1을 넣으면서 기존 스크립트와 역할이 겹쳤다. **실제로 도는 것은 V1 하나뿐**인데
나머지 둘이 남아 있어 "어느 것을 실행해야 하는가"가 불분명했다.

| 파일 | 처리 | 근거 |
|---|---|---|
| `db/init/01-pgvector.sql` | **삭제** + compose 마운트 제거 | 확장 등록만 했고 V1이 대체한다. 데이터 디렉터리가 빌 때만 돌아 기존 볼륨엔 적용되지 않았고, 그 시점엔 테이블이 없어 인덱스는 어차피 못 만들었다 |
| `docs/migration/2b-pgvector.sql` | **삭제** | `bytea → vector` 일회성 이관. 그 상태의 DB가 더는 없다. 내용은 ADR-0006 8-1에 전부 있다 |
| `docs/migration/2b-hnsw-index.sql` | **`docs/db/rebuild-hnsw-index.sql`로 이동 + 용도 재정의** | 마이그레이션이 아니라 **운영 절차**다. V1은 인덱스를 만들 뿐, 대량 데이터에서 재생성할 때 필요한 세션 설정(`maintenance_work_mem`)은 주지 못한다 |

**실측 주석을 잃지 않았다.** 삭제한 두 파일의 근거(빌드 4분 56초→3분 09초, `/dev/shm` 64MB 문제,
인덱스 195MB, `USING NULL` 캐스팅)는 **이미 ADR-0006 8-1/8-2에 기록되어 있음을 확인**한 뒤 지웠다.

**검증 — 별도 임시 컨테이너로 실제로 확인했다.** `db/init` 없이 빈 DB에 V1만 적용해:
