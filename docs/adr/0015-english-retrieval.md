# ADR-0015: 영어 검색 — 문서를 영어로 번역해 색인할 것인가, 질문을 한국어로 번역해 물을 것인가

- 상태: **제안(초안).** 2026-11-27. 숫자는 기존 측정에서 옮긴 것이고 이 ADR의 실험은 아직 돌리지 않았다
- 대상 코드: `rag/service/IndexingService`(`indexTranslations`), `rag/service/RetrievalService`(`search`·`cap`), `ai/service/FastApiService`(`saveTranslateLog`), `rag/model/SourceType`, 측정 `SearchQualityEvalTest`·`CorpusSeedGeneratorTest`
- 관련 문서: ADR-0006(벡터 검색, 12절 교차언어), ADR-0008(번역 서버), ADR-0013 2단계 2, `docs/SLO.md` 7-1·10-2, `docs/SEARCH-QUALITY-EVAL-PLAN.md`(E2), `docs/WORK-BACKLOG.md` P2-8-2·P2-8-3
- 관련 이슈: #170(평가셋), #189(영어 ANN 손실), #219(정답 라벨), #172(HNSW 메모리)
- 작성 목적: SLO 7-1에서 영어가 B 목표에서 가장 멀다. SLO 10-2와 ADR-0013 2단계 2는 다음 수로 **영어 번역본 색인**을 적어 두었다. 그런데 같은 문제를 **질문 번역**으로도 풀 수 있고, 그쪽이 훨씬 싸다. 둘 중 무엇을, 어떤 측정으로 고를지 정한다.

---

## 1. 지금 어디에 있나

### 1-1. 영어가 얼마나 먼가 (E1, 2026-11-27, `ann-decided`)

| 언어 | 용어형 Hit@5 | 의미형 Hit@5 | P@5 |
|---|---|---|---|
| ko | 1.00 | 0.44 | 0.52 |
| en | **0.34** | **0.20** | **0.11** |
| vi | 0.82 | 0.72 | 0.49 |

- 목표(SLO 7-1 B)는 용어형 ≥ 0.90, 의미형 ≥ 0.80, P@5 ≥ 0.60, 언어 간 격차 ≤ 10%p다. 영어는 세 칸 모두 가장 멀고 격차는 52~66%p다.
- 정답 라벨에 버그가 있다(#219). 파일럿을 다시 세면 영어는 거의 그대로였다(의미형 0.27 → 0.27). **영어가 약하다는 결론은 라벨과 무관하다.**
- 영어에는 ANN 손실도 따로 있다(#189, 정확 검색 대비 평균 −0.08). 이 ADR의 범위는 아니다.

### 1-2. 영어는 어떻게 틀리나 — 실패 분류 (파일럿 30문항)

파일럿 영어 의미형 실패 11건을 상위 5개의 슬롯으로 나눴다(분류 방법은 #219와 같다 — 일지 본문을 다시 만들어 사건별 슬롯을 되읽었다).

| 분류 | 건수 | 예 |
|---|---|---|
| **증상·원인은 맞고 설비가 틀림** | **5** | "oil leaked from the crane cylinder" → 누유 일지는 가져오는데 크레인이 아니다 |
| 설비는 맞고 증상·원인이 틀림 | 4 | "conveyor was shaking" → 컨베이어는 맞는데 진동이 아니다 |
| 둘 다 틀림 | 2 | "forklift wouldn't start" |

한국어는 반대로 "설비는 맞고 증상이 틀림"이 가장 많았다. **영어의 첫 번째 문제는 설비 이름이 한국어 설비명으로 이어지지 않는 것이다.** crane ↔ 겐트리 크레인, welder ↔ CO2 용접기, painting robot ↔ 무인 도장설비. 이건 임베딩이 언어를 건너는 데서 생기는 손실이라, 질문과 문서를 같은 언어로 맞추는 쪽이 정면으로 겨냥한다.

### 1-3. 베트남어는 무엇으로 올라왔나 (E2)

| | ko | en | vi |
|---|---|---|---|
| 번역본 없음 → 있음 | +0.00 | +0.01 | **+0.68** (0.09 → 0.77) |

베트남어는 번역본 색인이 거의 전부다. 다만 이 숫자를 영어에 그대로 옮기기 전에 알아야 할 것이 셋 있다.

1. **측정 코퍼스의 번역본은 기계번역이 아니다.** `CorpusSeedGeneratorTest`는 베트남어 일지를 슬롯 번역 사전(`*_VI`)으로 조립한다. 평가 질문의 베트남어도 같은 모델이 옮겼다. 그래서 **질문과 번역본이 같은 단어를 쓰고**, 그만큼 점수가 오른다(평가셋 README `[추측]`).
2. **운영의 번역본은 요청이 있을 때만 생긴다.** `FastApiService.saveTranslateLog`는 사용자가 일지 번역을 누를 때 번역하고 `work_log_translations`에 남긴다(하루 50건 한도). 측정 코퍼스는 일지의 30%에 번역본을 깔아 두었다. **운영에서 몇 %의 일지에 번역본이 생길지는 모른다.**
3. **정답이 질문당 십여~수백 건이다.** 30%만 번역돼 있어도 정답 중 몇 건은 번역본이 있어 Hit@5가 쉽게 오른다. 정답이 한두 건인 실데이터에서는 덮인 비율이 그대로 상한이 된다.

## 2. 선택지

| | A. 문서 번역 색인 | B. 질문 번역 | C. 둘 다 |
|---|---|---|---|
| 무엇을 | 일지를 ko→en으로 번역해 `WORK_LOG_TRANSLATION`(language_code=en)으로 색인 | 영어 질문을 en→ko로 번역해 한국어로 검색 | A + B |
| 덮는 범위 | **번역된 일지만.** 전부 번역하려면 배치가 필요하다 | **모든 일지.** 원문을 검색한다 | 전부 |
| 번역 호출 | 일지당 1회(제목+본문). 하루 약 4,000건(SERVICE-SCALE 1인 1일 1건) | 질문당 1회. 챗봇 한도 20/일/인이라 상한이 정해져 있다 | 둘의 합 |
| 저장·색인 | 청크 **+100%**(원문만큼 더). HNSW도 같이 커진다 | **0** | +100% |
| 검색 지연 | 그대로 | **+번역 1회.** ko→en HTTP 73ms(밤 6, m7i.2xlarge, 짧은 문장) — en→ko는 잰 적 없다 | +번역 1회 |
| 번역 오류의 영향 | 번역이 틀린 일지는 영어로 못 찾지만 원문 경로는 남는다 | **질문이 틀리게 번역되면 그 질문 전체가 틀린다** | 서로 보완 |
| 결과 중복 | 원문·vi·en 세 벌이 top-5를 나눠 먹는다(P2-8-2) — **먼저 고쳐야 한다** | 없음 | A와 같음 |
| 키워드·하이브리드와 | 영어 키워드가 영어 번역본에 걸린다 | 번역된 한국어 키워드가 원문에 걸린다 — #210 하이브리드가 그대로 쓰인다 | |
| 모델 | 있음 — opus-mt ko→en(ADR-0008, 밤 6~10) | **en→ko 모델이 번역 서버에 있는지 확인 필요** `[확인 필요]`. NLLB-600M은 방향 무관 | |

### 2-1. A의 비용 — 계산

| 항목 | 값 | 근거 |
|---|---|---|
| 하루 번역량 | 약 4,000건 | SERVICE-SCALE 1인 1일 1건 |
| 번역 처리량 | opus-mt ko→en 한 대 30 req/s, 마이크로배칭 60~96 req/s | 밤 6·9·10. **채팅 길이(9~28자)로 잰 값이다.** 일지는 수백 자라 건당 시간이 몇 배 늘어난다 `[추측]` |
| 하루 번역 시간 | 30 req/s면 약 2분 → 일지 길이를 감안해도 **야간 배치 수십 분 안** `[추측]` | 위 둘 |
| 청크 증가 | 영업일당 +8,000~12,000청크 (원문과 같은 양) | #172 |
| HNSW 메모리 | DB 1G에서 열화 지점까지 **2~3개월 → 약 1~1.5개월** | #172 외삽을 절반으로 `[추측]` |
| 임베딩 | 원문과 같은 양만큼 더. 100만 청크 약 3.3시간(CPU) — 처리량은 병목이 아니다 | SERVICE-SCALE 6절 |

**A의 진짜 비용은 번역 서버가 아니라 #172다.** 벡터가 두 배가 되면 DB 메모리 문제가 두 배 빨리 온다. 베트남어까지 전부 번역하면 세 배다.

| 항목 | 값 | 근거 |
|---|---|---|
| 번역량 | 질문 수만큼. 사용자당 하루 최대 20 | `ai.quota.daily.chatbot=20` |
| 지연 | +수십~수백 ms. 자체 호스팅 LLM 생성이 p95 10~39초라(#202) 상대적으로 작다 | 밤 6, ADR-0013 7절 |
| 저장 | 0 | |
| 실패 시 | 번역 서버가 죽으면 원래 영어 질문으로 검색한다 — 지금과 같은 품질로 떨어질 뿐 | |

## 3. 결정 (제안)

### D1. 먼저 B를 잰다. A는 B로 모자랄 때만 한다

- 비용 차이가 크다. B는 저장 0이고 코드 변경이 검색 앞 한 단계다. A는 저장 2배, 배치, 중복 제거, #172 앞당김을 같이 가져온다.
- 1-2의 실패 모양(설비명이 안 이어짐)은 B가 정면으로 푼다. 질문이 한국어가 되면 한국어 용어형처럼 동작할 것으로 본다 — 한국어 용어형은 Hit@5 1.00이다 `[추측]`.
- B가 약할 곳도 안다: 현장 말투 영어("keeps going up and down")를 번역기가 코퍼스 용어("출력이 불안정했다")로 옮기지 못하면 한국어 의미형(0.44)의 문제를 그대로 물려받는다. 그때 A와 비교할 근거가 생긴다.

### D2. A를 하게 되면 — 범위와 선행 조건

1. **선행: 결과 중복 제거(P2-8-2).** `cap`의 키를 `sourceType:sourceId`에서 **원본 일지 id**로 바꾼다. 하네스는 이미 일지 단위로 묶어 세므로 지금 숫자에는 이 문제가 안 보인다 — **운영 top-5에서만 생긴다.** 번역본이 세 벌이 되면 근거 5개 중 2~3개가 같은 일지일 수 있다.
2. **전부 번역(배치)인가, 요청 시 번역인가.** 요청 시 번역만으로는 덮는 비율이 정해지지 않는다(1-3의 2). 영어 사용자를 위해서라면 **승인된 일지(`APPROVED`, ADR-0012)만 배치로 번역**하는 것이 범위를 줄이는 안이다 — 근로자 검색에 나오는 것도 승인분뿐이다.
3. **#172와 같이 정한다.** 보존 기간 N, DB 메모리, 오래된 일지 색인 제외 중 무엇으로 두 배 늘어난 벡터를 받을지.

### D3. 측정 — E7

평가셋 E1(120문항 × 3언어)을 그대로 쓴다. **#219(라벨 수정)를 먼저 머지한다** — 고친 라벨로 기준선을 다시 낸 뒤 비교한다.

| 방식 | 내용 | 답하는 것 |
|---|---|---|
| `ann-decided` | 기준선(E1) | |
| `qtrans` | 영어 질문을 en→ko 번역 후 `ann-decided` | B의 효과 |
| `qtrans-hybrid` | `qtrans` + #210 하이브리드 | 번역된 한국어 키워드가 얼마나 더 주나 |
| `en-index-100` | 영어 번역본을 일지 100%에 색인 | A의 상한 |
| `en-index-30` | 영어 번역본을 일지 30%에만(베트남어와 같은 조건) | 덮는 비율이 결과를 얼마나 정하나 |
| `vi-qtrans` | 베트남어 질문을 vi→ko 번역 후 검색 | 베트남어도 B로 대체할 수 있나 — 되면 vi 번역본 색인을 다시 볼 근거 |

**측정 코퍼스의 영어 번역본은 슬롯 사전이 아니라 실제 번역 모델(opus-mt ko→en)로 만든다.** 베트남어처럼 슬롯 사전으로 조립하면 질문과 번역본이 같은 단어를 쓰게 되어 A가 부풀려진다(1-3의 1). 운영과 같은 파이프라인이어야 운영에서 얻을 것을 잴 수 있다.

- 코퍼스 2만 건 번역: 한 대 30 req/s 기준 수십 분 `[추측]`. GPU 측정 인스턴스에 번역 서버를 함께 띄운다.
- 질문 번역도 같은 서버로. 번역된 질문은 TSV로 남겨 **틀린 번역 때문에 틀린 질문**을 따로 센다.
- 통제군: 한국어 행은 모든 방식에서 같아야 한다(`en-index-*`는 한국어 질문을 바꾸지 않는다). 다르면 색인 조건이 어긋난 것이다.
- 비교와 판정은 SLO 7-1 A(같은 질문 짝지은 차이, 칸별 구간)를 따른다.

### D4. 판정

| 결과 | 결정 |
|---|---|
| `qtrans`가 영어를 B 목표 근처(용어형 ≥ 0.80)까지 올리고 격차가 크게 준다 | **B로 간다.** A는 하지 않는다. SLO 10-2를 "질문 번역"으로 고친다 |
| `qtrans`가 용어형은 올리지만 의미형이 그대로다 | B를 넣고, 의미형은 하이브리드·재순위(ADR-0013 2단계 3·4)와 함께 본다. A는 `en-index-100`이 의미형에서 `qtrans`보다 확실히 나을 때만 |
| `qtrans`가 거의 안 오른다(번역 오류가 많다) | A를 D2의 선행 조건과 함께 진행한다 |
| `vi-qtrans`가 vi 번역본 색인과 비슷하다 | 베트남어 번역본 색인을 끌지 따로 ADR로 — 저장 1/3을 돌려받는다 |

## 4. 하지 않는 것

- **임베딩 모델 교체.** 더 큰 다국어 모델(bge-m3 등)은 언어를 건너는 손실을 줄일 수 있지만, 차원이 바뀌어 전부 재색인이고 이 하드웨어에서 색인 처리량이 안 나온다(ADR-0006 4절). 품질 기준선과 B·A 비교가 끝난 뒤의 문제다.
- **영어 전용 키워드 분석기.** 하이브리드는 한국어 원문 위에서 돈다. B면 필요 없다.
- **LLM 질의 재작성으로 번역 대체.** 번역과 재작성(ADR-0013 2단계 5)을 한 호출로 묶을 수는 있지만, 자체 호스팅 LLM 한 번이 수 초다(#202). 번역 서버(수십 ms)로 먼저 잰다.

## 5. 아직 모르는 것

- 영어가 실제로 필요한 언어인가. SLO 7-1은 필수로 두었지만, 현장 외국인 근로자가 영어를 쓰는 비율은 확인 전이다 `[현장 확인 필요]`. 영어 사용자가 거의 없으면 이 ADR 전체의 우선순위가 내려간다.
- 번역 서버에 en→ko, vi→ko 모델이 있는가, 그리고 현장 말투 질문을 얼마나 옮기는가.
- 일지 길이(수백 자)에서 opus-mt 처리량. 측정값은 채팅 길이뿐이다.
- 운영에서 요청 시 번역이 일지의 몇 %를 덮는가 — 파일럿에서 `work_log_translations` 행 수 / 일지 수로 본다.
