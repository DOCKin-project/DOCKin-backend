# ADR-0012: 승인된 작업일지만 RAG 근거로 공유한다 — 범위는 앱의 권한(같은 구역)을 넘지 않는다

- 상태: **결정.** 2026-11-15(사용자). 코드는 `feat/rag-area-sharing`. 이슈 #174
- 대상 코드: `rag/service/IndexingService`(`toTarget`의 `Visibility.OWNER` 고정), `rag/service/ChunkIndexWriter`(해시가 같으면 건너뜀), `rag/repository/NearestChunkJdbcRepository`·`DocumentChunkRepository`(선필터), `rag/model/Visibility`, `worklog/model/WorkLog`(`approve`·`reject`·`resetReview`), `worklog/service/WorkLogReviewService`, `worklog/service/WorkLogsService.requireVisible`
- 관련 문서: ADR-0006 6절(선필터)·8-4(선택도 스윕), ADR-0007(보존), `docs/SEARCH-QUALITY-EVAL-PLAN.md` E6, `docs/PORTFOLIO-ROADMAP.md` 8-1·8-2
- 작성 목적: ADR-0006은 **남의 작업일지가 새지 않게** 하는 데 집중했고, **무엇을 공유해야 하는지**는 정하지 않았다. 그 결과 메인 기능이 관리자에게만 성립했다. 공유 대상(승인된 일지), 공유 범위(같은 구역), 상태 변화를 청크에 반영하는 방법을 정한다.

---

## 1. 무엇이 문제였나

작업일지와 번역본 청크는 전부 `Visibility.OWNER`로 색인된다. `PUBLIC`은 안전교육과 체크리스트뿐이다.
선필터는 의도대로 동작했고, 그래서 **근로자는 RAG 챗봇으로 자기가 쓴 일지만 검색한다.**

| 누가 | 챗봇이 근거로 쓰는 작업일지 |
|---|---|
| ADMIN | 전부 |
| 근로자 | 자기가 쓴 것만. 시드 기준 소유자 500명이라 약 0.2%(2만 건 중 40건 남짓) |

로드맵 8-1이 메인 기능으로 내세운 문장은 "베트남어로 물어도 **한국어 작업일지에서** 답을 찾아준다"이다.
베트남어 근로자의 자기 일지는 대개 자기가 쓴 것이므로, 이 문장은 남의 한국어 일지를 볼 수 있는 관리자에게만 참이었다.

### 확인해 보니 RAG가 앱보다 엄격했다

앱의 작업일지 화면은 **같은 구역의 일지를 상태와 관계없이** 근로자에게 보여준다.

| 경로 | 범위 |
|---|---|
| 목록 `GET /api/work-logs` (`findByArea`) | 같은 구역, 모든 상태(`status` 파라미터로 거를 수 있음) |
| 키워드 검색 `searchByKeyword` | 같은 구역 |
| 다른 작업자 일지 `readOtherWorklog` | 같은 구역이면 허용 |
| 상세·번역 `requireVisible` | 다른 구역이면 403 |
| **RAG 챗봇** | **본인만** |

즉 "남의 일지를 근로자에게 보이면 안 된다"는 제약은 이 서비스에 원래 없었다. RAG만 따로 더 좁았다.

## 2. 결정

> **근로자의 RAG 근거 = 본인 일지 전부 + 같은 구역의 `APPROVED` 일지.** 관리자는 그대로 전부.

두 부분으로 나뉜다.

### 2-1. 무엇을 — `APPROVED`만

앱 화면은 같은 구역의 미승인 일지도 보여주지만, RAG 근거로는 승인된 것만 쓴다.

- **화면과 근거는 무게가 다르다.** 화면의 일지는 "누가 쓴 기록"으로 읽히지만, 챗봇 답변에 녹은 내용은 "회사가 아는 사실"로 읽힌다. 반려될 일지(틀린 조치, 잘못 적은 원인)가 답변의 근거가 되면 틀린 정비 절차가 다른 근로자에게 사실처럼 전달된다.
- **검토가 관문이 된다.** `review_status`(V8)가 이미 있고, 반려 → 고침 → 재승인 흐름이 동작한다. 공유를 위한 새 절차를 만들지 않는다.
- **본인 일지는 상태와 무관하게 본다.** 지금과 같다. 자기가 쓴 미승인 일지를 자기 챗봇이 못 찾을 이유는 없다.

### 2-2. 어디까지 — 같은 구역 (앱의 권한을 넘지 않는다)

검토한 범위는 둘이었다.

| 안 | 내용 | 판단 |
|---|---|---|
| A. 승인 일지 **전체 공개** | `APPROVED`면 `PUBLIC` | **채택하지 않는다** |
| B. 승인 일지 **같은 구역 공개** | `APPROVED`면 작성자 구역에 공개 | **채택** |

A를 버린 이유:

1. **RAG가 원천 시스템의 권한을 넘으면 안 된다.** 검색·RAG의 권한은 원본 시스템의 권한을 그대로 따르는 것이 원칙이다. 넘으면 앱 화면에서는 403인 일지의 내용을 챗봇에게 물어 꺼낼 수 있다. ADR-0006 6절이 막으려던 유출이 정책 차원에서 다시 생긴다.
2. **출처를 누르면 403이 난다.** 챗봇이 다른 구역 일지를 근거로 인용하면, 근로자가 출처를 눌렀을 때 `requireVisible`이 403을 낸다. 답변과 화면이 서로 다른 권한 모델을 쓰고 있다는 것이 사용자에게 드러난다.
3. **넓히는 것은 나중에 할 수 있고, 좁히는 것은 어렵다.** 한 번 전체에 공개된 내용은 회수할 수 없다.

다른 구역의 지식이 필요하다는 근거(예: 같은 설비가 여러 구역에 있다)가 생기면, **앱의 권한을 먼저 넓히고 RAG가 따라간다.** 순서를 거꾸로 하지 않는다.

## 3. 상태 변화를 청크에 반영한다 — 배치를 기다리지 않는다

### 지금 구조로는 반영되지 않는다

- 색인은 매일 03:00 배치다(`rag.indexing.cron`).
- `ChunkIndexWriter`는 본문 해시가 같으면 그 청크를 **건너뛴다.** 승인·반려는 본문을 바꾸지 않으므로, 배치가 돌아도 `visibility`가 바뀌지 않는다.

### 반영이 늦으면 생기는 것

| 사건 | 늦으면 |
|---|---|
| 승인 | 다음 03:00까지 공유되지 않는다. 불편하지만 안전하다 |
| **승인된 일지를 작성자가 수정** (`resetReview` → `PENDING`) | **검토 안 된 새 내용이 최대 하루 동안 같은 구역에 공개된다.** 2-1의 관문이 뚫린다 |

수정 후 재색인은 해시가 바뀌므로 배치에서 처리되지만, 그때까지 옛 청크가 `AREA` 공개 상태로 남는다. 새 본문이 색인될 때도 공개 여부를 상태로 다시 계산해야 한다.

### 그래서 두 겹으로 반영한다

1. **즉시 — 상태가 바뀌는 트랜잭션 안에서 메타데이터만 UPDATE.**
   `approve` / `reject` / `resetReview`가 일어나는 같은 트랜잭션에서 그 일지와 번역본의 청크에 `UPDATE document_chunks SET visibility = …, area = …`를 건다.
   임베딩은 다시 계산하지 않는다. 행 수가 일지당 수 개라 비용이 작다.
   **좁히는 방향(`resetReview`·`reject`)은 반드시 같은 트랜잭션이다.** 커밋 뒤 이벤트로 미루면 그 사이 창이 생긴다.
2. **배치 — 해시가 같아도 메타데이터는 맞춘다.**
   아직 청크가 없는 일지(오늘 쓰고 오늘 승인된 것)는 1이 갱신할 행이 없다. 03:00 배치의 `toTarget`이 상태로 공개 범위를 계산하고, `ChunkIndexWriter`는 해시가 같아도 `visibility`·`area`·`owner_user_id`가 다르면 UPDATE한다. 1이 어떤 이유로 빠졌을 때의 보정도 겸한다.

## 4. 스키마와 쿼리

| 변경 | 내용 |
|---|---|
| `Visibility` | `AREA` 추가. 작업일지 청크는 `OWNER`(미승인·반려) 또는 `AREA`(승인) |
| `document_chunks.area` | 새 컬럼(nullable). `AREA`일 때 작성자의 구역. CHECK에 `visibility`가 `AREA`면 `area`가 NOT NULL |
| 번역본 청크 | 원본 일지의 상태·구역을 따른다. 번역본만 따로 공개되지 않는다 |
| 선필터 | 지금의 `PUBLIC` / `OWNER AND owner_user_id = :me`에 `AREA AND area = :myArea`를 하나 더한다. ADR-0006 8-4처럼 조건마다 따로 뽑아 합친다(`OR`는 인덱스를 못 탄다 — ADR-0006 6-3) |

### 구역을 청크에 복사하는 대가

앱은 작성자의 **현재** 구역을 조인으로 본다(`findByArea`). 청크에 복사하면 작성자가 구역을 옮겼을 때 어긋난다.

- 구역이 바뀌면 그 사용자의 `AREA` 청크를 같은 트랜잭션에서 UPDATE한다. 지금은 구역을 바꾸는 API가 없어 걸리는 경로가 없지만, 생기면 이 규칙을 같이 넣는다.
- 조인으로 풀지 않는 이유: 벡터 검색 SQL에 `members` 조인을 넣으면 HNSW 탐색 중 필터가 행마다 조인을 탄다. 선택도 스윕(ADR-0006 8-4)이 전제한 단일 테이블 필터가 깨진다.

### 마이그레이션 번호

`area` 컬럼과 CHECK는 새 Flyway 파일이다. 번호는 구현 PR을 열 때 AGENTS.md의 절차대로 main과 열린 PR 전부를 보고 정한다.

## 5. HNSW에 주는 영향 — 위험이 오히려 줄어든다

ADR-0006 8-4의 위험 구간은 **선택도가 아주 낮을 때**였다(0.2%에서 `ef_search` 40이 후보를 거의 다 버림).

| 경로 | 선택도 |
|---|---|
| 지금 근로자(본인만) | 약 0.2% |
| 이 결정 뒤 근로자 | 본인 0.2% + 같은 구역 승인분. 구역 6곳이면 최대 약 1/6 × 승인 비율 |

본인 조건과 구역 조건을 따로 뽑으므로 본인 쪽은 지금과 같고(`iterative_scan`이 계속 필요), 구역 쪽은 선택도가 높아 HNSW에 유리하다.
승인 비율은 모른다 `[측정 필요]`. 시드는 상태를 만들지 않으므로(전부 `PENDING`) 측정 전에 시드 생성기가 승인 비율을 받게 해야 한다.

## 6. 하지 않는 것

| 하지 않는 것 | 이유 |
|---|---|
| 승인 일지 전체 공개 | 2-2의 A |
| 미승인 같은 구역 일지를 근거로 | 2-1. 화면에서 보이는 것과 근거로 쓰는 것은 다르다 |
| 개인정보 자동 마스킹 | 검토자가 승인할 때 본다. 자동화는 실제 일지에 무엇이 들어오는지 본 뒤에 판단한다 `[추측]` |
| 승인 철회 API | 지금 없다. 생기면 `reject`와 같은 경로(즉시 좁힘)를 탄다 |
| 공유 범위를 사용자 설정으로 | 작성자가 "비공개"를 고르는 기능. 요구가 확인되지 않았다 |

## 7. 검증

구현 PR에서 다음을 테스트로 고정한다.

- 같은 구역 `PENDING` 일지가 근로자의 RAG 결과에 나오지 않는다
- 같은 구역 `APPROVED` 일지는 나온다. 다른 구역 `APPROVED` 일지는 나오지 않는다
- 승인된 일지를 작성자가 수정하면, **배치를 돌리지 않고도** 같은 트랜잭션 커밋 직후 다른 근로자의 결과에서 사라진다
- 승인 직후 청크가 아직 없는 일지는 배치 한 번으로 `AREA`가 된다
- 번역본 청크가 원본과 같은 공개 범위를 따른다
- KEYWORD 폴백도 같은 범위를 쓴다(ADR-0006 7절 — 장애 시에도 권한은 느슨해지지 않는다)

효과는 `SEARCH-QUALITY-EVAL-PLAN.md`의 E6으로 잰다. 이 결정 전과 후에 같은 질문을 근로자 경로로 던져 **"볼 수 있는 범위 안에 정답이 있는 질문 비율"** 이 얼마나 오르는지 본다.

## 8. 아직 모르는 것

- 실제 승인 비율과 승인까지 걸리는 시간. 승인이 며칠씩 밀리면 공유되는 지식이 늘 며칠 늦다
- 일지에 개인정보·책임 소재(누구의 실수인지)가 얼마나 담기는가. 많으면 승인 기준에 공유 여부를 따로 두어야 한다 `[추측]`
- 구역 경계가 지식 공유의 단위로 맞는가. 같은 설비가 여러 구역에 있으면 구역 밖의 기록이 더 쓸모 있을 수 있다(2-2의 마지막 문단)
