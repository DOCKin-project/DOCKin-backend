# ADR-0001: 출근 체크(Clock-in) 중복 처리 및 동시성 제어 전략

- 상태: 코드 구현 완료 (Redis 분산락 + DB 유니크 제약), k6 실측 완료 (3번 표 참고)
- 대상 코드: `AttendanceService.clockin()`, `attendance` 테이블
- 작성 목적: 왜 이 방식을 선택했는지에 대한 판단 기록. 결과 수치보다 비교 과정 자체가 문서의 핵심.

## 1. 개요 & 문제 상황

### 비즈니스 배경

DOCKin은 조선소/건설 현장처럼 다국어 근로자가 섞여 일하는 환경을 대상으로 한다. 출근 체크는 단순 근태 기록이 아니라 **"지금 이 현장에 누가 있는가"를 파악하는 안전 확인 수단**이다. 이 데이터가 중복되거나 누락되면, 사고 발생 시 인원 파악이 지연될 수 있다는 점에서 단순 게시판의 "좋아요 중복" 문제보다 정합성 요구 수준이 높다.

### 현재 구현의 문제

`AttendanceService.clockin()`은 check-then-act 패턴으로 중복 출근을 막는다.

```java
if (attendanceRepository.findByMemberAndWorkDate(member, today).isPresent()) {
    throw new IllegalArgumentException("이미 오늘 출근 처리가 완료되었습니다.");
}
// ... 이 사이에 동시 요청이 끼어들면 둘 다 통과 가능
Attendance saved = attendanceRepository.save(attendance);
```

조회와 저장 사이에 원자성이 없다. 동시에 두 요청이 들어오면 둘 다 "출근 기록 없음"을 보고 각자 insert를 시도해 **중복 출근 레코드가 생성될 수 있다.**

추가로 확인한 사실: `schema.sql`의 `attendance` 테이블에는 `work_date` 단일 컬럼 인덱스만 있고, `(user_id, work_date)` 복합 유니크 제약이 없다. 즉 지금은 **애플리케이션 코드 하나가 유일한 방어선**이다.

```sql
CREATE TABLE attendance (
    ...
    CONSTRAINT fk_attendance_member FOREIGN KEY (user_id) REFERENCES users (user_id),
    INDEX idx_work_date (work_date)
    -- UNIQUE(user_id, work_date) 없음
);
```

## 2. 이론적 비교

문제를 처음 마주하면 "Redis 분산락"이 정답처럼 보이지만, 실제로는 4가지 선택지가 있고 각각 트레이드오프가 다르다.

| 방식 | 원리 | 장점 | 단점 |
|---|---|---|---|
| **DB 유니크 제약**<br>`UNIQUE(user_id, work_date)` | DB가 중복 insert 자체를 거부 | 구현 최소, 인스턴스 몇 대든 무조건 정합성 보장, 인프라 추가 없음 | 실패를 예외(`DataIntegrityViolationException`)로만 알 수 있음, 사용자 응답 메시지를 별도로 다듬어야 함 |
| **낙관적 락**<br>`@Version` | 조회 시점과 커밋 시점의 버전 비교 | 락 대기 없음, 충돌 드문 상황에 적합 | 이 케이스는 "새 row 생성" 경합이라 `@Version`이 원천적으로 안 맞음(업데이트 충돌 감지 도구지 insert 중복 방지 도구가 아님) |
| **비관적 락**<br>`SELECT ... FOR UPDATE` | 조회 시점에 row/gap 락 | 애플리케이션 레벨에서 완전 직렬화 | 해당 row가 없는 상태(최초 출근)라 잠글 대상이 없음 → gap lock에 의존, MySQL REPEATABLE READ에서 데드락 위험(6번 참고) |
| **Redis 분산락**<br>(Redisson) | `user_id:work_date` 키로 분산 락 | 인스턴스 여러 대에서도 동작, DB 부하 이전에 차단 가능, 응답 속도 이점 | Redis라는 단일 장애점 추가, 락 해제 타이밍/TTL 설계 필요, "락은 잡았는데 Redis가 죽으면?" 시나리오 대응 필요 |

**결론**: 낙관적 락은 이 문제 유형(신규 insert 중복)에 애초에 적합하지 않아 후보에서 제외. 남은 셋 중 하나만 쓰기보다, 4번(의사결정)에서 이중 구조를 제안한다.

## 3. 수치 기반 성능/정합성 비교

**테스트 환경**
- 로컬 docker-compose로 MySQL 8.0 + Redis 7 단일 인스턴스 기동, 앱은 로컬 JVM(Gradle bootRun)으로 실행, 단일 인스턴스.
- k6 시나리오: 동일 `user_id`로 30개 VU가 동시에 `POST /api/attendance/in`을 1회씩 호출(`per-vu-iterations`, 30 VUs × 1 iteration).
- 각 전략을 실제 코드로 스위칭해가며(같은 커밋의 working tree ↔ HEAD 시점 코드) 3회 반복 실측.
- 측정 지표: 평균 응답시간 / p95 / 실제 생성된 attendance 중복 행 수(DB에서 직접 COUNT) / 5xx 비율.

| 전략 | 평균 응답시간(성공 요청) | p95(전체) | 중복 발생 건수 | 5xx 비율 | 비고 |
|---|---|---|---|---|---|
| 현재 (애플리케이션 체크만, HEAD) | 836ms | 1.21s | **10건 / 30회** | 66.7% (20/30) | check-then-act 경합 창이 실제로 열려 중복 출근이 발생함을 확인 |
| DB 유니크 제약만 (락 없음) | 1.92s | 2.64s | 0건 | 96.7% (29/30) | 중복은 막히지만 `DataIntegrityViolationException`을 못 잡아 거의 전부 500으로 응답 |
| DB 유니크 + Redis 분산락 (최종) | 1.64~2.06s | 2.06~2.6s | **0건** | 0% (409로 정상 처리) | 정합성 보장 + 사용자에게 깨끗한 409 응답 |

**해석**: DB 유니크 제약만으로도 데이터 정합성(중복 0건)은 지켜지지만, 그 자체로는 사용자 경험이 오히려 가장 나쁘다(5xx 96.7%) — 이게 "DB 제약만 쓰면 예외 기반 처리라 응답이 지저분해진다"는 2번 섹션의 이론적 우려가 실측으로 확인된 지점이다. Redis 분산락을 얹었을 때 응답시간이 더 느려 보이는 건(1.64~2.06s) 대부분 `LOCK_WAIT_SECONDS=3`까지 락을 기다리다 실패하는 29개 요청의 대기시간이 평균에 섞여서다 — 실제 성공 요청 1건의 처리 자체는 빠르다.

갭락 데드락(REPEATABLE READ)은 이번 측정 범위에서는 확인하지 않았다 — 별도로 `SHOW ENGINE INNODB STATUS` 기반 검증이 필요하면 후속 작업으로 분리한다.

### 3-1. 측정 중 발견한 버그 2건 (실제 코드에 존재, ADR과 무관하게 수정 필요했음)

k6로 "현재(최종) 구현"을 처음 측정했을 때 30개 요청이 전부 500으로 실패했다. 원인은 두 가지였고, 실측을 위해 실제로 고쳤다:

1. **`clockin()`이 읽기 전용 트랜잭션으로 실행되고 있었다.** 클래스에 `@Transactional(readOnly = true)`가 걸려 있고, `clockin()`은 "락 대기시간을 트랜잭션에서 빼려고" 의도적으로 어노테이션을 안 걸어뒀는데, 스프링은 어노테이션이 없으면 클래스 레벨 설정을 그대로 상속한다. 그 결과 `clockin()` 전체가 읽기 전용 트랜잭션으로 묶여 내부의 INSERT가 전부 `Connection is read-only` 예외로 실패하고 있었다. `@Transactional(propagation = Propagation.NOT_SUPPORTED)`를 명시해 트랜잭션 자체에 참여하지 않도록 고쳤다(의도했던 "락 대기시간을 트랜잭션 밖에 둔다"는 설계를 실제로 성립시킴).
2. **`BusinessException`을 실제 HTTP 상태 코드로 변환하는 핸들러가 프로젝트 전체에 없었다.** `ErrorCode`/`ErrorResponseDto`는 상태 코드·메시지 구조를 다 갖추고 있었지만 이를 사용하는 `@RestControllerAdvice`가 없어서, `ATTENDANCE_ALREADY_CHECKED`(409)를 포함한 모든 `BusinessException`이 항상 500으로 나가고 있었다. `GlobalExceptionHandler`를 추가해 해결했다.

두 버그 다 이 ADR이 다루는 동시성 설계와는 별개의 결함이지만, 실측을 하지 않았다면 발견하지 못했을 것이다 — "설계는 맞는데 실제로 돌려보니 다른 이유로 깨져 있었다"는 것 자체가 왜 실측이 필요한지에 대한 근거다.

## 4. 의사결정 및 구현 전략

### 최종 선택: DB 유니크 제약(최후 방어선) + Redis 분산락(1차 방어) 이중 구조

Redis 분산락 하나만 쓰지 않는 이유: Redis가 "일시적으로 응답이 느려서 락을 못 잡은 것"과 "다운돼서 아예 락 기능이 없는 것"을 구분하지 못한 채 분산락에만 의존하면, Redis 장애가 곧 데이터 정합성 장애로 번진다. 반대로 DB 유니크 제약만 쓰면 매 요청마다 예외 기반 처리라 사용자 응답이 지저분해지고, 트래픽이 몰릴 때 DB에 부하가 그대로 전달된다.

그래서:
1. **1차 방어 (Redis 분산락)**: `attendance:lock:{userId}:{workDate}` 키로 짧은 TTL 락을 잡고 정상 흐름을 빠르게 처리. 대부분의 요청은 여기서 걸러진다.
2. **2차 방어 (DB 유니크 제약)**: Redis가 다운되거나 락 획득에 실패해도, DB의 `UNIQUE(user_id, work_date)` 제약이 최종적으로 중복을 막는다. `DataIntegrityViolationException`을 잡아 동일한 "이미 출근 처리됨" 응답으로 변환한다.

### Redis 장애 시 폴백 전략

- Redisson 클라이언트 연결 실패/타임아웃 시 예외를 잡아, **분산락 없이 바로 DB insert를 시도**하도록 우회 경로를 둔다.
- 이 경우 유니크 제약이 유일한 방어선이 되고, 응답 속도는 느려지지만(예외 기반 처리) 데이터 정합성은 깨지지 않는다.
- 즉 Redis는 "성능/UX 최적화 계층"이고 DB 제약이 "정합성 보장 계층"이라는 역할 분리를 명확히 한다. Redis가 죽어도 서비스 정합성 자체는 무너지지 않아야 한다는 게 이 설계의 핵심 기준.

### 동기화/일관성

락은 출근 처리 로직 실행 구간에만 잡고, 트랜잭션 커밋 직후 즉시 해제한다(TTL은 트랜잭션 최대 소요 시간보다 충분히 짧게, 예: 3초). 락 보유 중 커넥션 풀 고갈로 트랜잭션이 지연되는 경우를 대비해 TTL과 DB 커넥션 타임아웃 값의 관계도 함께 점검한다.

## 5. 추가 고려사항

- **모니터링**: Redis 락 획득 실패율, 유니크 제약 위반 발생 횟수를 지표로 남겨서 "1차 방어선이 실제로 얼마나 걸러주는지"를 운영 관점에서 확인할 수 있게 한다.
- **악용 방지**: 동일 사용자가 여러 기기/위치에서 동시에 출근을 시도하는 경우는 이번 ADR의 범위 밖(위치 기반 검증은 별도 이슈로 분리).
- **한계**: 이 설계는 단일 리전/단일 Redis 클러스터를 가정한다. 멀티 리전으로 확장 시 분산락 자체의 정합성 문제가 재발하며, 이는 현재 서비스 규모에서 다룰 필요가 없다고 판단해 범위에서 제외한다.
