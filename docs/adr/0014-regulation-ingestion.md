# ADR-0014: 안전 법령을 RAG 근거로 — 조문은 구조로 받고, 별표(표)는 파싱하고, 청크마다 출처 머리말을 붙인다

- 상태: **제안 (2026-11-26).** 구현 없음. 법제처 Open API 응답을 아직 본 적이 없다(5절)
- 대상 코드(예정): `rag/model/SourceType`, `rag/chunking/*`, `rag/service/IndexingService`, `rag/service/RagPrompt`, 새 `regulation` 패키지, Flyway `V21`; pylab `regdocs/`
- 관련 문서: ADR-0006(벡터 검색) "규정 문서(PDF/HWP) 적재 — Phase 1.5로 분리", ADR-0013 3단계 "데이터 범위 확장"·1단계 뒤 남은 것 2("안전 질문을 평가셋에 넣기"), pylab ADR-0002(규정은 법제처 API로), `docs/SLO.md` 7-1, `docs/SEARCH-QUALITY-EVAL-PLAN.md`
- 작성 목적: RAG 근거가 지금은 작업일지·번역본·안전교육·점검항목, 즉 **DB에 있는 짧은 글**뿐이다. 조선소 작업자가 가장 확인하고 싶은 것 중 하나는 "이 작업에 법이 무엇을 요구하나"인데, 그 근거가 없다. 긴 구조 문서를 검색 가능한 청크로 바꾸는 경로를 정한다.

---

## 1. 무엇이 문제인가 — 짧은 글과 긴 구조 문서는 자르는 법이 다르다

작업일지는 200~500자짜리 독립된 글이다. 고정 500자 청킹(`FixedSizeChunkingStrategy`)으로 잘라도 청크 하나가 대개 글 하나다.

법령은 다르다.

| 성질 | 예 | 고정 크기로 자르면 |
|---|---|---|
| **위계** | 법 → 장 → 절 → 조 → 항 → 호 → 목 | 청크가 "어느 법의 몇 조인지" 모른다. "① 사업주는 다음 각 호의 조치를 하여야 한다" 만 떨어진 청크는 검색돼도 쓸 수 없다 |
| **길이 편차** | 한 줄짜리 조부터 수천 자짜리 조까지 | 짧은 조 여러 개가 한 청크에 섞이거나, 긴 조가 항 중간에서 끊긴다 |
| **참조** | "제38조제1항에 따른", "별표 1의 위험물질" | 참조 대상이 다른 청크에 있다 |
| **표** | 별표(위험물질 목록, 보호구 기준, 점검 주기) | 표를 줄글로 펴면 행·열 관계가 사라진다 — "질산 / 산화성 액체 / 농도 40% 이상"이 한 줄로 뭉개진다 |
| **판본** | 개정·부칙으로 조마다 시행일이 다르다 | 옛 조문과 새 조문이 같이 검색된다 |

**실무 RAG에서 품질 차이가 가장 크게 나는 자리가 여기다** — 같은 임베딩 모델이어도 청크가 "자기가 무엇인지" 아는지에 따라 검색이 갈린다.

## 2. 범위

| 넣는다 | 이유 |
|---|---|
| 산업안전보건법, 같은 법 시행령·시행규칙 | 사업주·근로자 의무의 뿌리 |
| **산업안전보건기준에 관한 규칙** | 조선소 작업(용접·고소작업·밀폐공간·크레인·중량물)의 구체 기준이 거의 다 여기 있다. 조 수가 가장 많다 |
| 위 규칙의 **별표** | 보호구·점검 주기·위험물질 같은 수치 기준이 표로 있다 (4절 D6) |

| 넣지 않는다 (이번에) | 이유 |
|---|---|
| 사내 작업 표준서·사규 | 실물이 없다. 꼴(PDF? HWP? 스캔본?)을 보고 정한다. 9절 |
| 고시·지침·KOSHA 가이드 | 법령 다음. 법적 구속력이 다르다는 표시가 먼저 필요하다 |
| 판례·해석례 | 근로자용 답변의 근거로 쓰기에 위험하다 |

규모 추정 `[추측]`: 법·시행령·시행규칙·기준규칙 합쳐 조 2천 개 안팎, 청크 4천 개 안팎. 지금 HNSW(합성 2만 건)보다 작다 — 저장·색인 비용은 문제가 아니다.

## 3. 흐름

```
[pylab regdocs]                                   [DOCKin Spring]
 법제처 API ─ fetch ─▶ <법령ID>-<MST>.xml (원본 보존)
                        │ parse
                        ▼
                  조문 JSONL ──────────▶ POST /api/admin/regulations/import (관리자)
                  별표 JSONL (D6) ─────▶        │ upsert (source_key)
                                                ▼
                                    regulation_articles  ◀── GET /api/regulations/{id} (원문 보기)
                                                │ 현행만 (D4)
                                                ▼
                                    StructuredChunkingStrategy (D3·D5)
                                                │
                                                ▼
                                    document_chunks (REGULATION, PUBLIC)
                                                │
                                    검색·근거 주입 (기존 경로 그대로)
```

**파싱은 Python, 자르기·색인은 Spring.** pylab ADR-0002 D2와 같다 — 자르는 정책이 두 군데 있으면 둘이 어긋난다. Python 쪽은 "구조를 잃지 않고 JSONL로" 까지만 한다.

## 4. 결정

> 아래 D5·D6의 법령 문구(편·장 위치, 별표 행)는 **꼴을 보여 주는 예시**다. 실제 위치와 문구는 단계 0에서 받은 데이터로 확인한다.

| # | 결정 | 버린 것 | 이유 |
|---|---|---|---|
| D1 | **조문은 법제처 Open API의 구조화 XML로 받는다.** PDF/HWP 본문 파싱은 하지 않는다 | 국가법령정보센터 PDF·HWP 다운로드를 파싱 | pylab ADR-0002. 조·항·호·목이 요소로 나뉘어 오고 조마다 시행일이 있다. 파싱으로 다시 만들 이유가 없다 |
| D2 | **원본 테이블 `regulation_articles`를 둔다.** `document_chunks.source_id`는 이 테이블의 `id`(BIGINT). 키는 `source_key = 법령ID:조문번호`(UNIQUE), 판본 `mst`·`effective_date`·`text`·`content_hash`·`repealed`를 함께 | `document_chunks`에 바로 넣기 / `source_id`를 문자열로 | ① `source_id`가 BIGINT라 `"001766:38"`을 못 넣는다 ② 근거 [n]을 누르면 **원문 조 전체**를 보여 줘야 한다(C2) — 청크는 조의 일부일 수 있다 ③ 개정 판본을 받으면 같은 키로 upsert하고 `content_hash`가 같으면 재임베딩하지 않는다(멱등, 기존 색인 배치와 같은 규칙) |
| D3 | **청크 경계는 구조를 따른다: 조 하나 = 청크 하나, 500자를 넘으면 항(①②…) 경계에서 나눈다.** 항 하나가 그래도 넘으면 호(1. 2. …) 경계, 그래도 넘으면 기존 문장 경계 절단 | 고정 500자 / 항 단위 고정 | 항만 떼면 "다음 각 호의" 같이 열린 문장이 생기지만, 아래 D5의 머리말이 그 맥락을 메운다. 고정 크기는 1절 표의 문제를 그대로 가진다. 500자는 e5-small 512토큰 상한에서 나온 기존 근거(`FixedSizeChunkingStrategy` 문서)를 따른다 |
| D4 | **현행만 색인한다.** `effective_date ≤ 오늘`인 가장 최근 판본의 조만 `document_chunks`에 있다. 시행 전 조문은 `regulation_articles`에만 두고 매일 색인 배치가 날짜를 다시 본다. 삭제된 조(`삭제 <2023. 1. 1.>` 꼴)는 `repealed=true`로 두고 청크를 지운다 | 검색 쿼리에 시행일 필터 | 벡터 검색 SQL(권한 선필터·HNSW iterative scan)을 건드리지 않는다. 시행 전 조문이 검색되는 것은 "틀린 답"이다(ADR-0013 C1) |
| D5 | **청크마다 출처 머리말을 붙여 임베딩한다:** `[산업안전보건기준에 관한 규칙 > 제2편 안전기준 > 제1장 기계·기구 > 제38조(사전조사 및 작업계획서의 작성 등) 제1항]` + 본문 | 본문만 임베딩 | 항 단위로 나뉜 청크가 "무슨 법의 무슨 조인지"를 스스로 말한다. 질문이 "밀폐공간 작업 전에 뭘 해야 해"처럼 장 제목의 단어를 쓰면 머리말이 맞춰 준다. **효과는 잰다**(6절 E2) — 안 오르면 뺀다. 머리말은 토큰을 먹으므로 D3의 500자는 머리말 포함 길이다 |
| D6 | **별표(표)는 행 단위로 펴서 청크를 만들고, 행마다 열 머리를 반복한다:** `[기준규칙 별표 1 위험물질의 종류 > 산화성 액체 및 산화성 고체] 물질명: 질산 / 기준: 농도 40% 이상` | 표를 마크다운 통째로 / 표를 건너뛰기 | 표 통째는 한 청크에 수십 행이 들어가 어떤 행에 대한 질문에도 점수가 흐려진다. 열 머리 없이 행만 두면 "40% 이상"이 무엇의 기준인지 모른다. **별표는 API가 본문 XML로 주지 않을 수 있다**(5절) — 그러면 첨부(HWP/PDF)를 받아 표를 뽑는다. 이 작업에서 실제로 파싱이 필요한 자리는 여기뿐이다 |
| D7 | **가시성은 `PUBLIC`, 언어는 `ko`, 번역본은 만들지 않는다(이번에)** | 조문 기계번역 색인 | 법조문 오역은 안전 문제다. 베트남어 질문은 다국어 임베딩의 교차언어 검색으로 찾고, 답은 번역해 주되 **원문 조문을 항상 같이 보여 준다**(D8). 교차언어 검색이 모자라면(6절 E3) 번역본 색인을 그때 재고 결정한다 — 작업일지에서는 번역본이 베트남어를 0.13 → 0.87로 올렸다 |
| D8 | **프롬프트·응답:** 근거 출처 표시에 `법령`을 따로 쓴다(`RagPrompt.describe`). 법령 근거가 있으면 "조문 번호를 밝히고, 해석이 필요한 부분은 안전관리자에게 확인하라"를 지시에 더한다. 응답 `retrieval.sources`에 `REGULATION`·`sourceId`가 오므로 앱이 `GET /api/regulations/{id}`로 원문을 연다 | 답변 안에 조문 전체 인용 | 답은 짧게, 원문은 한 번 눌러서. ADR-0013 C2(출처를 항상 보여 준다) |
| D9 | **적재는 관리자 업로드(JSONL)로 시작한다.** Spring이 법제처를 직접 부르지 않는다 | Spring 스케줄러가 API 호출 | 개정은 1년에 몇 번이다. 자동화보다 "무엇이 들어갔나"를 사람이 보는 편이 맞다. 자동 개정 추적은 필요해지면(9절) |

## 5. 아직 확인하지 못한 것 — 이것부터

1. **실제 API 응답을 본 적이 없다.** pylab `regdocs`의 파서는 기억으로 만든 추정 픽스처로만 테스트됐다(pylab ADR-0002 5절). 실제 응답 한 번이 이 문서 전체의 전제다.
   - 2026-11-26: open.law.go.kr 마이페이지에 OC(인증키)가 **등록돼 있다.** 실제 호출이 되는지는 아직 확인하지 않았다 — 인증키와 별도로 OPEN API 메뉴에서 활용 신청(쓸 API 종류, 호출 IP/도메인)이 필요할 수 있다 `[추측]`.
   - OC 값은 호출 URL 쿼리(`?OC=…`)에 실린다. **저장소에 커밋하지 않는다** — 환경 변수로만 둔다. pylab `regdocs`는 `LAWGO_OC`를 읽는다. DOCKin 쪽에서 쓸 일이 생기면 같은 이름을 쓰고 `.env.example`에는 이름만 둔다.
2. **별표가 어떻게 오는가.** 본문 XML 안에 표 구조로 오는지, 첨부 파일 링크(HWP/PDF)로만 오는지 모른다 `[미확인]`. 후자면 D6은 HWP/PDF 표 추출이 된다 — 후보는 HWP→PDF 변환 뒤 `pdfplumber` 표 추출, 또는 HWPX(XML)라면 직접 읽기. 실물을 보고 정한다.
3. **조 길이 분포.** 500자를 넘는 조가 몇 %인지 모른다. 실제 데이터로 D3의 항 분할이 얼마나 일어나는지 센다.

## 6. 어떻게 잴 것인가 — 바꾸기 전에 기준선

기존 검색 품질 하네스(`SearchQualityEvalTest`, #170)에 법령 질문을 더한다. **정답은 조 단위**(`source_key`)다 — 항으로 나뉜 청크 중 어느 것이 나와도 그 조가 상위 5개에 있으면 맞은 것으로 본다.

| 실험 | 비교 | 지표 | 결정 |
|---|---|---|---|
| E1 법령 평가셋 | 질문 30 × 3언어(ko·vi·en). 유형: 용어형("밀폐공간 산소농도 기준") · 의미형("탱크 안에 들어가기 전에 뭘 재야 해") · 별표형("보안경 써야 하는 작업") · 답 없음(법에 없는 사내 규칙) | Hit@5, MRR@10 (조 단위) | 아래 비교의 기준 |
| E2 청킹 | A 고정 500자 / B 구조 청킹(D3) / C 구조 청킹 + 머리말(D5) | E1 지표, 짝지은 부트스트랩 | C가 B보다 나쁘지 않으면 C. 나쁘면 머리말을 뺀다 |
| E3 교차언어 | E2 승자에서 언어별 격차 | vi·en Hit@5 − ko | 격차가 SLO 7-1 기준을 넘으면 D7 재검토(조문 번역본 색인) |
| E4 별표 | 표 통째 / 행 단위(열 머리 없음) / 행 단위 + 열 머리(D6) | 별표형 질문의 Hit@5 | |
| E5 섞임 | 작업일지 2만 건 코퍼스에 법령을 더했을 때 **기존 작업일지 질문의 Hit@5** | SLO 7-1 A 회귀 기준 | 법령이 작업일지 검색을 밀어내면 소스별 할당(상위 5개 중 법령 최대 N개)을 정한다 |
| E6 답변 | ADR-0013 D5 하네스에 법령 질문 추가 | 충실도, **안전 질문 충실도(0건 불변식)**, 출처 정확도 | ADR-0013 "1단계 뒤 남은 것 2"를 이것으로 채운다 |

**질문은 사람이 만들고 정답 조는 사람이 붙인다.** 합성 코퍼스와 달리 법령은 실물이라 질문만 만들면 된다. 30문항을 만드는 데 반나절 `[추측]`.

| 5 | 별표(D6) → E4 | |
| 6 | 프롬프트·응답(D8) → E5·E6 | 안전 질문 충실도 0건 |

**2단계를 3단계보다 먼저 하는 이유:** 구조 청킹이 고정 크기보다 낫다는 것은 통념이다. 이 코퍼스에서도 그런지, 얼마나인지를 재야 결정이 근거를 갖는다. 기준선 없이 구조 청킹부터 만들면 "좋아졌다"를 말할 수 없다.

## 8. 하지 않는 것

- **범용 PDF/HWP 파서.** 법령 본문은 API가 구조로 준다. 파싱은 별표 표(D6)와, 나중의 사내 문서에서 실물을 보고 그 꼴에 맞춰 만든다.
- **조문 참조 따라가기**("제38조제1항에 따른" → 제38조를 함께 가져오기). 효과가 있을 법하지만 E2 결과를 보고 검색 실패가 참조 때문인 사례가 나오면 그때.
- **법령 LLM 요약본 색인.** 요약은 원문과 다른 말을 만들 수 있다. 근거는 원문이어야 한다.

## 9. 다음에 올 것

- **사내 작업 표준서(PDF/HWP/스캔본).** 여기서부터는 법제처 같은 구조가 없다. 레이아웃 분석(제목·번호 체계 인식), 표 추출, 스캔본 OCR이 필요하다. D3·D5(구조 경계 + 머리말)를 그대로 쓰되 "구조"를 파서가 복원해야 한다. 실물 한 부를 받는 것이 시작이다.
- **개정 자동 추적.** `regdocs search`로 최신 MST를 주기적으로 보고 바뀌면 다시 받는다.
- **하이브리드 검색(ADR-0013 2단계 3).** 법령 질문은 "제38조", "산소농도 18%"처럼 용어·숫자가 많아 키워드 경로의 효과가 작업일지보다 클 것이다 `[추측]` — E1 평가셋이 그 비교에도 쓰인다.
