# 프로젝트 범위 및 역할 분담

DOCKin은 팀 프로젝트다. `docs/adr/*` 문서와 이 저장소(`DOCKin-backend`)에 담긴 모든 설계/구현 내용은 **본인이 담당한 Spring 백엔드 + DB 설계 범위**에 한정된다. 포폴/이력서/면접에서 이 저장소의 내용을 인용할 때, 담당 범위를 벗어난 내용(FastAPI 쪽 AI 처리)을 본인이 만든 것처럼 서술하지 않기 위해 경계를 명시해둔다.

> **갱신 이력**
> - 2026-08-05: RAG/벡터 검색이 **로드맵에서 구현으로 바뀌어** 이 문서를 전면 수정했다.
>   이전 판은 "벡터 임베딩 기반 교차언어 검색은 이 프로젝트에 존재하지 않는다"고 명시하고 있었다.
>   저장소(MySQL → PostgreSQL) 변경도 함께 반영했다.

## 담당 범위 (본인, 이 저장소)

- 인증/인가: JWT 발급/블랙리스트, RBAC(`ADMIN`/`USER`)
- 근태: 출퇴근 체크 동시성 제어(Redis 분산락 + DB 유니크 제약), 근무조별 지각 판정 — `docs/adr/0001`
- 휴가 신청/승인 도메인, 승인 시 근태 반영(`ApplicationEvent` 기반), 자정 결근 배치, 근무일 캘린더
- DB 스키마 설계 및 쿼리/인덱스 (`docs/adr/0002`의 N+1, LIKE 검색 진단 포함)
- 채팅(WebSocket/STOMP), 작업일지 CRUD, 안전교육 이수 관리, 장비 점검 체크리스트 API
- **RAG 검색 파이프라인** — 아래에 범위를 따로 적는다
- FastAPI 연동 클라이언트 레이어(`ai` 패키지: `fastApiService`, `SttService`) — **FastAPI를 호출하고 응답을 받아 DB에 저장하는 Spring 쪽 코드**. `docs/adr/0002` 2-1의 `Mono.zip` 병렬화 등 이 레이어의 성능/구조 개선은 본인 책임 범위.

### RAG / 벡터 검색 — 무엇을 만들었고 무엇을 가져다 썼는가

이 항목은 특히 오해를 사기 쉬워 경계를 나눠 적는다. **모델을 만들지 않았다. 모델을 쓰는 시스템을 만들었다.**

| | 내용 |
|---|---|
| **가져다 쓴 것** | 임베딩 모델 `intfloat/multilingual-e5-small`(오픈소스), 추론 서버 HuggingFace TEI(컨테이너 이미지), pgvector 확장, Hibernate `hibernate-vector` 모듈 |
| **직접 만든 것** | 청킹 전략(토큰 비율 실측 기반), 멱등 재색인 배치, 권한 선필터 검색, 챗봇 근거 주입, 장애 시 키워드 폴백과 모드 기록, PostgreSQL 이관과 pgvector 도입, HNSW 인덱스와 그 한계 실측 |

- 설계 근거: `docs/adr/0006`
- **모델 학습·파인튜닝은 하지 않았다.** 사전학습 모델을 그대로 쓴다.
- 따라서 "RAG 시스템을 구현했다"는 서술은 정확하지만, **"임베딩 모델을 만들었다"는 사실이 아니다.**
- 교차언어 검색이 성립하는 것도 다국어 모델의 성질 덕분이며(`CrossLingualRetrievalTest`로 확인), 본인 기여는 그 성질을 **권한·감사·트랜잭션과 함께 쓸 수 있게 오케스트레이션한 부분**이다.

## 팀원 담당 범위 (다른 저장소, 본인 책임 아님)

- FastAPI 서버: HuggingFace 기반 번역, STT(음성 인식).
  **임베딩/벡터 검색은 FastAPI에 없다** — RAG는 Spring 쪽(이 저장소)에 구현되어 있다.
  챗봇 응답 생성(LLM 호출)은 FastAPI가 담당하며, 근거 검색과 프롬프트 주입이 Spring 담당이다.
- (프론트엔드 등 있다면 별도 담당자 — 필요 시 추가)

## 저장소 / 인프라

- **DB는 PostgreSQL이다**(2026-08-04 MySQL에서 이관, `docs/adr/0006` 8절). 이관 근거는 벡터 검색의 ANN 인덱스이며, 부수적으로 JDBC 배치 INSERT와 트랜잭션 단위 락 타임아웃이 함께 해결됐다.
- Redis: 출근 체크 분산락 전용.
- 스키마 관리는 **과도기다.** `document_chunks`는 Flyway(`db/migration/V1`)가, 나머지 테이블은 여전히 Hibernate `ddl-auto=update`가 만든다. `src/main/resources/schema.sql`은 **실행되지 않는 참조 문서이며 MySQL 문법이 남아 있어 현재 stale하다** — 인용하면 안 된다.
- **현재 PostgreSQL 스키마는 `docs/db/postgresql-schema.sql`에 있다.** 손으로 쓴 것이 아니라 실제 DB에서 뽑은 덤프이며, 소스 오브 트루스는 여전히 엔티티다. 엔티티와 DB의 일치는 `SchemaValidationTest`(`ddl-auto=validate`)가 검증한다.

## 명시적으로 짚어야 할 오해 소지

- **`docs/adr/0003`(검색 도메인 확장)은 여전히 로드맵이다.** 다만 전제가 MySQL이라 3-1(ngram FULLTEXT)은 PostgreSQL 대응물(pg_trgm/tsvector)로 바뀌어야 하고, 3-3(Elasticsearch)은 벡터 검색 도입으로 우선순위가 내려갔다. 자세한 관계는 `docs/adr/0006` 9절. **"하이브리드 검색(BM25 + 벡터)을 구현했다"는 사실이 아니다** — 벡터 검색만 구현되어 있고 키워드 경로는 장애 시 폴백용 LIKE다.
- **"다국어 번역/STT를 구현했다"는 표현은 팀원 담당 영역이므로 쓰지 않는다.** 본인 기여는 "번역/STT 결과를 받아 저장·조회·검색 가능하게 만든 백엔드 설계"로 한정해서 서술한다.
- **`docs/adr/0005`의 격차 진단은 2026-07-04 시점 기록이다.** 이후 상당수가 해소됐고 일부는 반대로 뒤집혔다(CI/CD 워크플로 삭제). 그 문서 상단의 갱신 표를 함께 볼 것.
- **재현 절차는 앱을 띄우는 것이 전부다** (2026-08-05 갱신). 이전에는 `docs/migration/`의 SQL을 손으로 실행해야 했고 빠뜨려도 에러 없이 조용히 동작이 달라졌다. 지금은 Flyway `V1`이 `CREATE EXTENSION` → 테이블 → HNSW 인덱스를 기동 경로에서 처리한다. `ddl-auto`가 만들지 못하는 것은 여전히 그 둘이며, 달라진 것은 **사람이 기억할 필요가 없어졌다**는 점이다.
