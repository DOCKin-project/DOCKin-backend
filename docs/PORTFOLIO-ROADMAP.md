# 포트폴리오 로드맵 — 무엇을 더 만들고, 무엇을 이야기할 것인가

- 기준일: 2026-08-05
- 대상 독자: 나 자신(다음에 뭘 할지 정할 때) + 면접에서 이 프로젝트를 설명할 때의 나
- 관계: `WORK-BACKLOG.md`가 **할 일 목록**이라면 이 문서는 **그것이 왜 값어치가 있는가**다.
  우선순위가 서로 다를 수 있고, 그 차이 자체가 이 문서의 내용이다.

---

## 0. 이 프로젝트의 진짜 차별점은 기능 목록이 아니다

먼저 냉정하게 볼 것. **기능만 나열하면 이 프로젝트는 평범하다.**
근태, 작업일지, 채팅, 체크리스트, 챗봇 — 조합은 흔하고, 신입 포트폴리오에서 자주 보이는 구성이다.
"RAG를 붙였다"도 이제 흔하다.

차별점은 **결정의 근거를 실측으로 남겼다는 것**이고, 더 정확히는
**측정이 자기 가설을 뒤집은 기록이 여러 건 있다는 것**이다. 이건 흔하지 않다.

| 이미 갖고 있는 서사 | 무엇이 특이한가 |
|---|---|
| 브루트포스 → pgvector 전환 | 병목이 "DB가 느려서"가 아니라 **클라이언트 전송(81%)** 이라는 걸 `EXPLAIN`으로 찾았고, 인덱스 없이 계산 위치만 옮겨 **70배**를 얻었다. 인덱스는 그 다음이었다 |
| `SENTENCE_LOOKBACK = 120` | 실측하려고 어서션을 걸었더니 **가설이 틀려서 테스트가 실패**했다. 값은 그대로 두고 근거만 바꿨다 |
| JDBC 배치가 안 먹던 것 | 설정은 켜져 있었는데 `IDENTITY`가 막고 있었다. `Com_insert`로 **DB가 센 값**으로 확인 |
| MySQL → PostgreSQL 이관 | `ddl-auto=update`가 DDL 실패를 로그만 남기고 기동을 막지 않아 **테이블 없이 정상 기동한 것처럼** 보였다 |
| Elasticsearch를 **안 쓴** 결정 | 다국어 임베딩이 요구사항을 먼저 풀어서 도입 근거가 사라졌다. **안 한 이유를 근거와 함께 남긴 것** |
| `@Lob` 버그 (2026-08-05) | 아래 1절 |

> **면접에서 강한 것은 "무엇을 만들었나"가 아니라 "무엇이 틀렸다는 걸 어떻게 알았나"다.**
> 이 프로젝트에는 후자가 여섯 건 있다. 그걸 못 살리면 그냥 CRUD + RAG 프로젝트가 된다.

## 1. 가장 최근에 생긴 서사 — 시드 데이터가 가리고 있던 것

`data.sql`을 지운 뒤 표본 데이터를 넣을 수단이 없었다. 그 상태로 지내다 시드를 만들어
**색인을 처음 돌린 순간** 이게 나왔다:

```
Bad value for type long : 오전 작업 시작 직후부터 용접 와이어가 간헐적으로...
```

`WorkLog.logText`의 `@Lob` 때문이다. PgJDBC는 CLOB을 Large Object의 **OID(숫자)** 로 취급하는데
컬럼은 `text`라 내용을 `long`으로 파싱하려다 실패한다. MySQL에서는 `LONGTEXT`로 잘 돌았다.

**핵심은 왜 이게 그때까지 안 드러났느냐다.**

| 방어선 | 왜 통과했나 |
|---|---|
| `ddl-auto=validate` | `columnDefinition = "TEXT"`가 DDL을 강제하므로 **테이블은 정상**이다. validate는 컬럼 타입만 보고 **JDBC 바인딩은 보지 않는다** |
| `SchemaValidationTest` | 같은 이유로 통과 |
| 테스트 100여 개 | `work_logs`가 비어 있어 **조회가 행을 반환한 적이 없다.** 터지려면 실제 행을 읽어야 한다 |

**JPA로 작업일지를 읽는 모든 경로가 깨져 있었다.** 목록도 상세도. 그런데 아무도 몰랐다.

> 이 이야기의 값어치는 버그 자체가 아니라 **"검증 장치가 셋인데 셋 다 통과했다"** 는 데 있다.
> 그리고 그 셋을 모두 우회한 원인이 **"데이터가 없어서"** 였다는 것. 테스트 커버리지 이야기를
> 할 때 흔히 빠지는 지점이다.

### 2-1. 지금 당장 (측정 마무리 — 이미 재료가 다 있다)

시드와 생성기가 생겨서 **막혀 있던 측정이 전부 가능해졌다.** 코드를 더 쓸 필요가 거의 없다.

| # | 할 일 | 왜 지금인가 | 포폴 값어치 |
|---|---|---|---|
| A1 | **ANN recall 측정** (`WORK-BACKLOG` 2b) | 생성기로 코퍼스를 만들면 브루트포스가 정답 기준선이 된다 | ★★★ HNSW를 "켰다"가 아니라 **"켜도 되는지 쟀다"** 가 된다 |

| A3 | **원문·번역본 중복 점유 빈도** (P2-8-2) | top-5 중 2자리를 같은 내용이 먹는 것이 이미 재현됨 | ★★☆ A2와 한 묶음 |

| A5 | **목록 API 성능 실측** (2-3 참고) | 생성기로 100만 건을 넣으면 바로 잰다 | ★★★ 아래 2-3 |

> **A1~A4는 새 기능이 아니라 "이미 만든 것의 근거를 채우는 일"이다.**
> 그리고 이 프로젝트의 차별점이 바로 그 근거이므로, **기능을 하나 더 만드는 것보다 값어치가 크다.**

### 2-2. 그다음 (품질 — 이미 진단된 결함)

| # | 할 일 | 근거 | 포폴 값어치 |

### 2-3. 새로 발견된 것 — 원본 도메인이 방치되어 있다

RAG 쪽 `document_chunks`에는 인덱스가 5개인데 **`work_logs`에는 PK 하나뿐이다.**
연 100만 건이 쌓이는 테이블인데 그렇다.

| 지점 | 문제 |
|---|---|
| `findByMemberIn(areaMembers, ...)` | 구역 사용자를 전부 조회해 `IN` 절에 통째로 넣는다. `user_id` 인덱스가 없어 **풀스캔** |
| `Page<>`의 COUNT | 매 요청 `SELECT count(*)`. PostgreSQL은 MVCC라 정확한 count에 풀스캔이 필요 |
| OFFSET 페이징 | 뒤 페이지일수록 느려진다. **색인 경로는 P1-13에서 커서로 바꿨는데 목록 API는 그대로** |
| `ORDER BY created_at DESC` | 인덱스 없음 → 매번 정렬 |
| `searchWorkLogs`의 `LIKE %kw%` | 양쪽 와일드카드라 인덱스 불가. `pg_trgm`이 해법(ADR-0003 6-1) |

> **이게 지금 가장 좋은 다음 소재일 수 있다.** 이유가 셋이다.
> ① 생성기로 100만 건을 넣어 **실측할 수 있다** — 추측이 아니라 숫자로 시작한다.
> ② `EXPLAIN ANALYZE` → 인덱스 추가 → 커서 페이징 → `pg_trgm`까지 **한 서사로 이어진다.**
> ③ **"RAG는 튜닝했는데 정작 원본 테이블은 안 봤다"** 는 자기 진단으로 열 수 있다.
> 스스로 발견한 격차라는 점이 남이 지적한 것보다 훨씬 낫다.

### 2-4. 하지 않을 것 (그리고 그 이유를 남길 것)

**안 한 이유를 적어두는 것 자체가 이 프로젝트의 방식이다.** 무작정 늘리지 않는다.

| 항목 | 안 하는 이유 |
|---|---|
| Elasticsearch | 다국어 임베딩이 요구사항을 먼저 풀었다(ADR-0003 6-2) |
| Kafka / CDC(Debezium) | 챗봇 0.02 TPS. **애플리케이션 이벤트라는 중간 선택지**가 있다(P2-8-6) |
| 리랭커(cross-encoder) | i3-6100에서 지연 부담. Phase 1 실측 후 판단으로 미뤘다 |
| Redis 캐시 | 0.02 TPS에서 캐시 히트가 나지 않는다(ADR-0002 2-4) |
| 스케일아웃 | MAU 5,000 피크가 약 10 TPS. **처리량 근거가 없다.** 늘린다면 이유는 가용성 |
| Kubernetes | 위 스케일아웃의 도구다. 근거가 없으면 도구도 따라 나온다. 서버 1대·컨테이너 5개는 compose가 맞는 규모다 |
| 다단계 결재 | 스키마부터 바꿔야 하는데 서사 값어치가 낮다 |

## 3. 포폴 구성안 — 무엇을 어떤 순서로 이야기할 것인가

기능 목록이 아니라 **판단의 연쇄**로 구성한다. 한 꼭지가 다음 꼭지의 근거가 되게.

### 꼭지 1 — "느린 이유가 내 생각과 달랐다" (완료, 가장 강함)

브루트포스 10만 청크 5,165ms → `EXPLAIN`으로 병목이 **DB 내부가 아니라 클라이언트 전송(81%)**
→ 인덱스 없이 계산 위치만 DB로 이동 → **57ms(약 70배)** → 그다음에 HNSW → 1.7ms.

**포인트:** 인덱스를 먼저 만들지 않았다는 것. 대부분은 여기서 인덱스부터 붙인다.

### 꼭지 2 — "Elasticsearch를 도입하려다 안 하게 된 과정" (완료)

ADR-0003이 언어별 analyzer(Nori/ICU)로 다국어 검색을 계획 → 다국어 임베딩이 같은 요구를 먼저 충족
→ **도입 근거가 사라져서 취소.** 대신 정합성 문제를 만들지 않는 pgvector 단일 저장소.

**포인트:** 기술을 **안 쓴 결정**을 근거와 함께 말할 수 있다는 것.

### 꼭지 3 — "검증 장치 셋을 전부 통과한 버그" (완료, 2026-08-05)

`@Lob` → `validate` 통과, `SchemaValidationTest` 통과, 테스트 106개 통과 →
**데이터가 없어서** 아무도 몰랐다 → 시드를 만들자 첫 색인에서 즉사.

**포인트:** "테스트가 있다"와 "검증된다"는 다르다는 걸 자기 사례로 말할 수 있다.

### 꼭지 4 — "재고 나서 기능을 뺐다" (A2 완료 시)

번역본 색인이 교차언어의 성립 조건이 아님을 테스트가 이미 반증 →
비용(저장·임베딩 2배 + top-k 중복 점유) 대비 이득을 측정 → 결과에 따라 유지/제거.

**포인트:** 만든 기능을 **재고 나서 뺄 수 있는지**. 이게 되면 앞의 셋보다 인상적이다.

### 꼭지 5 — "RAG는 튜닝했는데 원본 테이블은 안 봤다" (2-3 진행 시)

`document_chunks` 인덱스 5개 vs `work_logs` 인덱스 1개 → 100만 건 실측 → `EXPLAIN` →
인덱스·커서 페이징·`pg_trgm`.

**포인트:** 새 기술에 쏠려 기본을 놓친 것을 **스스로 발견**했다는 것.

## 5. DB를 현업 수준으로 — 빠진 것

지금 이 프로젝트의 DB 작업은 **RAG 쪽만 깊고 나머지는 얕다.** 현업과의 차이는 기능이 아니라
**"문제가 생겼을 때 찾을 수 있는가"** 다.

**이미 현업스러운 것** — Flyway로 스키마가 코드에 있고, `validate`로 drift를 막고,
비관적 락 + 동시성 테스트가 있고, `EXPLAIN` 기반으로 인덱스를 결정한 기록이 있다.

| # | 빠진 것 | 왜 중요한가 | 지금 할 수 있는가 |
|---|---|---|---|
| D1 | **원본 도메인 인덱스 설계** | `work_logs`에 PK 하나. 연 100만 건 테이블 | ✅ 생성기로 즉시 실측 |
| D2 | **슬로우 쿼리 상시 관측** | `pg_stat_statements`를 **로드해놓고 쓰지 않는다.** 현업은 여기서 시작한다 | ✅ 이미 로드됨 |
| D3 | **N+1 전수 점검** | 채팅 하나만 진단하고 방치. 현업은 전 도메인을 훑는다 | ✅ 코드 전수 읽기 |
| D4 | **커넥션 풀 근거** | HikariCP 기본 10. **왜 10인지에 답이 없다** | ✅ 부하 테스트 필요 |
| D5 | **격리 수준 판단** | READ COMMITTED를 쓰는데 **고른 적이 없다.** 어떤 이상현상을 허용하는지 | ✅ 재현 테스트 |
| D6 | **데드락 재현·대응** | `deadlock_timeout` 설정만 있고 만들어본 적 없다 | ✅ 락 순서 뒤집기 |
| D7 | **무중단 스키마 변경** | `ALTER TABLE`이 100만 행에서 테이블을 잠근다. `CREATE INDEX CONCURRENTLY` | ✅ 실측 가능 |
| D8 | **파티셔닝 실행** | ADR-0007에 계획만. 해봐야 안다 | ✅ 데이터 확보됨 |
| D9 | 백업·복구 절차 | 현업 필수지만 포폴 값어치는 낮음 | △ |

## 6. 네트워크·OS 층위 — 이미 겪었는데 그 이름으로 쓴 적이 없다

**여기서 중요한 발상 전환 하나.** 이 프로젝트는 이미 OS·네트워크 문제를 여러 건 겪었다.
다만 전부 **"pgvector 이야기"나 "성능 이야기"로만 적혀 있고, 그 층위의 문제로 정리한 적이 없다.**
새로 만들 것보다 **이미 있는 것을 다시 쓰는 것**이 먼저다.

### 6-1. 이미 겪은 OS 문제 (재료가 이미 있다)

| 겪은 일 | 지금 어디에 적혀 있나 | OS 층위로 다시 쓰면 |
|---|---|---|
| HNSW 병렬 빌드 실패 | ADR-0006 8-2 "`/dev/shm` 64MB에 DSM이 안 들어감" | **컨테이너의 `/dev/shm` 기본 64MB**와 PostgreSQL 병렬 워커의 동적 공유메모리(DSM). `shm_size`를 키우면 되지만 512MB 컨테이너에서 OOM 위험 — **공유메모리와 컨테이너 메모리 제한의 상충** |
| `maintenance_work_mem` 부족 | ADR-0006 8-2 "28,363건에서 넘쳐 디스크 빌드로 전환, 4분56초 → 3분09초" | **작업 메모리가 넘칠 때 디스크로 흘리는(spill) 동작**과 그 비용 |
| 인덱스 195MB vs `shared_buffers` 128MB | ADR-0006 8-2 | **버퍼 캐시가 작업 집합보다 작을 때** 무슨 일이 나는가. 페이지 캐시와 이중 캐싱 |
| `Xmx400M` → 브루트포스 상한 10만 청크 | SERVICE-SCALE-ASSUMPTIONS 3-2 | **컨테이너 메모리 제한(cgroup)과 JVM 힙**의 관계 — 다만 이 전제 자체가 틀려 있었다. 아래 6-5 |
| i3-6100 2코어 → bge-m3 제외 | compose.yaml 주석 | **CPU 코어 수가 추론 처리량과 병렬 빌드를 동시에 제약**한 사례 |

> **이 다섯 개를 묶어 "512MB 컨테이너 안에서 벡터 검색을 굴리며 부딪힌 자원 한계"로 한 꼭지를 쓸 수 있다.**
> 전부 실제로 겪었고 숫자가 있다. 새로 만들 필요가 없다. **지금 없는 것은 경험이 아니라 그 서사다.**

### 6-1-1. 확인해보니 힙 설정이 적용된 적이 없었다 (2026-08-05 점검)

```yaml
compose.yaml:45   JAVA_OPTS=-Xmx400M -Xms256M
```
```dockerfile
Dockerfile:4      ENTRYPOINT ["java", "-Xmx512M", "-Xms256M", "-jar", "/app.jar"]
```

**`ENTRYPOINT`가 `JAVA_OPTS`를 참조하지 않는다.** exec 형식이라 셸을 거치지 않아 변수 전개도
일어나지 않는다. 환경변수는 설정되기만 하고 **완전히 무시되며, 실제 힙 상한은 512M이다.**

| 결과 |
|---|
| **① 메모리 산정 문서 전체가 틀린 전제 위에 있었다.** `Xmx400M` 기준으로 계산한 브루트포스 상한(약 10만 청크)이 **Phase 1 → 2 전환 트리거의 근거**였다 |
| **② 힙 상한이 컨테이너 제한과 같다.** 힙 밖(메타스페이스·코드 캐시·스레드 스택·다이렉트 버퍼·GC 구조체)이 얹히면 RSS가 512M을 넘어 **커널 OOM Killer가 SIGKILL** → `OutOfMemoryError` 없이 **종료코드 137로 조용히 사라진다.** 400M이었다면 있었을 112MB 여유가, 그 여유를 만들려던 설정이 무시되면서 사라졌다 |
| **③ 스왑이 열려 있다.** `MemorySwap = Memory × 2`(실측 확인). OOM 전에 스와핑으로 극심한 저하가 먼저 온다 — 메모리 접근이 많은 벡터 검색에서 최악이고, **진단은 더 어렵다** |
| **④ CPU 제한이 없다.** `NanoCpus=0`(실측). 2코어를 컨테이너 넷이 경쟁하고, TEI가 인덱싱 중 다 먹으면 PostgreSQL과 앱이 굶는다 |
| **⑤ `shm_size`가 여전히 없다.** ADR-0006 8-2가 지적한 `/dev/shm` 64MB 문제가 그대로다 |

> **이것은 이 프로젝트가 계속 잡아온 것과 정확히 같은 부류다** — `batch_size`가 `IDENTITY`에 막혀
> 무시되던 것, JPA 락 힌트를 MySQL이 무시하던 것, `@Lob`이 `validate`를 통과하던 것.
> **설정은 있는데 안 먹는다.** 층위만 애플리케이션에서 컨테이너로 옮겨갔다.

#### 무엇을 할 것인가

**1단계 — 고치기 (반나절)**

| 할 일 | 내용 |
|---|---|
| `JAVA_OPTS`를 실제로 먹게 | `ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar /app.jar"]`, 또는 Dockerfile의 `-Xmx`를 지우고 `JAVA_TOOL_OPTIONS`로 넘긴다 |
| 힙과 컨테이너 사이 여유 확보 | 고정 `-Xmx` 대신 `-XX:MaxRAMPercentage=70`. **컨테이너 크기가 바뀌어도 따라간다** |
| 스왑 차단 | `memswap_limit`을 `mem_limit`과 같게. 스와핑으로 느려지는 것보다 **빨리 죽는 편이 진단에 낫다** |
| CPU 제한 부여 | `cpus:`를 주고 근거를 남긴다. TEI가 DB를 굶기지 않게 |

**2단계 — 실측 (현업과의 진짜 차이)**

지금은 "메모리가 모자랄 것이다"를 **계산만** 했다. 현업은 **재고 안다.**

| 재는 것 | 방법 |
|---|---|
| 힙 밖이 얼마인가 | `jcmd VM.native_memory`(NMT). 다이렉트 버퍼가 얼마나 쓰이는지 — WebClient가 쓴다 |
| OOM이 어느 쪽인가 | 실제로 터뜨려보고 `docker inspect -f '{{.State.OOMKilled}}'`. **종료코드 137과 `OutOfMemoryError`의 차이를 자기 사례로** |
| 브루트포스 상한 검증 | 청크를 늘려가며 죽는 지점을 찾는다. **문서의 계산이 맞는지** |
| PostgreSQL 캐시 히트율 | `pg_statio_user_tables`. 인덱스 195MB + 테이블 195MB vs `shared_buffers` 128MB에서 실제 디스크 접근량 |

### 6-2. 이미 겪은 네트워크 문제

| 겪은 일 | 지금 어떻게 적혀 있나 | 네트워크 층위로 다시 쓰면 |
|---|---|---|
| 병목의 81%가 전송 | 6-3 "서버 실행 925ms vs JDBC 왕복 4,882ms" | **이게 사실 네트워크 이야기다.** 10만 행 × 1.5KB 벡터를 소켓으로 옮기는 비용. 계산을 데이터 쪽으로 옮긴 것이 해법이었다 |
| TEI 배치 호출 8배 | 6-1 "단건 99ms/건 vs 배치 12ms/건" | **왕복 횟수(RTT)가 지배**한다. 배치는 알고리즘이 아니라 왕복을 줄인 것 |

### 6-3. 확인해보니 실제로 어긋나 있었다 (2026-08-05 점검)

**추측으로 두지 않고 `nginx/conf.d/default.conf`, `WebClientConfig`, `WebSocketConfig`,
`compose.yaml`을 대조했다.** 셋이 나왔다.

#### N1 — WebSocket이 Nginx를 통과하지 못한다

```nginx
location / {
    proxy_pass http://dockin-app:8080;
    proxy_set_header Host $host;
    ...
    # proxy_http_version 1.1;                       ← 없다
    # proxy_set_header Upgrade    $http_upgrade;    ← 없다
    # proxy_set_header Connection "upgrade";        ← 없다
}
```

Nginx는 기본적으로 업스트림에 **HTTP/1.0**으로 말하고 `Upgrade`·`Connection` 같은
hop-by-hop 헤더를 걷어낸다. 위 세 줄이 없으면 **WebSocket 핸드셰이크가 성립하지 않는다.**

그리고 `WebSocketConfig`가 `addEndpoint("/ws")`만 하고 **`.withSockJS()`를 붙이지 않아**
HTTP 폴링 폴백도 없다. 즉 실패하면 그대로 실패다.

> **지금 동작하는 이유는 `dockin-app`이 8080을 직접 노출하고 있기 때문일 가능성이 크다.**
> 그러면 채팅만 리버스 프록시를 우회하는 셈이고, **TLS 종단·프록시 헤더·접근 제어가
> 그 경로에만 적용되지 않는다.** 의도한 구성인지부터 정해야 한다.

#### N2 — Nginx 60초가 Spring 120초를 이긴다

| 설정 | 값 |
|---|---|
| `spring.mvc.async.request-timeout` | **120,000ms** |
| Nginx `proxy_read_timeout` | **미설정 → 기본 60초** |

**120초는 Nginx를 통과하는 경로에서는 도달할 수 없는 값이다.** 60초에 끊긴다.
120초를 설정한 이유가 있었을 텐데(STT·번역·챗봇 같은 긴 작업) 그 의도가 무력화되어 있다.
게다가 Nginx가 끊으면 **504가 나가고 Spring은 여전히 작업 중**이라, 클라이언트가 재시도하면
같은 작업이 겹쳐 돈다.

#### N3 — WebClient에 타임아웃이 하나도 없다

`WebClientConfig`에 `HttpClient`·`responseTimeout` 설정이 없다. Reactor Netty 기본값은
**연결 타임아웃 30초, 응답 타임아웃 없음(무한)** 이다.

**연결은 됐는데 응답이 오지 않는 상황에서 영원히 매달린다.** 그리고 이게 겹치는 지점이 나쁘다 —
`ChunkIndexWriter.writePage()`는 **`@Transactional` 안에서 임베딩 HTTP 호출**을 한다
(그 클래스 주석이 스스로 인정한 부채다). 즉 TEI가 멈추면:

```
임베딩 호출이 무한 대기
  → 트랜잭션이 안 닫힌다
  → DB 커넥션이 반납되지 않는다
  → HikariCP 풀이 마른다
  → 배치가 아니라 서비스 전체가 멎는다
```

**단일 장애가 전파되는 경로**이고, 타임아웃 한 줄이 막는다.

> keep-alive 자체는 걱정하지 않아도 된다 — Reactor Netty는 기본으로 커넥션 풀을 쓴다.
> 문제는 재사용이 아니라 **포기할 시점이 없다는 것**이다.

#### N4 — 업로드 한계가 아슬아슬하게 맞물려 있다

| | 값 |
|---|---|
| Nginx `client_max_body_size` | 10M (**요청 전체**) |
| `spring.servlet.multipart.max-file-size` | 10MB (**파일 하나**) |
| `spring.servlet.multipart.max-request-size` | 10MB (요청 전체) |

숫자는 같지만 **멀티파트는 경계 문자열과 헤더가 붙어 요청 전체가 파일보다 크다.**
그래서 정확히 10MB인 파일은 Nginx에서 413으로 잘린다.

더 문제인 건 **그때 나가는 응답이 Nginx의 기본 HTML**이라는 점이다. `GlobalExceptionHandler`가
만드는 `ErrorResponseDto`(`status`/`message`/`timestamp`)와 형식이 다르다. P0-9에서
"클라이언트가 내 잘못과 서버 고장을 구분할 수 있게" 예외 처리를 표준화했는데,
**이 경로만 그 표준 밖에 있다.**

#### 아직 안 본 것

| # | 지점 |
|---|---|
| N5 | STOMP heartbeat 미설정 — 현장 와이파이에서 끊긴 걸 양쪽이 알 수 있는가 |
| N6 | Hikari `connection-timeout=30000`의 근거. 30초인 이유가 없다 |
| N7 | 부하 시 TIME_WAIT / 소켓 고갈 |

> **N1~N4는 전부 "설정 두 개가 서로 안 맞아서 조용히 잘못되는" 부류다.** 이 프로젝트가
> 지금까지 잡아온 것들(`ddl-auto=update`가 DDL 실패를 삼킨 것, JPA 락 힌트가 MySQL에서
> 무시된 것, `@Lob`이 validate를 통과한 것)과 정확히 같은 성격이고, **층위만 애플리케이션에서
> 인프라로 옮겨간 것**이다. 그래서 서사가 자연스럽게 이어진다.

### 6-4. 권하는 순서

| 순서 | 할 일 | 비용 |
|---|---|---|
| 1 | **N3 타임아웃 추가** — `responseTimeout` 한 줄. 풀 고갈로 서비스가 멎는 경로를 막는다 | 30분. **가장 급하다** |
| 2 | **N1 결정** — WebSocket을 Nginx로 통과시킬 것인가, 8080 직결을 유지할 것인가. 통과시킨다면 `proxy_http_version 1.1` + `Upgrade`/`Connection` 3줄 | 1시간 |
| 3 | **N2 타임아웃 정렬** — Nginx `proxy_read_timeout`을 Spring 120초와 맞추거나, 애초에 120초가 필요한지 재검토 | 1시간 |
| 4 | **N4 정렬** — Nginx를 12M 정도로 올려 Spring이 먼저 걸리게 한다. 그래야 오류 형식이 하나가 된다 | 30분 |
| 5 | **6-1을 문서로 정리** — 새 실측 0. 이미 있는 숫자를 OS 층위로 묶는 것뿐 | 반나절 |
| 6 | **D4 + N6를 한 번에** — 부하가 필요하므로 D1 실측과 같은 세션에서 | 하루 |

> **1~4는 합쳐도 하루가 안 되는데 전부 실제 결함이다.** 그리고 고치는 것보다
> **"어떻게 찾았는지"** 가 서사가 된다 — 설정 파일 넷을 대조한 것뿐이라는 점이 오히려 좋다.

> **하지 말 것: 일반론 공부를 포폴에 적는 것.** "TCP 3-way handshake를 이해하고 있습니다"는
> 아무 값어치가 없다. **"우리 TEI 호출이 keep-alive를 안 써서 배치 이득의 일부를 잃고 있었다"** 는
> 값어치가 있다. 차이는 **이 프로젝트 안에서 실제로 확인했는가**뿐이다.

## 7. DB·네트워크·OS 말고 또 무엇이 남았나

세 축을 정리하고 나서 남는 것을 훑었다. **의존성과 설정을 실제로 확인한 결과**이며,
빈칸이 큰 순서로 적는다.

### 7-1. 관측 가능성 — 가장 큰 빈칸

`build.gradle`에 **`actuator`도 `micrometer`도 없다.** 즉 다음이 전부 불가능하다.

| 없는 것 | 그래서 못 하는 것 |
|---|---|
| 헬스 체크 엔드포인트 | 앱이 살았는지 **밖에서 알 방법이 없다.** compose `healthcheck`는 DB에만 있다 |
| 메트릭 | **HikariCP 풀이 말랐는지, GC가 얼마나 도는지, 힙이 얼마인지** 볼 수단이 없다. P2-9-1(타임아웃 없음)이 실제로 터졌을 때 원인을 못 찾는다 |
| 요청 상관관계 | `traceId`가 **DTO 필드로만** 존재한다. FastAPI로 넘기고 `chat_history`에 저장하지만 **애플리케이션 로그에는 없다.** MDC를 안 쓰므로 로그를 봐도 어느 요청의 것인지 못 잇는다 |
| 구조적 로깅 | 평문 로그라 검색·집계가 안 된다 |

> **그런데 이 프로젝트에는 이미 관측 가능성 사고방식의 씨앗이 있다.**
> `chat_history.retrieval_mode`에 `VECTOR`/`KEYWORD`/`NONE`을 남겨
> **"요즘 답변이 이상하다"를 "언제부터 폴백이었다"로** 바꾼 것이 정확히 그것이다.
> 그 발상을 도메인 한 곳이 아니라 시스템 전체로 넓히는 일이고, 그래서 서사가 자연스럽다.

**할 일:** Actuator + Micrometer → `traceId`를 MDC에 넣어 로그 패턴에 포함 → 풀·GC·힙 메트릭 노출.
Prometheus/Grafana까지 갈지는 선택이지만, **`traceId`를 로그에 잇는 것만으로도 값어치가 크다** —
이미 있는 값을 쓰는 것뿐인데 지금은 절반만 쓰고 있다.

### 7-2. 복원력 — 폴백이 RAG에만 있다

`RetrievalService`는 임베딩 서버가 죽으면 키워드 검색으로 떨어진다. **설계가 좋은 부분이다.**
그런데 그 사고방식이 다른 외부 호출에는 적용되어 있지 않다.

| 외부 의존 | 실패하면 |
|---|---|
| TEI(임베딩) | ✅ 키워드 폴백 있음 |
| FastAPI(번역·STT·챗봇) | ❌ 폴백 없음. **타임아웃도 없다**(P2-9-1) |
| Redis(분산락) | ADR-0001이 "죽어도 DB가 최종 방어선"이라 했으나 코드로 확인된 적은 없다 |
| S3 | ❌ 확인 안 함 |

`resilience4j` 같은 의존성이 없으므로 **재시도·서킷 브레이커·벌크헤드가 전무**하다.
다만 **먼저 할 것은 라이브러리 도입이 아니라 타임아웃**이다 — 타임아웃 없는 서킷 브레이커는 의미가 없다.

### 7-3. 보안 — 확인된 것 셋

| # | 항목 | 상태 |
|---|---|---|
| S1 | **CORS가 전면 개방** | `WebConfig`와 `WebSocketConfig` **둘 다 `allowedOriginPatterns("*")`**. 후자에는 `//추후 포트 알면 변경` 주석이 남아 있다. 자격증명을 함께 허용하면 위험이 실질적이다 |
| S2 | **`JwtBlacklist` 인메모리** | 재배포하면 로그아웃한 토큰이 만료 전까지 되살아난다 (P2-5) |
| S3 | **시크릿 관리** | `.env`는 커밋되지 않지만, **배포 환경에 어떻게 전달할 것인가**에 답이 없다. AWS로 가면 Secrets Manager / SSM Parameter Store 결정이 필요 |

> S1은 **한 줄 고치는 일인데 방치된 티가 가장 많이 나는 항목**이다. 주석이 그걸 자백하고 있다.

### 7-4. 테스트 격리 — skip 24개가 CI에서 안 돈다

`testcontainers` 의존성이 없다. 그래서 DB가 필요한 테스트는 **개발자 로컬 PostgreSQL에 의존**하고,
CI에서는 통째로 skip된다(P0-11 / P0-12가 같은 이야기).

Testcontainers를 쓰면 CI에서 진짜 PostgreSQL + pgvector를 띄워 벡터 테스트까지 돌릴 수 있고,
P0-7이 "CI에 DB를 주지 않기로" 한 두 이유(스위치가 하나뿐, `lock_timeout` 서버 파라미터를 못 줌)가
**둘 다 해소된다** — 컨테이너 인자를 코드로 줄 수 있기 때문이다.

> **이건 단순 개선이 아니라 P0-7의 결정을 뒤집는 근거**라서 서사가 된다.

### 7-5. 배포 — CI는 있고 CD는 없다

P0-7에서 테스트 CI는 복구했으나 배포는 의도적으로 복구하지 않았다(삭제된 워크플로가 실패한
이유가 테스트가 아니라 Docker Hub 푸시와 EC2 배포였고, 한 잡에 묶여 있었다).

AWS로 다시 올린다면 필요한 것: 무중단 배포(헬스 체크 기반 → **7-1이 선결**), 롤백 절차,
마이그레이션과 배포의 순서(Flyway가 기동 시 도는데 **인스턴스가 둘이면 동시에 돈다**).

### 7-6. 우선순위

| 순서 | 이유 |
|---|---|
| 1. **P2-9-1 타임아웃** | 서비스 전체가 멎는 경로. 한 줄 |
| 2. **S1 CORS** | 한 줄, 방치 티가 가장 남 |
| 3. **7-1 Actuator + MDC `traceId`** | 이후 모든 진단의 전제. 이미 있는 값을 절반만 쓰고 있다 |

| 6. 7-2 복원력, 7-5 배포 | 위가 된 다음 |

## 8. 이 서비스의 메인 기능은 무엇인가

**포폴을 한 문장으로 소개해야 한다면 무엇을 말할 것인가.** 이걸 정하지 않으면
기능 목록을 나열하게 되고, 그러면 0절이 경계한 "평범한 프로젝트"가 된다.

### 8-1. 메인은 "다국어 현장을 위한 교차언어 작업일지 검색"이다

> 조선소에는 한국어를 못 읽는 근로자가 있다. 작업일지는 한국어로 쌓인다.
> **베트남어로 물어도 한국어 작업일지에서 답을 찾아준다.**

이걸 메인으로 두는 이유가 셋이다.

| 이유 | 내용 |
|---|---|
| **도메인이 다국어를 진짜로 요구한다** | 다국어를 "붙인" 게 아니라 **없으면 서비스가 성립하지 않는다.** 흔한 RAG 포폴은 다국어가 장식인데 여기서는 요구사항이다 |
| **기술적 깊이가 여기 몰려 있다** | pgvector 이관, HNSW, 브루트포스 기준선, 청킹 크기 산정, 권한 선필터 — 실측이 붙은 결정이 전부 이 축에 있다 |
| **"안 한 결정"도 여기서 나온다** | Elasticsearch를 검토하다 임베딩으로 대체한 기록(ADR-0003 6-2). 도입한 이야기보다 **취소한 이야기**가 드물다 |

### 8-2. 그중에서도 가장 강한 단일 포인트 — 권한이 걸린 RAG

**대부분의 RAG 포폴에는 접근 제어 개념이 없다.** 문서를 전부 한 인덱스에 넣고 유사도만 본다.
이 프로젝트는 그러지 않았고, 그 이유를 코드와 문서에 남겼다.

- **벡터 유사도만으로는 접근 제어가 안 된다** — 검색 결과를 그대로 프롬프트에 넣으면
  **권한 없는 사용자에게 남의 작업일지가 노출된다.** `Visibility`가 그 방어선이다.
- **후필터가 아니라 선필터로 구현했다** — 후필터는 요청한 k보다 적게 반환되어
  "내가 못 보는 문서가 존재한다"는 사실이 유출되고, 검색어를 바꿔가며 반복하면
  문서의 존재 윤곽을 그릴 수 있다.
- **폴백도 같은 권한 모델을 쓴다** — 기존 키워드 검색을 그대로 폴백에 썼다면
  **장애 상황에서만 남의 작업일지가 새어 나갔을 것이다.**

> 이 세 문장은 **면접에서 그대로 쓸 수 있는 밀도**다. 그리고 셋 다 "구현했다"가 아니라
> **"이렇게 하면 무엇이 새는가"를 먼저 말한다는 점**이 다르다.

### 8-3. 보조 축 — 근태 동시성

ADR-0001(분산락 + 비관적 락 + 멱등성)과 P2(휴가 승인 이벤트 → 근태 반영, 자정 배치, 근무일 캘린더)는
**깊이는 있지만 소재가 흔하다.** 메인으로 내세우면 다른 지원자와 구분되지 않는다.

다만 **"서비스가 실제로 돌아간다"는 증거**로는 값어치가 크고,
`Attendance.clockInTime`을 nullable로 바꾼 판단이나 배치에 `Clock`을 주입한 것처럼
**작은 결정에도 이유가 붙어 있다**는 걸 보여주는 데 좋다. 두 번째 꼭지로 둔다.

### 8-4. 채팅 — 지금은 넣으면 감점이지만, 세 번째 축이 될 수 있다

**처음에는 "얕으니 빼라"고 적었으나 실제 코드를 확인하고 판단을 바꿨다.** 얕지 않다:
STOMP `CONNECT`에서 JWT 검증, `lastReadTime` 기반 읽음 처리, 안읽음 카운트,
`last_message_content`/`last_message_at` 비정규화, `(room_id, sent_at)` 인덱스가 모두 있다.

문제는 깊이가 없는 게 아니라 **정합성이 어긋나 있다는 것**이고, 그건 오히려 소재가 된다.

#### 8-4-1. 확인된 정합성 결함 넷

| # | 문제 | 내용 |
|---|---|---|
| 1 | **N+1 (확정)** | `ChatRoomService`가 `chatRoomsPage.map(room -> countByChatRoomsRoomIdAndCreatedAtAfter(...))` — **방마다 COUNT 쿼리**를 날린다. 방 20개면 21쿼리. ADR-0002 2-2가 진단만 하고 방치한 그것이다 |
| 2 | **시계가 둘이다** | `ChatMessages.sentAt`은 `@PrePersist`의 **애플리케이션 시각**, `last_message_at`과 `last_read_time`은 네이티브 쿼리의 **DB `NOW()`**. 두 시계가 어긋나면 읽음 경계와 최신 메시지가 함께 틀어진다 |
| 3 | **읽음 기준이 시각이다** | `createdAt > lastReadTime`으로 안읽음을 센다. 같은 시각에 도착한 메시지의 경계가 모호하고, 2번과 겹치면 **읽은 것을 안 읽었다고 세거나 그 반대**가 된다. 정확한 기준은 `last_read_message_id`(단조 증가 PK) |
| 4 | **`last_message_content` 경합** | 동시에 두 메시지가 오면 UPDATE 순서 보장이 없다. 방 목록의 "마지막 메시지"가 실제 마지막이 아닐 수 있다 |

> **2·3번이 특히 좋은 소재다.** "시각으로 상태를 판단하면 안 되는 이유"는 근태 배치에 `Clock`을
> 주입한 판단과 같은 계열이고, 해법(단조 증가 ID 기준)은 인덱싱에서 OFFSET을 커서로 바꾼
> P1-13과 같은 발상이다. **세 도메인이 같은 원리로 묶인다.**

#### 8-4-2. FCM — 없으면 채팅이 반쪽이다

푸시 알림이 전혀 없다(의존성·코드 모두 확인). WebSocket은 **앱이 떠 있을 때만** 동작하므로
앱을 내리면 메시지를 받지 못한다. 조선소 현장에서 앱을 계속 켜두지 않는다.

**FCM이 포폴이 되는 이유는 붙이기 어려워서가 아니라 그 안에 판단이 있어서다.**

| 문제 | 내용 |
|---|---|
| **트랜잭션 경계 (핵심)** | 메시지 저장 트랜잭션 안에서 FCM을 호출하면 **롤백돼도 알림은 이미 나간다.** 없는 메시지의 알림이 뜬다. `@TransactionalEventListener(AFTER_COMMIT)`이 답이다 |
| **중복 알림** | WebSocket으로 이미 받았는데 FCM도 오면 두 번이다. "이 사용자가 지금 연결돼 있는가"를 알아야 하는데, `StompHandler`가 `CONNECT`/`DISCONNECT`를 잡고 있어 **연결 상태를 관리할 자리가 이미 있다** |
| **토큰 생명주기** | 기기별 토큰, 만료·갱신, 로그아웃 시 삭제, 다기기 |
| **도메인 연결** | `WorkShift`가 있으니 **야간 근무자에게 새벽 알림을 보낼 것인가**가 실제 판단이 되고, `language_code`가 있으니 알림 본문 다국어가 붙는다 |

> **트랜잭션 경계가 이 항목의 백미다.** 이건 P2에서 내린 판단과 **정반대**다 —
> 휴가 승인 → 근태 반영은 **동기 리스너로 같은 트랜잭션**에 뒀다. 근태 반영이 실패하면
> 승인도 함께 롤백돼야 하기 때문이다.
>
> **같은 도구(`ApplicationEvent`)를 정반대로 쓰는 이유를 설명할 수 있으면 매우 강하다.**
> 기준은 하나다 — **"함께 실패해야 하는가."** 근태는 그래야 하고, 알림은 그러면 안 된다.

#### 8-4-3. 레벨과 비용

| 레벨 | 내용 | 비용 | 평가 |
|---|---|---|---|
| **0 (지금)** | WebSocket이 Nginx를 통과 못함, N+1, CORS `*` | — | **넣으면 감점** |
| **1** | 결함 제거 (P2-9-2 / N+1 / CORS) | 하루 | 감점은 면한다. 가점은 없다 |
| **2 ★** | **정합성 축** — 읽음 기준을 `message_id`로, 시계 일원화, 순서 보장, 재연결 시 유실 없는 동기화 | 2~3일 | **한 꼭지가 된다** |
| **3 ★** | **FCM** — 트랜잭션 경계 + 중복 억제 + 토큰 생명주기 | 3~4일 | 레벨 2와 합치면 **메인급** |
| 4 | 다중 인스턴스 (`enableSimpleBroker` → Redis Pub/Sub) | 1주+ | **문서와 충돌한다.** ADR-0004가 "스케일아웃 근거 없음"이라 했으므로, 하려면 이유를 처리량이 아니라 **가용성(무중단 배포)** 으로 잡아야 한다 |

**2 + 3을 묶으면 일주일 정도에 "실시간 메시지 전달의 정합성"이라는 축이 생긴다.**
그리고 그것이 벡터 검색(권한)·근태(상태 정합성)와 **같은 사고방식**이라 세 축이 따로 놀지 않는다.

#### 8-4-4. 깊게 판다면 — 중심 질문 하나로 모은다

레벨 2·3을 나열하면 할 일 목록이지 서사가 아니다. **하나의 질문을 중심에 두면 나머지가 딸려온다.**

> ### "메시지가 유실되지 않는다는 것을 어떻게 보장하고, **어떻게 증명하는가**"

이걸 중심으로 두는 이유가 셋이다.

| 이유 | 내용 |
|---|---|
| **도메인이 요구한다** | 선박 내부·밀폐공간·도크는 네트워크가 끊긴다. **"끊긴다"가 예외가 아니라 일상**이다. 억지로 만든 문제가 아니다 |
| **하위 문제가 전부 딸려온다** | 아래 표 |
| **증명할 수 있다** | 연결을 강제로 끊고 유실을 재는 실험이 가능하다. **"유실 0건"을 숫자로** 말할 수 있고, 그게 이 프로젝트의 방식이다 |

| 하위 문제 | 유실 관점에서 |
|---|---|
| 순서 (P2-12-2 시계가 둘) | 순서를 모르면 **무엇이 빠졌는지도 모른다** |
| 재연결 동기화 (P2-12-5) | 끊긴 동안의 것을 어디서부터 받을 것인가 |
| 중복 (재시도) | 유실을 막으려 재시도하면 중복이 생긴다 — **같은 동전의 양면** |
| 읽음 경계 (P2-12-3) | 같은 축으로 판단해야 어긋나지 않는다 |
| FCM (P2-12-6) | 연결이 아예 없을 때의 전달 |
| heartbeat | 끊긴 것을 **언제** 아는가 |

##### 핵심 설계 결정 한 줄

> **시각(clock)을 버리고, 서버가 부여한 단조 증가 시퀀스를 신뢰의 축으로 삼는다.**

순서도, 재연결 커서도, 읽음 경계도, 중복 판별도 **전부 같은 축**이 된다.
지금은 `sent_at`(애플리케이션 시각)과 `NOW()`(DB 시각)가 섞여 있고, 그걸 하나로 통일하는 것이다.
벡터 검색의 **"권한은 선필터로"**, 근태의 **"함께 실패해야 한다"** 와 같은 급의 결정이다.

##### 진짜 함정 — 여기까지 가면 깊다

**`message_id`가 `IDENTITY`라 "커밋 순서 ≠ ID 순서"다.** 시퀀스는 트랜잭션 밖에서 발급된다.

```
트랜잭션 A:  id=10 발급 → (느림) ─────────→ 커밋
트랜잭션 B:  id=11 발급 → 커밋                      ← 11이 먼저 보인다
```

이때 클라이언트가 조회하면 11까지 받고 `lastSeen = 11`로 갱신한다.
**그 뒤에 10이 커밋되면 영영 받지 못한다.** 재연결 커서를 ID로 잡았는데
**바로 그 커서가 구멍을 만드는** 셈이다.

| 대응 | 대가 |
|---|---|
| 방 단위 시퀀스를 **트랜잭션 안에서** 부여 | 방마다 직렬화 → 경합. 다만 채팅방은 원래 순서가 필요하므로 받아들일 만하다 |
| 따라잡기에 안전 여유(watermark)를 둔다 | 구현이 단순, 지연이 붙는다 |
| 갭 감지 후 재조회 | 클라이언트 복잡도가 올라간다 |

> **어느 것을 고르든 "왜 그것을 골랐나"가 곧 서사다.** 근태에서 비관적 락을 고른 판단,
> RAG에서 선필터를 고른 판단과 같은 결의 이야기다.

##### 증명할 것 (실측)

| 재는 것 | 방법 |
|---|---|
| 강제 끊김 하 유실률 | N건 전송 중 연결을 끊었다 붙이고, **수신 집합과 DB를 대조** |
| **ID 역전이 실제로 나는가** | 동시 전송 부하를 걸고 커밋 순서와 ID 순서를 비교 — **함정이 이론이 아님을 보이는 것** |
| 재연결 따라잡기 지연 | 끊긴 동안 쌓인 M건을 따라잡는 시간 |
| 중복률 | 재시도 시 같은 메시지가 두 번 저장되는가 |

##### 순서

| 순서 | 할 일 | 비고 |
|---|---|---|
| 1 | **시계 일원화** (P2-12-2) — 모든 판단을 `message_id` 축으로 | 나머지의 전제 |
| 2 | **읽음 기준을 `last_read_message_id`로** (P2-12-3) | 1의 첫 적용 |
| 3 | **재연결 동기화** (P2-12-5) — 마지막 수신 ID 이후를 따라잡는 경로 | |
| 4 | **ID 역전 실측** (P2-12-7) — 실제로 나는지 확인하고 대응 선택 | **가장 깊은 지점** |
| 5 | 중복 억제 — 클라이언트 생성 키 기반 멱등성 | |
| 6 | **FCM** (P2-12-6) — 연결이 없을 때 | |
| — | N+1(P2-12-1)은 병렬로 아무 때나 | 위와 독립 |

**1~4가 핵심이고 3~4일이다.** 5~6까지 하면 일주일 정도이며, 그 시점에
"실시간 메시지 전달의 정합성"이 벡터 검색·근태와 나란한 축이 된다.

### 8-5. 세 축이 하나의 원리로 묶인다

메인 축을 셋으로 잡으면 각각이 다른 기능인데 **판단의 원리는 같다.**

| 축 | 질문 | 답 |
|---|---|---|
| 교차언어 RAG | 유사도만으로 접근 제어가 되는가 | 안 된다 → **선필터**, 폴백도 같은 권한 모델 |
| 근태·휴가 | 상태가 두 곳에 있을 때 어긋나지 않으려면 | **함께 실패해야 한다** → 동기 이벤트 |
| 채팅 | 시각으로 상태를 판단해도 되는가 | 안 된다 → **단조 증가 ID**, 알림은 반대로 `AFTER_COMMIT` |

> **셋 다 "이렇게 하면 무엇이 어긋나는가"에서 출발한다.** 기능 셋을 나열하는 것보다
> 이 원리를 앞세우고 사례 셋을 드는 편이 강하다.

### 8-5. 한 문장 소개안

> **"조선소 다국어 현장의 작업일지를 언어에 상관없이 검색할 수 있게 만들고,
> 그 과정에서 내린 결정을 전부 실측으로 뒷받침한 프로젝트."**

앞 절이 기능, 뒤 절이 차별점이다. **뒤 절이 없으면 흔한 프로젝트가 된다.**

## 9. 실행 순서 (전 축 통합)

각 절에 우선순위가 흩어져 있어 하나로 모은다. **위 다섯 개는 합쳐서 하루가 안 되는데
전부 실제 결함**이다.

| 순서 | 항목 | 근거 | 비용 |
|---|---|---|---|
| 1 | **P2-9-1** WebClient 타임아웃 | 임베딩 서버가 멈추면 트랜잭션이 안 닫혀 **Hikari 풀이 마르고 서비스 전체가 멎는다** | 30분 |
| 2 | **P2-11-1** CORS `*` 제거 | 두 곳 다 전면 개방. `//추후 포트 알면 변경` 주석이 방치를 자백한다 | 30분 |
| 3 | **P2-10-1** 힙/컨테이너 정리 | `JAVA_OPTS`가 무시되어 힙 상한이 컨테이너 제한과 같다. **종료코드 137로 조용히 죽는 경로** | 1시간 |
| 4 | **P2-9-2~4** Nginx 정합 | WebSocket 통과, 타임아웃 60 vs 120, 업로드 413 응답 형식 | 2시간 |

앞을 빨리 끝내고 뒤에 시간을 쓰는 것이 맞다.

> **관통하는 원칙 하나** — 지금까지 잡은 결함 대부분이 **"설정은 있는데 안 먹는다"** 였다:
> `batch_size`가 `IDENTITY`에 막힌 것, JPA 락 힌트를 MySQL이 무시한 것, `data.sql`이
> 실행되지 않던 것, `@Lob`이 `validate`를 통과한 것, `JAVA_OPTS`가 참조되지 않던 것.
> **선언과 실제를 대조하는 습관**이 이 프로젝트가 실제로 익힌 것이고, 그게 서사의 축이다.
