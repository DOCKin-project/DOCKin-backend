# ADR-0003: 검색 도메인 확장 로드맵 (다국어 작업일지 검색)

- 상태: **로드맵. 다만 전제가 두 가지 바뀌었다 — 6절을 먼저 볼 것**
  (① 저장소가 MySQL → PostgreSQL, ② 다국어 검색이 이 로드맵이 아니라 벡터 검색으로 해결됨)
- 대상 코드: `Work_logsRepository.searchWorkLogs`, `work_log_translations` 테이블
- 작성 목적: "검색"을 별도 포트폴리오 소재로 밀 경우 어디까지 갈 수 있는지, 각 단계에서 무엇을 근거로 다음 단계로 넘어가는지 기록한다. ADR-0001의 원칙(숫자를 지어내지 않는다)을 그대로 따른다.

## 1. 전제 — 이건 "필요해서"가 아니라 "시연을 위한" 확장이다

DOCKin은 이미 심사가 끝난 해커톤 프로젝트라 실사용자의 실제 다국어 검색 트래픽이 없다. 그래서 이 로드맵은 실제 운영 문제를 푸는 게 아니라, Shadowfit에서 1억 행을 합성 적재해 실측했던 것과 같은 방식으로 **합성 데이터로 문제 상황을 재현하고 성능을 실측하는 시연 프로젝트**로 진행한다. 실사용 트래픽 여부와 인프라 예산 제약은 확인 결과 없는 것으로 보고, 로컬/개인 환경에서 자유롭게 구성 가능하다고 가정한다.

## 2. 현재 상태

```java
@Query("SELECT w FROM Work_logs w WHERE w.title LIKE %:keyword% OR w.logText LIKE %:keyword%")
Page<Work_logs> searchWorkLogs(@Param("keyword") String keyword, Pageable pageable);
```

- 양쪽 와일드카드 LIKE라 B-Tree 인덱스를 못 타고, 데이터가 늘어나면 풀스캔이 된다(ADR-0002 2-2 참고).
- `work_log_translations` 테이블에 로그별 다국어 번역본이 이미 저장되고 있지만, 검색은 원문(`title`, `logText`)에만 걸려 있어 번역본은 검색 대상이 아니다.

## 3. 단계별 로드맵

### 3-1. MySQL 안에서 최대치 — ngram FULLTEXT

- `title`, `logText`에 `WITH PARSER ngram` FULLTEXT 인덱스 적용.
- `EXPLAIN`으로 `type=ALL`(풀스캔) → FULLTEXT 인덱스 사용으로 바뀌는 것을 확인하고, 합성 데이터 규모별(예: 1만/10만/100만 건) 응답 시간을 실측해 표로 남긴다.
- **여기서 오검색/미검색 사례를 실제로 수집한다.** 예: ngram은 형태소 인식이 없어 "일지"로 검색했는데 의미 없는 부분 매칭이 늘어나는 경우 등. 이 사례가 다음 단계로 넘어가는 근거가 된다.

### 3-2. 다국어 통합 검색 필요성 확정

- 3-1에서 확보한 한계를 바탕으로, "어느 언어로 검색해도 원문/번역본에서 찾아준다"는 기능 요구사항을 명시한다.
- 이 요구사항이 없으면 3-3(Elasticsearch)으로 넘어갈 근거가 없다 — 여기서 멈추고 ngram으로 마무리하는 것도 유효한 결론이다.

### 3-3. Elasticsearch 도입

- `work_logs` + `work_log_translations`를 언어별 필드(`title_ko`, `title_vi`, `title_en` ...)로 인덱싱.
- 언어별 analyzer 적용: 한국어는 Nori, 영어권은 standard, 그 외는 ICU 등으로 구성.
- MySQL → ES 동기화 방식 선택: 배치(스케줄러로 주기 동기화) vs CDC(Debezium). 개인 프로젝트 규모에서는 배치가 구현·운영 부담이 적어 기본값으로 추천, CDC는 "왜 지금은 안 썼는지"를 근거와 함께 남긴다.
- 검색 API를 MySQL 쿼리에서 ES 쿼리로 전환.

### 3-4. 정합성 문제 (가장 기술적으로 밀도 있는 구간)

- MySQL(원본)과 ES(검색 인덱스)가 분리되는 순간 발생하는 문제: 동기화 지연 동안의 조회 불일치, 동기화 실패 시 재인덱싱.
- ES 장애 시 검색 기능을 MySQL LIKE/FULLTEXT로 폴백시키는 경로 설계 — ADR-0001에서 "Redis가 죽어도 DB가 최종 방어선"이라는 사고방식을 여기서도 그대로 재적용한다. 즉 ES는 성능 최적화 계층, MySQL은 정합성 최종 보증 계층으로 역할을 분리한다.

### 3-5. 검색 품질/운영 (선택, 우선순위 낮음)

- 오타 허용(fuzzy) 검색, 관련도 스코어(BM25) 튜닝, 인덱싱 배치 실패 모니터링.
- 여기까지는 시간이 남을 때만 — 3-1~3-4만으로도 완결된 아키텍처 결정 서사가 나온다.

## 4. 경쟁 서비스 대비 포지션

롯데건설(AI 다국어 번역, 20개 언어)·GS건설(Xi-Voice, 120개 언어)·현대건설(HPMS) 모두 **번역** 자체는 이미 대형 R&D로 상용화했지만, 검색 시스템 자체를 다룬 사례는 조사 범위에서 확인되지 않았다. 즉 "번역했다"는 임팩트는 이미 시장에 있으므로 약하고, "번역된 다국어 데이터를 검색 가능하게 만드는 아키텍처를 설계했다"는 게 이 로드맵의 실질적 차별점이다.

## 5. 결론 (작성 당시)

- 최소 실행선: 3-1(ngram FULLTEXT) + 3-2(요구사항 확정)만으로도 EXPLAIN 기반 개선 서사가 완성된다.
- 확장 실행선: 3-3~3-4(Elasticsearch + 정합성 설계)까지 가면 ADR-0001과 같은 급의 아키텍처 의사결정 문서가 하나 더 생긴다.
- 3-5는 시간 여유가 있을 때만 손댄다.
- 모든 단계에서 숫자(응답시간, 정확도, 인덱스 크기)는 합성 데이터로 직접 실측한 값만 기록하고, 추정치는 "[실측 필요]"로 표시한다(ADR-0001 관례).

## 6. 갱신 (2026-08-05) — 전제 두 가지가 바뀌었다

### 6-1. 저장소가 PostgreSQL이다

3-1의 **`WITH PARSER ngram` FULLTEXT는 MySQL 전용 문법이라 더 이상 그대로 쓸 수 없다.**
PostgreSQL의 대응물은 둘이며 성격이 다르다.

| | 용도 |
|---|---|
| `pg_trgm` (GIN/GiST) | 3-gram 부분 일치. **양쪽 와일드카드 `LIKE '%키워드%'`를 인덱스로 태울 수 있다** — 2절이 지적한 풀스캔 문제의 직접적 해법 |
| `tsvector` / `tsquery` (GIN) | 어휘 기반 전문검색 + BM25 성격의 랭킹. 다만 **기본 파서에 한국어 형태소 분석이 없다** |

즉 3-1의 목표(풀스캔 제거)는 `pg_trgm`으로, 랭킹까지 원하면 `tsvector`로 간다.
**ngram이 형태소를 모른다는 3-1의 한계 지적은 `pg_trgm`에도 그대로 적용된다** — 엔진만 바뀌고 성질은 같다.

### 6-2. 다국어 검색은 이 로드맵이 아니라 벡터 검색으로 해결됐다

3-2가 "3-3으로 넘어갈 근거"로 삼았던 요구사항 — *어느 언어로 검색해도 원문/번역본에서 찾아준다* — 는
**ADR-0006의 다국어 임베딩으로 이미 성립한다.** 베트남어·영어 질의로 한국어 원문을 찾는 것을
`CrossLingualRetrievalTest`로 확인했다(영어 recall@1 5/5, 베트남어 4/5).

3-3이 계획했던 **언어별 analyzer 구성(Nori/ICU)이 통째로 불필요해졌다.**
같은 벡터 공간에 넣는 것만으로 언어 경계가 사라지기 때문이다.

### 6-3. 그래서 각 단계의 현재 지위

| 단계 | 지위 |
|---|---|
| 3-1 ngram FULLTEXT | **살아 있다.** 엔진만 `pg_trgm`/`tsvector`로 바뀐다. 현재 `searchWorkLogs`와 RAG 키워드 폴백이 모두 양쪽 와일드카드 LIKE라 인덱스를 못 탄다 |
| 3-2 다국어 요구사항 확정 | **충족됨** (벡터 검색으로) |
| 3-3 Elasticsearch | **보류.** 도입 근거였던 다국어 analyzer가 사라졌다 — 6-4 참고 |
| 3-4 정합성 설계 | **소멸.** PostgreSQL 전면 이전으로 원본과 벡터가 한 트랜잭션에 묶인다. 사이드카를 택했다면 그대로 남았을 문제다 |
| 3-5 검색 품질/운영 | 유지 (우선순위 낮음) |

### 6-4. pgvector를 도입했으니 Elasticsearch는 안 쓰는가

**지금 규모에서는 도입 근거가 없다.** 다만 "벡터 검색이 ES를 대체한다"는 말은 정확하지 않다 — 겹치는 영역은 일부다.

| ES가 잘하는 것 | PostgreSQL에서 되는가 |
|---|---|
| kNN 벡터 검색 | ✅ pgvector로 대체됨 |
| 언어별 analyzer 기반 다국어 검색 | ✅ 다국어 임베딩으로 **필요 자체가 사라짐** |
| BM25 키워드 검색·랭킹 | △ `tsvector`로 가능. 다만 **한국어 형태소 분석기가 없다**(ES는 Nori 보유) |
| 오타 허용(fuzzy), 동의어 사전 | △ `pg_trgm` 유사도로 부분 대체. 사전 관리 기능은 없다 |
| 하이라이팅, 패싯/집계 | △ 직접 구현해야 한다 |
| 수억 문서 분산 검색 | ❌ 이 프로젝트 상한은 청크 10만이라 해당 없음 |

**결정: 도입하지 않는다.** 이유는 "pgvector가 더 좋아서"가 아니라 셋이다.

1. **도입 근거였던 항목(다국어 analyzer)이 다른 방법으로 해결됐다.** 3-3의 존재 이유가 그것이었다.
2. **저장소를 하나 더 두면 정합성 문제가 새로 생긴다.** 3-4가 통째로 다시 살아난다.
3. **규모가 근거를 대지 못한다.** 챗봇 0.02 TPS, 청크 상한 10만. ES의 강점은 이보다 훨씬 큰 규모에서 나온다.

**하이브리드 검색(BM25 + 벡터)도 ES 없이 간다.** PostgreSQL 안에서 `tsvector`와 `vector`를 같은 트랜잭션에서 조합할 수 있다. 벡터가 못 잡는 정확 일치(장비 코드 `P-1204`, 조항 번호)를 키워드 경로가 받쳐주는 구조이며, 이것이 3-1이 살아 있는 이유다.

**뒤집힐 조건**은 명시해둔다 — 한국어 형태소 분석 품질이 검색 실패의 주원인으로 실측되거나, 하이라이팅·패싯이 요구사항이 되거나, 문서 규모가 백만 단위를 넘어설 때.
