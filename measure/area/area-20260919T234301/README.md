## 읽는 법

1. **가장 큰 발견은 A↔B가 아니라 O→A다 — #127이 검색의 최악 경로를 바꿨다.** #127 이전(O) 검색은 `user_id` Bitmap Heap Scan + Filter + top-N 정렬이라 키워드가 뭐든 구역 행을 한 번 읽고 끝났다(240~550ms, 병렬). #127 이후(A) 플래너는 정렬 인덱스 V10을 최신순으로 걸으며 `LIKE`를 거르고 21건이 모이면 멈추는 계획을 고른다 — 흔한 키워드에선 142행 만에 끝나 100배 빠르지만(338→3.7ms), **구역에 없는 키워드면 100만 행을 끝까지 걷는다**: 힙 페이지를 인덱스 순서로 100만 번 두드려 1g에서 **2.1s**(O 0.55s의 4배), 512m에선 힙이 캐시에 안 들어가 **31~47s**(O의 60~90배). PR #127이 잰 12만 행에서 310ms였던 그 "없는 키워드" 줄이 100만 행에서 이렇게 된다. #127을 되돌릴 일은 아니다 — 목록은 358→1.7ms, 흔한 검색은 100배다 — 검색의 **"없는 키워드" 경로에 상한이 필요하다**는 뜻이다. → #154.
2. **비정규화(B)는 그 최악을 못 푼다.** 구역 인덱스를 걸으니 구역 몫만 걷지만(A1 50%면 50만 행), 그것도 끝까지다: 1g에서 2.1→1.5s, 512m에선 오히려 병렬이 빠져 45~53s. 구역 비율만큼 줄 뿐이고 "없는 키워드 = 구역 전체 걷기"는 같다.
3. **B가 이기는 자리는 셋이고, 셋 다 절대값이 작거나 특수하다.** ① 소구역(1%) 목록 6~7ms→0.7ms(10배) — A는 남의 행 2,000개를 걷고 users를 2,000번 찾는다(Memoize 500 미스). 구역이 작을수록, 즉 신설 구역일수록 비례해서 커진다(0.1%면 2만 행 걷기 `[추정]`). ② 소구역 흔한 검색 77→1.7ms(46배), 같은 이유. ③ A0 희귀 검색 1,284~2,576→297~547ms — A는 조인이라 `user_id` 비트맵을 못 만들고 **전체 Seq Scan**으로 떨어지고(1g에서도 722ms, O 290ms보다 느리다), B는 O처럼 구역 비트맵으로 돌아간다. **큰 구역(17%·50%) 목록·흔한 검색에서는 A·B 모두 1~3ms — 차이가 없다.** #118의 무릎(초당 12명·DB CPU)은 A로 이미 끝났다(53ms×9,349블록 → 1.7ms×471블록).
4. **이관 비용이 B의 진짜 대가다.** 백필 UPDATE 100만 행 100s 동안 힙이 두 배가 되고, 그걸 돌리려면 `VACUUM FULL`(전체 잠금 1분) 또는 `pg_repack`. `docs/db/online-ddl.md` ②(nullable → 배치 채움 → NOT NULL)로 하면 잠금은 없지만 힙 두 배는 같다. 거기에 작성자 구역이 바뀌면 옛 일지의 구역을 어떻게 볼지(작성 당시 값으로 굳나, 따라가나) 결정과 쓰기 경로 한 줄이 든다.
5. **512m vs 1g는 #83의 재확인이다.** 같은 계획·같은 버퍼 수(`hit=772k read=231k`)인데 512m 23~47s / 1g 1.7~2.1s — 차이는 read가 디스크로 가느냐 cgroup 페이지 캐시에서 채워지느냐뿐. 힙 477MB인 표에 512m 컨테이너는 "전체 걷기"류 쿼리에 10~20배 벌금을 물린다. #148(1G)이 맞았다.
6. **통제군 폭.** 같은 조건 두 패스가 A0 희귀 2,576↔1,284, A5 첫 페이지 6.1↔7.2, 1g A0 첫 페이지 7회가 두 무리. 이 호스트에 다른 세션 컨테이너가 있었다. 배수 2 이하는 이 폭 안이라 읽지 않는다.

## 판단 — #91 비정규화는 "지금은 안 한다"를 추천한다 (결정은 사용자)

- 목록: #127로 끝났다. B가 이기는 건 1% 구역뿐이고 그것도 7ms→0.7ms다.
- 검색: 느린 자리는 구역 필터가 아니라 **"결과가 적거나 없는 키워드 = 정렬 인덱스 끝까지 걷기"**로 옮겨 갔다. B는 그것을 구역 비율만큼만 줄인다. 그 자리의 후보는 (a) 검색에 **기간 상한**(예: 최근 1년 — 인덱스 걷기가 그 범위에서 끝난다, 커서 조건과 같은 꼴이라 Index Cond가 된다) (b) `title`만 `pg_trgm`(D1 재검토 조건 — 3자 이상 희귀어에서만 이긴다) (c) 검색만 정렬 인덱스를 못 타게 해 O의 비트맵 계획으로 되돌리기(`ORDER BY created_at + 0` 같은 꼴 — 흔한 키워드의 100배를 반납한다). (a)가 제일 싸고 제품 의미도 있다 `[추측]`. → #154.
- 되돌릴 조건: 구역 하나가 사용자 1% 미만인 채로 목록·검색이 D3 슬로우 쿼리 보고서 [2]에 보일 때. 또는 검색 기간 상한을 못 두는 요구가 확정될 때.

## rig를 만들며 걸린 것 (다음 사람용)

1. **bash는 스크립트를 실행하면서 읽는다.** 돌고 있는 `.sh`를 고치면 그 뒤 줄이 바이트 단위로 어긋나 `syntax error near unexpected token`으로 죽는다(연기 시험 1). 본 판은 스크립트를 복사해 두고 복사본을 돌렸다.
2. **`ANALYZE work_logs` 전체는 행 수와 무관하게 90~190s** — `trgm-lab`이 적은 en_US.utf8 `strcoll`(본문 표본 3만 행 정렬). 인덱스·컬럼이 바뀌어도 본문 통계는 안 변하므로 패스마다는 `ANALYZE work_logs (user_id, created_at, log_id, status[, ship_yard_area])`만 — 1~6s.
3. **`created_at || ' ' || log_id`를 `read a b`로 받으면 타임스탬프 안의 공백에서 갈린다.** 구분자를 `|`로.
4. **`INSERT … SELECT g.*, u.col FROM (서브쿼리) g JOIN users u`는 서브쿼리 컬럼에 별칭이 있어야 한다.** `gen_rows`에 `AS title …` 붙임. 그리고 `cols` 누적은 루프 안에서 초기화(첫 판에 `ship_yard_area, ship_yard_area`).
5. **CSV에 넣는 이름에 쉼표 금지** — 인덱스 컬럼 목록 `(a, b)`가 열을 쪼갰다. `·`로.
6. 백필 UPDATE 뒤 힙 두 배는 일반 VACUUM으로 안 돌아온다(끝 페이지만 자른다 — `autovacuum-lab`이 본 것과 같다). 패스 간 비교를 위해 `VACUUM FULL`을 넣고 그 시간도 이관 비용에 적었다.
