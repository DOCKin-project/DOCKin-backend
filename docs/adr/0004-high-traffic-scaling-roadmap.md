# ADR-0004: 대용량 트래픽 대응 로드맵 (출퇴근 버스트 트래픽)

- 상태: 로드맵 정리 단계, 구현 전
- 대상 코드/인프라: `AttendanceService`, `application.properties`(HikariCP), `compose.yaml`(nginx/app/redis/db)
- 작성 목적: 검색 도메인 확장(ADR-0003)과 달리, 이 주제는 도메인 자체에서 자연 발생하는 문제(출퇴근 버스트)이므로 합성 정당화 없이 바로 실측 기반으로 진행한다는 것을 전제로 로드맵을 정리한다.

## 1. 왜 이 도메인은 검색과 다른가

ADR-0003(검색 도메인)은 실사용 트래픽이 없어 합성 데이터로 필요성을 만들어야 했다. 반면 출퇴근 체크는 "새벽/아침/저녁 교대 시간에 전 인원이 몰린다"는 버스트 패턴이 도메인 자체에 내재해 있어, 별도 정당화 없이 실측을 시작할 수 있다. 즉 이 로드맵은 처음부터 "왜 이 문제를 다루는가"에 대한 답이 이미 있는 상태에서 출발한다.

## 2. 현재 상태 (그대로 두면 버스트에서 발생할 문제)

- `application.properties`에 HikariCP `connection-timeout`만 설정돼 있고 `maximum-pool-size`는 명시가 없어 기본값(10)으로 동작한다.
- `compose.yaml`에 `dockin-nginx`가 앞단에 있지만, `dockin-app`은 `container_name: dockin-app-1` 하나뿐이라 로드밸런싱이 아니라 단순 리버스 프록시 역할만 하고 있다.
- `dockin-redis`는 단일 노드, 메모리 100M 제한(원래 용도가 출근 분산락 전용이라 소용량으로 잡아둔 것).
- ADR-0001의 k6 테스트 계획은 "같은 유저의 중복 요청"(정합성 문제)만 재현하도록 설계돼 있고, "서로 다른 다수 유저의 동시 요청"(순수 처리량 문제)은 시나리오에 없다.

## 3. 단계별 로드맵

### 3-1. 베이스라인 실측

ADR-0001의 k6 시나리오에 두 번째 케이스를 추가한다: N명의 서로 다른 `user_id`가 09:00에 동시에 `clockin`을 호출하는 상황. 측정 지표는 평균/95p 응답시간, 에러율, HikariCP 커넥션 대기 시간(`hikaricp.connections.pending` 등). 이 숫자가 이후 모든 단계의 개선 전 기준값이 된다.

### 3-2. 애플리케이션 레벨 튜닝

- HikariCP `maximum-pool-size`, Tomcat `server.tomcat.threads.max`, Redisson 커넥션 풀 크기를 조정한다.
- 3-1과 동일한 시나리오로 전/후 비교 실측. 여기서 처음으로 "숫자로 증명된 튜닝"이 나온다 — 추정치로 튜닝값을 정하지 않는다.

### 3-3. 읽기 트래픽 분리

`getMyAttendanceRecords`, `WorkLogsService.readWorklog` 등 조회 API는 읽기 전용이다. `application.properties`에 이미 주석 처리된 AWS RDS 엔드포인트가 있어 RDS 사용을 염두에 뒀던 흔적이 있는데, 여기에 Read Replica를 붙여 조회 트래픽을 쓰기(clockin/clockout)와 분리하면 출근 버스트 중에도 조회 성능이 영향을 덜 받는다.

### 3-4. 수평 확장 (스케일 아웃)

- `dockin-app` 인스턴스를 여러 개로 늘리고, 앞단의 `dockin-nginx`가 실제로 로드밸런싱하도록 구성한다.
- 이 확장이 상대적으로 수월한 이유 두 가지를 확인해뒀다: ① JWT 기반 인증이라 서버가 stateless라 세션 스토어가 별도로 필요 없다. ② Redisson 분산락은 원래 다중 인스턴스 환경을 전제로 설계된 것이라(ADR-0001) 이 단계에서 락 로직 자체를 손볼 필요가 없다.
- 반대로 이 단계에서 처음 문제가 되는 것: WebSocket(채팅)은 각 인스턴스에 붙은 커넥션이 서로 다르므로, 인스턴스 A에 붙은 사용자에게 인스턴스 B가 받은 메시지를 전달하려면 Redis Pub/Sub 같은 브로드캐스트 계층이 필요해진다. 단일 인스턴스 때는 근거가 약했던 부분이 여기서부터 실제 요구사항이 된다.

### 3-5. 오토스케일링/백프레셔 (선택, 낮은 우선순위)

버스트 시간에만 인스턴스를 늘리는 오토스케일링, 과부하 시 429로 요청을 걷어내는 백프레셔. 개인 프로젝트 범위에서는 실제 구현보다 "필요성을 인지하고 있고, 왜 지금 단계에서는 안 했는지"를 근거와 함께 남기는 선에서 정리한다.

## 4. 우선순위 정리

1. 3-1(베이스라인 실측) — ADR-0001 k6 계획에 시나리오 추가만 하면 되므로 즉시 가능
2. 3-2(애플리케이션 튜닝) — 1번 결과가 나와야 튜닝 방향이 정해짐
3. 3-3(읽기 분리) — RDS 전환이 먼저 필요, 인프라 변경 수반
4. 3-4(수평 확장) — 가장 완결된 아키텍처 결정 서사가 나오는 구간
5. 3-5는 시간 여유가 있을 때만

## 5. 원칙

모든 단계의 수치(응답시간, 처리량, 에러율)는 k6 실측값만 기록하고, 아직 측정하지 않은 항목은 "[실측 필요]"로 표시한다(ADR-0001 관례를 그대로 따름).
